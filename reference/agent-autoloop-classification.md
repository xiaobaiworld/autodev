读的是线上 `main`（最新提交 `d3e6d26`，比我们锁定的 `8f8e2ee` 新；差别对分类没有影响）。本机锁定的仓库没动，这份是在 `/tmp/aal-latest` 里的只读副本上整理的。

## 1. 没有"任务类型"字段

事件和运行里没有 `type` 之外的分类字段，`rules.json` 里也没有"所属类型"。分类不是数据属性，而是**由规则本身承载**：规则的 `name`、`when`、`skill`、`to`、`access`、`parallel`、`askFirst` 等字段组合起来，就是一类任务的定义。类似的任务复制一份这组配置，不是写进同一个类型。

一句话：**同一类任务 = 同一条规则，不是贴标签。**

## 2. 作者给出的七个"场景模板"（README）

这七个是作者自己整理的类型，每个带规则、Skill 和启用说明。我把分类维度拉出来对比：

| 场景 | 触发 | 用什么 Agent（`use`） | 权限（`access`） | 并发 | 需要问人（`askFirst`） | 结果去哪 |
| --- | --- | --- | --- | --- | --- | --- |
| 每日早报 | `cron 0 8 * * *` | codex | edit | 没写（整条规则一个事项） | 规则里没写 `askFirst` | 本地 `briefs/<日期>.md` |
| 跟进 GitHub Issue | 定时轮询变成 `issues.opened` | codex | edit | 1 | 规则里没写 `askFirst` | 本地改代码，不推送 |
| 线上告警排查 | 外部 `shop` 发 `alert.*` | codex | **read**；重启走单独的 `command` 规则 | 3 | 删数据、停服、花钱、对外发消息、改产品方向、新建或轮换密钥、修改权限、动线上 | 卡片 + 可选重启 |
| 用户反馈处理 | 外部 `feedback` 发 `feedback.new`、`feedback.followup` | codex | edit | 3 | 同上七条 | 本地修复、交付 |
| 网站巡检 | `cron */5 * * * *` + 回执事件 `site.down`、`site.recovered` | 定时脚本 + codex | **read** | 没写 | 同上七条 | 卡片，异常不重复通知 |
| 飞书周报 | `cron 0 18 * * 0` + 回执事件 `brief.ready` | 定时脚本 + codex | edit | 没写 | 同上七条 | 本地稿 + 飞书简短摘要 |
| PR 自动交付 | GitHub 轮询到有标签的 PR | 内置 delivery 插件 | — | 2（README 里的示例规则） | 协议里由交付插件的固定步骤把关 | 合并、Ship、健康核对 |

可以提炼出来的**分类维度**：

1. **触发方式**：定时、外部事件、外部事件但自己轮询变成事件、GitHub 标签。
2. **做什么**：生成内容、修改代码、线上处置、读取与汇总、交付上线、清理。
3. **权限档位**：`read`（只看）、`edit`（在工作目录改，默认）、`full`（完整）。线上处置和网站巡检明确用 `read`。
4. **并发**：一个事项同时跑几轮，`parallel` 决定。
5. **askFirst**：七条共同红线——删数据、停服、花钱、对外发消息、改产品方向、新建或轮换密钥、修改权限。线上处置多一条"动线上"。
6. **结果去向**：只写本地文件、写文件且走交付插件、发卡片。

## 3. 另一套分类：GitHub 标签

作者自己把它用在仓库上，不是靠类型字段，而是靠 **GitHub Issue/PR 标签**（`plugins/delivery/poll.ts`、`delivery.ts`、`run.ts`）。标签就是类型：

- `deliver`：PR 走完整交付（审查、等 CI、合并、Ship、健康核对）。
- `deliver-review`：只审查，不合并。
- `deliver-attended`：有人盯着，问题留在回执不另发通知。
- `ask-owner`：普通 Issue 转成一张问题卡片发给本人，答完去掉标签。

分支名也当作分类：仓库里的分支只能以 `claude/`、`codex/`、`dependabot/` 开头，tag 只用于发布。

## 4. 还有两种例子：技能式工作流

`examples/skills/` 下有两个作者自己用的流程：

- `ship-pr`：把 PR 送上线。这不是在 Agent 里重做交付，而是封装交付插件的用法。
- `weekly-sweep`：每周清理一次代码。有固定的四步：定范围、逐个读、动手、收尾。读的时候问固定几条：旧东西删了吗、防护有依据吗、同一件事写了两遍吗、文档被改假了吗。

`weekly-sweep` 这种"工作流 skill"更像一个**定型的任务模板**：有编号的步骤、每步要问的几个问题、各步的产物。

## 6. 对我们的意义

- 作者没把"工单类型"当成数据字段来存，而是**让一类任务 = 一条规则**。类型多，就复制一份规则；类型少，就写得宽一点，用 `types` 的通配符接住。
- 分类的粒度，参考他们的切法：按**触发方式 + 做什么 + 权限 + 结果去向** 来定，不要凭空想象。
- `askFirst` 的七条是作者的红线，建议我们直接沿用，不要自己重新发明。
- "成熟工具"在他们那里有现成例子：`delivery` 插件就是最成熟的那一类，被规则调用，不走 Agent；`cron + command` 规则是半成熟的，走程序但由 Agent 后处理（巡检、读取）；`cron + codex` 和事件驱动的 Agent 是没成熟的，纯靠 Agent。
- 我没有在仓库里找到“同类 3 次自动提炼”这样的机制（搜了提炼、沉淀、第三次、自动生成 skill 等关键词，没有命中）。目前看到的做法是人工加规则、写 skill、把常用能力抽成 delivery 这样的插件。这只是没找到，不等于作者没有做。

## 7. 我没验证的

- 这些分类维度是我从示例里归纳的，作者没有在文档里直接写“我们这样分类”。
- “一类任务 = 一条规则”也是我的归纳，来自规则的写法，不是作者的原话。
- `ask-owner` 的卡片与 `deliver-review` 的审查结论在他们自己仓库上实际跑过没有，我没查提交历史。
- `weekly-sweep` 他们是否真的每周运行、运行了多久，没查。
