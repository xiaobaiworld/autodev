# 阶段机器人与协作展示：设计草案

日期：2026-11-08。状态：三层职责划分、条件式原型确认与分级审查原则已获用户确认；第一步已实现 S2/S3 的项目上下文快照输入和设计产出契约，飞书/Web 设计任务入口、条件式原型确认及 D019 运行策略仍待实施。先记录[需求边界](2026-11-08-stage-bots-requirements.md)。既有运行实现保持不动；设计审查策略的演进以 D019 为准。依据：D004、D008、D010、D011、D014、D016/D017、D020/D019。

同步说明：提交时已合入远端 v0.3.3 主线整合（D018），下述资产描述已据最新源码校正。默认 SRS/统一 Web/独立飞书已有 S2 交接，应直接复用；版本化兼容工作台另有独立存储和审核流程，不把两者混为一套。原草案在本地旧提交 2047bb4 上形成，其事实不能覆盖整合后的实现。

## 1. 核心结构

用户补充的设计约束：原有设计、资产、分析与流程是基础，已测试并使用的资产尽量保持；只有重大矛盾或冲突才讨论取舍。实现阶段优先扩展现有 S2/S3 模板和输入组装，不以阶段机器人为由重构后端。下文新增交接、在途控制均为后续候选方案。

阶段机器人是有上下文、有职责的工作入口。用户已要求设计单列，当前划分为需求、设计、开发、测试、优化五个逻辑工作区。一个入口可调用不同执行与审查角色；程序步骤仍由程序执行。阶段身份不与某个模型、进程或飞书 App 一一绑定。独立 App 数量待用户选择。

```text
飞书入口 / 本机工作台
          ↓
身份与任务绑定 → 阶段路由 → 查询、讨论、明确操作
                              ↓
                  AutoDev 控制器与本地记录
                       ↓             ↓
                 需求共享后端     现有流水线
                                      ↓
                              autoloop → 执行 Agent

状态与产物 → 交接记录 → 总览、阶段对话、通知
```

机器人之间的“交谈”是有目标、有证据的业务交接。Agent 提出结果或建议，程序校验产物、版本和转移规则后推进（D004）；飞书消息用于展示，消息是否送达不决定业务是否执行。

### 1.1 阶段、负责人 Agent 与机器人入口

用户进一步明确其交互目的：进入某个负责人 Agent，相当于默认带入“我的职责和目标是什么”，人不用每轮重新指定角色；后续每位负责人可以有独立上下文。这是已确认的设计方向，具体存储和恢复机制待定。

建议上下文由角色职责与目标、当前项目/任务、该角色的交流历史与待办，以及对共享正式产物的引用组成。独立交流历史用于延续讨论；需求、设计、决定等正式依据仍以项目当前有效版本为准，不在各角色记忆中另立真源。跨角色确认的决定应记录到共享项目产物，并让受影响角色在后续执行时读取；不要求每个 Agent 接收所有其他角色的聊天。

用户确认分层方向，并提出未来增加项目、安全、文档等独立负责人 Agent。需要区分三个概念：阶段定义何时做什么、交什么；负责人 Agent 定义由谁以什么职责和权限完成；机器人入口定义人从哪里找到它、与它交流。三者不要求一一对应。

多个机器人主要服务于人的辨识、按职责进入讨论、阅读对应产物及追问责任。一个机器人也可以路由到多个独立 Agent；多个机器人也不天然保证上下文、权限或执行隔离，这些仍由后端绑定与校验保证。独立角色可以复用同一模型；审查规则以 D019 为准，其他既有路径的 D008 代码校验尚未改变，不代表旧硬门槛继续优先。

建议每位负责人维护明确的职责、角色上下文、任务和产物关联；共享项目的需求基线与正式产物，不复制成互不一致的项目状态。独立 Agent 按需运行，一轮结束释放进程，等待人回复不占用执行进程，符合 autoloop 的轮次机制。

项目、安全、文档负责人可能跨多个阶段工作，不因增加负责人就新增执行阶段或关口。例如安全负责人可以在设计与代码审查节点提供报告，文档负责人可以检查需求、设计、实现与使用文档的一致性；这是职责示例，尚未确定触发点、阻塞权限和执行规则。项目负责人可汇总进展、协调待办、提出交接建议，但流程推进仍由确定性程序决定。

后续每加一个角色，先明确：负责什么、在哪些现有阶段参与、读什么、交什么、能修改什么、是否有阻塞权限。已有机制能承载则复用；存在实质冲突再讨论最小调整。单 App 多入口与多 App 多身份均可承载上述职责，具体呈现继续按人的使用体验选择。

## 2. 五个工作区与已有流程

| 工作区 | 负责的事 | 复用与边界 |
| --- | --- | --- |
| 需求 | 原文、澄清、校验、定稿及分析交接 | 默认复用 ReqSessionStore/SRS 与 handoff；兼容 SessionStore 的版本审核与确认保持独立，不自动互转 |
| 设计 | 完整设计、开发计划、界面原型及设计审查 | 包含 S2/S3；交付一致、可供开发执行的设计包 |
| 开发 | 编码、根据缺陷修复及代码审查 | 展示 S4、S6；S6 保持独立审查，不由编码者自审 |
| 测试 | 检查、使用验证、验收与缺陷交接 | 展示 S5、S7U、S8；S5/S7U 是程序，不能虚构为模型执行 |
| 优化 | 基于运行结果、失败或人工反馈提出改进 | 无现成独立执行阶段；提案先交需求流程，不自动自我修改 |

工作区是用户视角，执行仍按 S1→S2→S3→S4→S5→S6→S7→S7U→S8→S9 流转，不把五个入口误当成五个顺序执行的大步骤。S7/S9 发布信息放总览，S9 保留人工关口与当前仅本地发布的边界。

默认 SRS 路径已有 requirements.handoff.handoff_srs_to_pipeline：先校验定稿 SRS，生成可追溯的 S1 分析基线并初始化 S2，避免重复分析，设计机器人应复用该交接器。版本化兼容工作台的 JSON 草稿/确认包不自动转换为该 SRS 基线，其映射仍需另定契约。发现需求歧义返回澄清，不静默改写定稿。

### 2.1 设计工作区的输入与交付

用户已明确：设计以上游需求分析文档为输入，S2/S3 合为设计这一块，交出完整设计、最终开发计划和原型。首版沿用 design.md、dev-plan.md，并以 prototype.md 独立交付原型；设计稿包含接口契约。

输入以需求分析文档为主，同时可追溯需求原文、验收标准、已确认约束，以及已有架构、接口、可复用资产和测试证据。新设计必须说明怎样承接现有能力；发现需求矛盾先返回澄清，不由设计角色自行改变范围。

| 交付内容 | 下游必须能据此确定什么 |
| --- | --- |
| 完整设计 | 模块职责、数据流与数据模型、资产复用、必要变更及理由、异常与权限边界 |
| 定稿开发计划 | 改动范围、任务顺序与依赖、各项输入输出、接口先后关系、测试与验收映射、完成条件 |
| 界面原型与交互说明 | `prototype.md` 描述页面与导航、关键操作路径、主要状态（加载、空、错误、成功）、输入校验与反馈，关联对应功能与接口；无 GUI 时明确写不适用 |
| 接口契约 | 上下游交付包关系，以及软件模块/入口的调用方式、输入输出、错误、权限与版本约束 |
| 设计审查结果 | 对需求、计划、界面、接口一致性的审查结论、问题与修订回应；未解决的阻塞明确标注 |

“接口完整”包含两个层次：设计阶段交给开发阶段的资料完整；做出来的软件模块与各使用入口的契约完整。两者都不能靠编码者临场猜测。开发中发现契约缺口应反馈设计补齐；不要求设计冻结所有内部编码细节。

面向人的界面与面向程序的入口一起考虑。建议业务能力保持可复用，GUI、所需 CLI/API 使用同一业务语义。按需求决定是否需要 CLI、本机调用接口或 HTTP API，不把开放性自动等同于公网服务，也不要求每个项目都交付所有入口。有 CLI 时设计命令、参数、输出及退出码；有 API 时设计操作、请求响应及错误语义；人用界面的关键流程应能对应到底层能力。

S2 沿用设计与开发计划的产出职责，在本次设计中补清原型和契约要求；S3 沿用独立审查与有界修订，检查需求、计划、界面和接口是否一致。代码和模板目前只要求 design.md、dev-plan.md 等既有产物，尚未验证原型交付；未来是否补充模板与校验，必须先核对现有文件承载能力，再讨论最小改动。

用户最新明确设计完成的条件：按 D019 选择的审查策略完成审核或有效降级/免审放行；涉及需原型的用户界面时，原型还须人工确认；无界面交付不强制等待人工确认设计。交付内容或适用复用引用须指向同一需求基线、计划可执行、没有阻塞性接口问题。审查分级与条件式门槛尚未实现，不能声称现有模板已支持。

## 3. 交接与版本

每次交接至少关联项目、需求会话、确认版本/哈希、流水线运行、来源与目标步骤、执行轮次、输入产物、结论、证据位置。代码相关结论另绑定代码快照标识。字段是设计要求，尚未制定持久化协议。

- 需求→设计：默认复用 SRS 校验→生成 S1 基线→进入 S2/S3 的现有交接；版本化需求包的转换另定。设计机器人所需任务绑定、重复启动幂等和授权仍需按选定入口核对。项目路径与检查脚本必须显式配置，不能沿用演示默认 toy 项目及 todo 使用脚本。
- 设计→开发：交付同一基线下的设计、计划、适用原型、接口契约及审查/降级/免审记录，简单复用可引用已有产物加必要差异说明。满足选定策略才交接；有界面且需原型时还须人工确认，无界面不加通用人工设计确认。设计完成不自动替代启动开发的授权。
- 开发→测试：只有本轮产物通过校验才交接。开发声称完成不等于测试通过。
- 测试→开发：传回可复现缺陷、失败验收项和原始日志；程序按现有模板回 S4，有界修复与复测，超限转人。
- 优化→需求：提交依据、预期收益、验证方式与停止条件，人工选择后形成新需求；未经确认不更改现有规则或自动开始下一轮。
- 交接先落盘再执行；消息去重之外还要有业务交接标识。不同消息重复点击同一次“启动开发”，也不能创建两个运行。
- 回退不擦除证据；旧测试结论保留，但只能证明其绑定的需求与代码版本。新版本必须重跑受影响步骤，首版建议保守重跑后续步骤。

## 4. 人怎么参与

先区分“进入阶段交流”和“改变正在执行的任务”。每个工作区优先提供查看、讨论，以及对已有待决问题提交意见；恢复、退回、拒绝沿用现有人工关口语义。看文档、问原因不会自动暂停；自然语言不会自动批准发布、变更需求或跳过审核。

首选方案是交互层包装已有能力：需求交流复用需求后端，流水线人工处理复用 needs-human 与 resume。用户随时进入工作区不等于系统必须即时打断执行。先讨论这种参与方式是否满足目标；只有确认为不足，才采用下面的在途控制候选方案。

讨论回复来自阶段相关的输入、产物与日志，不表示正在运行的执行 Agent 已收到消息。凡会改变任务的意见，先给出拟生效对象与动作，让用户明确提交；业务含义不清时追问，不猜测。

在途控制候选（需确认实质需求后另作取舍）：运行中的修改建议先入本地收件记录，并显示“已收到，尚未生效”。若新增边界暂停，则禁止派发下一步，等待当前调用结束；当前结果保存为待处理，暂停期间不得转移或发布。显示“暂停中”直到当前执行结束，才显示“已暂停”。已交给中台、可能稍后启动的任务也属于在途任务，不能漏掉。这些都不是现有已验证能力。

暂停后，用户确认补充属于原需求澄清还是范围变更：前者作为新一轮输入；后者回需求模块形成新版本并重新确认。范围不明则继续等待。确认后程序创建新轮，旧调用的迟到结果不得覆盖新轮。恢复前展示将从哪一步、用哪份需求和代码继续。

“接管”首版指接管决定与输入，不宣称支持人和 Agent 同时修改代码。若需要人直接编辑代码，必须另行设计独占写入、快照和归还校验。

操作应绑定任务、当前状态修订号和目标版本，避免过期卡片批准新结果；暂停与恢复也要幂等。既有 CLI 的 resume 只接受 needs-human，不能直接当成运行中暂停接口。

## 5. 展示与交互示例

总览显示项目、需求版本、当前步骤、执行者、耗时、阻塞、待人决定及最近产物。五个工作区固定可进入；切换工作区不启动任务。阶段页显示对话、输入与产物、关键交接；设计页并列查看设计、开发计划、原型和审查结果。查看历史时明确标记历史版本。

下面是示意文案，不是现有功能或实际运行证据：

```text
活动报名 · 需求 v3 · 当前：测试 / S7U
开发：本轮实现已提交检查，代码快照 abc123
测试：使用验证失败，报名截止后仍能提交
       依据：验收 A4、usage.log 第 6 步
交接：已按规则退回开发 / 第 2 轮

[需求] [设计] [开发] [测试] [优化]
[查看证据] [提问] [处理待决问题]
```

飞书展示关键完成、失败、交接和人工问题；长文指向本机工作台或受权文件回传。本机网页不因飞书接入而公开到网络。完整日志保留按需查看，不把内部推理作为展示内容。消息明确标注“执行结果”“程序转移”“人工意见”“模型建议”，避免把建议包装成既成决定。

飞书命令可考虑 `/开发 查看 运行ID`、`/测试 提问 运行ID | 内容`，仅为交互草案；入口数量与群/私聊选择后再定命令、卡片和平台权限。不在本轮验证尚未选定的飞书 App 方案。

## 6. 实现前必须解决的接缝

下表用于识别复用边界，不表示每项都要修改。优先保持 autoloop、流水线模板、审查规则、检查工具、需求后端及已有飞书传输；交互与展示尽量在其外侧组织。自动交接、运行中控制若不纳入确认范围，对应改造也不进入实施计划。

| 位置 | 已读源码确认的现状 | 实施需要补齐 |
| --- | --- | --- |
| requirements.handoff / ReqSessionStore | 默认 SRS 已可校验并生成 S1 基线直通 S2，Web/独立飞书共用服务 | 直接复用；核对设计任务绑定与重复启动控制，不重复实现交接 |
| requirements.versioned_session.SessionStore / messaging | 兼容 API 有需求版本确认及渠道绑定，与默认 SRS 不互转 | 若接此入口再定义固定版到 SRS/运行的转换与授权关联 |
| channels.MessageGateway（已移除，D024） | 原身份白名单、应用路由、消息去重 | 不再可复用；阶段操作适配改在各机器人入口内，白名单与环境规则见 D023 |
| cockpit.Controller / driver.reply | resume 仅接受 needs-human | 在途操作收件、安全边界暂停、版本校验与恢复 |
| driver.run / setup | 命令执行期间持有全局锁；project 固定 toy；规则安装会替换配置 | 项目映射、控制请求不抢执行锁、避免覆盖需求规则；共享中台前专项验证 |
| pipeline 模板 / workdir | 有阶段转移、轮次上限、快照与审查 | 保持旧语义，增量关联需求版本；明确使用脚本配置 |
| web.api / web.ui / dashboard | 统一 Web 已展示默认需求、S2 交接、流水线和人工待办；requirements.web 为兼容网页 | 在统一客户端上补设计工作区，不重做已有驾驶舱或混用会话 |
| requirements.feishu_daemon / 兼容消息适配 | 默认独立飞书已有渠道无关 presentation；旧 autosys /需求 接口是兼容入口 | 选择复用默认入口或兼容入口后再接设计能力，不新开同 App 长连接 |

首版保持现有单执行通道，独立工作区不承诺同时跑多份代码。收件可独立落盘，由控制器在提交结果和转移前消费；不能让飞书线程直接改运行状态。具体锁顺序、崩溃恢复和中台取消协议在开发计划中细化后才编码。

## 7. 分步落地建议

1. 已完成：映射现有资产，将上游需求与项目说明输入、设计/开发计划/原型输出接入 S2/S3 与下游模板。
2. 下一步：实现渠道无关的设计讨论/修订操作，复用统一 Web 与现有 Feishu 展现适配；补足任务版本绑定与失败恢复验证。
3. 落实 D019 的审查放行记录和需原型时的条件式人工确认，再包装其他已有人工关口；运行中暂停仍需单独设计。
4. 展示总览和交接，保留现有需求命令回归。
5. 最后补优化提案入口。首版不自动改提示词、规则或代码，不形成无限循环（D011）。

验收覆盖需求稿 B01～B18，自动测试优先用假 Agent；真实平台、取消运行及收费模型验证单独说明范围和费用。每个小步通过测试和文档审计后提交同步。

## 8. 设计机器人工作说明 v0.1

状态：S2/S3 的输入清单、项目上下文快照、设计/计划/原型产物契约已实现；渠道交互、D019 放行策略和条件式人工确认尚未实现。适用于接入的目标项目；设计 AutoDev 自身时目标项目才是 AutoDev，不能把平台仓库的全部规则与资料混入其他项目。

### 8.1 独立业务能力与渠道边界

设计负责人是逻辑角色，负责与人讨论、组织 S2 产出和解释审查策略及结果。正常 S3 审核优先独立模型；降级、自检或免审依 D019 如实区分，不把作者自检伪称独立审核。角色上下文按目标项目与设计任务隔离，不以飞书聊天窗口作为唯一归属。

用户最新明确：独立模型审核是大多数任务的优先路径，跨厂商是增加视角独立性的方法，不是审核本身，也不是所有任务的强制条件。具体分级按 8.6 执行；只有一个 Agent/模型也允许继续，简单复用可免去额外模型审核。复制会话或重复运行同一模型仍不算双模型。这是设计审查策略，不等同于产品代码已执行自动测试。

记录各次实际可核实的模型标识、角色、产物版本和检查/审查结果；请求模型名与独立验证的实际模型须区分。不把缺少第二模型造成的降级放行写成独立审核通过。备用模型配置、策略选择与结果协议在实施前验证；现有 check_vendors 的强制校验仍未修改。

Web、飞书与未来微信只负责认证后的身份接入、任务绑定、操作转译和结果呈现。后端统一提供开始设计、查看状态与产物、提交意见、推进设计/审查、修订及导出等业务操作；操作名不是已实现 API。接口返回结构化结果和产物引用，具体展示文本、卡片或文件由渠道适配。设计判断、版本、完成条件和状态推进不得放在平台回调中。

不同渠道之间须经授权关联到同一设计任务，不能因为名称相同就自动合并身份或开放访问。沿用现有消息网关及配对模式评估接入；未来微信需根据实际平台落实身份与传输，不宣称替换入口即可直接上线。

### 8.2 输入清单

| 输入 | 内容与用途 | 缺失时的处理 |
| --- | --- | --- |
| 项目与任务标识 | 确定目标项目、读写范围和本次设计对象 | 不明确则先澄清，不写入猜测的项目 |
| 上游需求包 | 需求分析、可追溯的原文/确认版本、验收标准及约束 | 可讨论草案；缺少交付所需基线或有阻塞歧义时不能定稿 |
| 项目规则与决策 | 适用的项目规则、相关历史决定、禁止改动与批准边界 | 查指定入口；冲突列出出处交人取舍，不静默选边 |
| 已有资产 | 相关架构、模块与接口、可复用 UI、测试及使用证据 | 按范围查找，区分已验证与未验证；全新项目可明确无既有资产 |
| 设计历史 | 当前草稿、人工已确认意见、上一轮 S3 问题与修订回应 | 首轮可为空；后续轮必须关联本任务有效记录 |
| 可用工具与权限 | 已验证工具、适用范围、允许读取/输出目录、是否可联网 | 缺失能力要明示；不为完成任务自行安装、扩大权限或修改服务 |

输入清单由程序通过现有 input.md 和运行内项目资料快照记录来源、快照及用途；设计者与审核者读取同一上下文基线，审核另加本轮完整交付包。当前已快照 README 与项目配置列出的 context 文件；其他资料仍需受控加入清单，不能只凭角色记忆补造事实。长期对话如何裁剪与恢复另待设计，不靠常驻进程保上下文。

### 8.3 应读什么：入口固定，内容按任务选取

设计机器人自己的工作约定保持简短：职责、输入输出、工具优先、证据边界、审核与人工取舍方式。通用软件设计原则引用适用的既有规范，不在角色提示词复制整套教程。

项目资料按三类组织：

- 必需：本次需求分析与基线、适用项目规则、与任务直接相关的既有决定、当前人工意见。
- 按需：从文档索引定位的架构、数据与接口文档、相应源码和测试、已有界面与使用证据。读取源码用于核对资产与接口，设计阶段不修改产品代码。
- 不自动读取：其他项目、其他角色的全部聊天、无关运行历史、凭证与私人配置；不扫描整个用户目录。

以 AutoDev 自身为目标时，由受信的输入准备步骤先从 docs/INDEX.md、docs/TOOLS.md、docs/lessons.md、docs/DECISIONS.md 定位相关内容，并引用当前需求和设计；涉及底座时加入 D004/D014、地基方案和锁定版本协议，涉及模型时加入 docs/MODELS.md，涉及手机入口时加入 requirements/channels.md。next.md 用于识别当前目标，不把其中全部历史待办当成这次需求。已有原型只作为明确标注的参考，不当成已实现界面。

当前 pipeline/design 的 scope 限定只读输入清单，禁止运行时自行读取平台 next/lessons/全局规则，并限制无网络环境。这与受控资料包可以共存：项目 README/context 已由程序明确列入，AutoDev 平台规则按任务是否列入项目 context 决定是否提供。若后续扩充输入范围，须按需加入清单并验证；提示词约定不等于操作系统级权限隔离。

### 8.4 工作步骤与工具分工

| 步骤 | 工具优先承担 | Agent 或人承担 |
| --- | --- | --- |
| 接收与检查输入 | 校验项目、文件存在、绑定关系、版本和路径范围 | 判断关键业务信息是否齐备，向人澄清 |
| 核对资产与约束 | 文件检索、接口定位、已有证据与差异查询 | 判断能否复用、指出真正冲突及取舍 |
| 编写方案与计划 | 文件读写、现有模板与清单 | 架构、交互与接口设计，任务拆分和解释 |
| 制作原型 | 复用已有组件和设计资产；本地预览、截图与关键操作检查 | 设计使用流程，结合人工反馈修订 |
| 交付包预检 | 文件/引用检查、版本对应、需求与任务标识对应、缺项列表 | 判断覆盖是否充分，不能把结构检查当语义正确 |
| S3 独立审查 | 复用派活、结果校验与轮次控制 | 审查需求、设计、计划、原型及契约是否一致 |
| 修订与交付 | 保存新版本、差异与审查关联，生成交付清单 | 逐项回应，需业务决定或超限时请人处理 |

能由规则表达的动作不再交模型反复推断。工具选择先查现有工具手册和项目能力；工具缺失时说明缺口并讨论最小补齐，不把“工具优先”变成为每个动作新建一个工具。工具执行失败与检查不通过要区分；未运行的检查明确标注未验证。

已有可复用：input.md/模板、文件读写、S2/S3 派活与返修、done.json 校验与运行记录；SRS validator、handoff 交接器、项目上下文探测、统一 Web 与渠道无关 presentation/飞书入口。兼容消息网关与版本化工作台另行保留。第一步复用项目 `README.md` 和 `config.yaml` 中该项目明确列出的 `context` 文件，在每个 S2 轮次建立运行内只读快照并供 S3 共用；同轮重试保持快照不变，不自动扩展到其他资料。独立 `prototype.md` 已进入交付清单并传给 S4/S6/S8。交互式原型预览、交叉检查及设计包版本管理尚未成为完整工具链，需逐项验证。

### 8.5 交付包与完成条件

沿用 design.md、dev-plan.md、review.md 以及返修时 response.md 的现有职责。接口契约作为 design.md 的明确章节；独立 prototype.md 关联页面、需求、接口和开发任务；无 GUI 的项目在该文件说明不适用，同时设计其实际使用入口。

原型建议优先复用目标项目的界面资产；无既有载体时可讨论本地可预览 HTML，用示例数据展示主要交互，并明确模拟行为。原型的视觉精度待确定；静态截图只能证明外观，不能证明交互通过。飞书/微信查看原型的方式也待设计：本机 URL 不能直接作为手机可访问链接，不因此自动开放公网服务。

每版交付包关联项目、需求基线、设计版本、文件清单与审查结果。修订保留旧版，改变设计/计划/原型/契约后旧审查不能自动覆盖新内容。文件齐全与引用有效由工具检查，实际含义是否满足需求由 S3 与人判断。

完成门槛：输入基线明确；交付内容或适用复用引用齐备且版本一致；关键需求能对应到方案、接口/页面、开发任务和验收；没有阻塞性未决问题；按 8.6 的选定策略完成审核或有效降级/免审放行。条件式人工介入规则由用户明确如下：

| 本次交付范围 | 设计完成额外条件 |
| --- | --- |
| 包含需要原型的用户界面 | 人确认本次交付的原型与对应交互；模型审核不能代替人的使用体验确认 |
| 无用户界面，如纯后台、部署、程序间调用 | 明确原型不适用，满足其余条件即完成，不增设通用人工设计确认 |

是否需要原型应由需求与本次交付范围确定并记录，不能由 Agent 为了绕过确认临时声称“无前端”。无界面不等于无需技术设计；仍交付适用的方案、接口、计划与审查。业务歧义、重大冲突、审核超限以及既有发布/高影响操作关口仍按原规则处理，不被“无界面免确认”覆盖。

原型确认绑定展示版本；人工要求改变原型后，旧确认不能放行新版；若改动影响设计包，应重新判断本轮适用的审查策略，并记录对应新版的审核或放行依据，不能挪用旧审核。最终交付须有适用审查/放行记录及原型确认。仅查看不算确认，各渠道采用相同后端校验。具体版本与确认数据协议待实施设计。

现有 S3 PASS→S4 没有上述条件式原型门槛。未来应在 AutoDev 交付/流转层以最小改动落实：需要原型而未确认时不得交给开发；无界面沿用既有通过路径。不更改 autoloop 内核，也不为所有项目增加一道人为审批。界面相关未验证项与非阻塞遗留问题须明示。

首个设计机器人阶段先在此完成设计包和导出，不因用户查看结果或结束讨论自动启动 S4。衔接完整 build 流水线的启动授权、人工定稿方式及版本消费协议在后续实施计划中明确。

### 8.6 分级审查与可用能力降级（D019）

目的为平衡效率与最终精度。先判断能否简单复用，再为其余任务优先安排独立审核；不为凑模型数量重复工作，也不因只有一个 Agent 停住所有任务。

| 情况或能力 | 建议处理 | 如实记录 |
| --- | --- | --- |
| 简单任务且已有适用的已验证资产 | 引用原设计/工具/产物和必要差异说明，免去额外模型审核 | 复用对象、证据、适用范围、免审原因 |
| 正常任务，有不同 Agent 和跨厂商模型 | 优先独立审核 | 作者/审核者、模型、版本、结论 |
| 无上述组合，但有不同模型 | 同 Agent 切换模型或同厂商不同模型审核 | 实际模型与审核结果，注明独立性条件 |
| 只有一个 Agent/模型或备用模型不可用 | 用现有模型及适用工具完成检查后降级放行，不额外强制人工批准 | 单模型检查与工具结果、降级原因、未覆盖检查 |

简单复用的选择规则尚待定稿，建议至少核对当前需求和旧资产的输入输出、接口、约束/运行环境是否匹配，引用已有测试或使用证据；有实质变化时默认回正常设计路径，不以“做过类似的”为充分证明。工具检查可验证文件、版本和已知契约；业务等价不能只由文件哈希证明。规则允许 Agent 提建议，但最终分级和流转由程序按明确条件处理（D004）。

工具检查与语义审查按任务适用，简单复用不要求再生成一整套同义文档或额外自检调用。模型可用性优先复用已知配置和运行结果，不每次穷举所有平台；尝试次数/超时预算待定，不能无限重试以满足优选组合。

执行结果须区分独立审核通过、单模型降级放行和复用免审；免审/降级不冒充 PASS 的审核证据。现有 S3 只有 PASS/REWORK/BLOCK，未来需在 AutoDev 的策略、结果记录与转移层作最小兼容设计，保留既有严格路径测试，不改 autoloop 内核。已发现的实质阻塞不因审查者不可用而自动消失；既有授权及适用的人工原型确认继续有效。

| 原规则/位置 | 冲突或关系 | 本轮处理与剩余工作 |
| --- | --- | --- |
| AGENTS、README、D008、主线/旧设计、模型手册、重跑指南 | 强制作者/审核者跨厂商 | 改为 D019 优先；操作指南注明旧程序仍拒绝同厂商 |

这项变更与“尽量不动已验证资产”也兼容：只在旧硬校验与新目标明确冲突之处安排后续最小修改；已测过的派活、检查工具、事实日志和恢复能力继续复用。当前文档统一不等于现有程序已经支持单模型放行。
