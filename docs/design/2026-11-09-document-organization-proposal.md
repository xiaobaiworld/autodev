## 1. 目标与边界

让人和 Agent 从项目总索引进入任一阶段后，能够确定：该阶段负责什么、读取什么、输出什么、采用什么规范与模板、如何验证、怎样交给下游，以及当前哪些要求尚未实现。

本轮只交付文档及索引，不移动现有文件，不改变模板加载路径、SRS 存储路径、阶段顺序、状态协议、权限或服务部署。研究外部项目仅提炼候选方法，不安装或运行 LobeHub，不复制其实现。

## 4. LobeHub 的可借鉴方法

以下“上游做法”来自第 9 节来源，“AutoDev 建议”为本轮推导，不表示现有代码已经具备。

| 上游做法 | AutoDev 建议 | 对目录与文档的影响 |
| --- | --- | --- |
| 角色、模型、技能、连接器权限和资料分别管理；外部 Agent 另有执行设备与会话 | 分开描述阶段、负责人、执行器、模型、渠道和环境，沿用现有注册表 | 阶段目录按职责命名，更换模型或机器人不改变资料归属 |
| 区分助理文档、话题关联文档、独立文稿和上传资源 | 标明平台公共、阶段公共、目标项目、本次需求或运行等资料范围 | 正式设计归目标项目与任务，负责人维护它，但不形成独占副本 |
| 文档访问权限与上下文加载策略独立；资料按需查找 | 区分“允许读取”与“本轮必须读取”，每阶段列必读、按需和不自动加载清单 | 用入口和引用装配上下文，不在每轮读取整个文档库 |
| 任务关联说明、负责人、评论、运行与产物 | 沿用现有需求及运行身份，贯通原文、基线、产物、返修、人工决定与证据 | 各页面通过索引读取同一份产物，减少复制正文 |
| 协作有顺序、并行、迭代和辩论方式 | 顺序用于主链，迭代用于返修，独立专项检查可评估并行，重大取舍可进行对抗讨论 | 工作方式写入阶段说明；负责人协调不取代 D004 的程序流转 |

适配边界：继续复用 autoloop 和现有运行记录，不引入 LobeHub 的整套运行时、数据库或通用群聊编排。项目总览可读取最新状态；正式执行与审查仍绑定同一版本的输入快照，不能因“实时上下文”破坏可复现性。

## 5. 建议的组织结构

### 5.1 先区分资料的生命周期

| 资料 | 归属 | 说明 |
| --- | --- | --- |
| AutoDev 自身产品需求、架构、数据协议、决策 | 现有项目级 `docs/` | 说明平台本身如何工作 |
| 阶段职责、输入输出、规范、文档模板 | 建议的 `docs/stages/` | 可供多次任务复用的工作规则 |
| 目标项目正式需求、现有架构与业务约束 | 目标项目 | 当前 SRS 的 `docs/requirements/` 契约保持；AutoDev 自身作为目标项目时也适用 |
| 某次执行的输入、产物、日志、结果 | 现有 `workspace/runs/` | 保留需求、阶段、轮次与尝试关联 |
| 版本化兼容需求会话 | 现有 `workspace/requirements/` | 遵守 D018，不与默认 SRS 或流水线运行静默合并 |
| 外部研究与历史记录 | `reference/`、`docs/archive/` 等现有入口 | 不自动获得当前规则的权威性 |

### 5.2 各执行阶段建立入口

以下为原建议结构；当前目录已建立，S2/S3 已拆分契约与标准，其余阶段保留完整 README：

```text
docs/
├── INDEX.md
├── DECISIONS.md
├── DATA_SPEC.md
├── lessons.md
├── stages/
│   ├── README.md
│   ├── S1-analysis/
│   ├── S2-design/
│   ├── S3-design-review/
│   ├── S4-code/
│   ├── S5-check/
│   ├── S6-code-review/
│   ├── S7-release/
│   ├── S7U-usage/
│   ├── S8-acceptance/
│   └── S9-publish/
├── modules/
├── guides/
├── reports/
└── archive/
```

这是新增阶段导航的示意，未列出的现有目录不因此被删除。`modules/` 描述软件模块的实现与使用，`stages/` 描述流水线工作的契约，两者互相引用，不长期维护重复正文。

`stages/README.md` 同时映射人的工作区：需求对应澄清及 S1；设计对应 S2/S3；开发对应 S4/S6；测试对应 S5/S7U/S8；S7/S9 发布在总览可见。优化目前无独立执行阶段，继续管理为提案与改进记录，不为凑齐目录新增阶段。

每阶段先有一份完整 `README.md`，内容较多时再拆：

| 文件 | 职责 |
| --- | --- |
| `README.md` | 目标、边界、角色、实现状态、阅读清单与资料导航 |
| `contract.md` | 输入输出、版本与身份关联、下游消费者、异常交接 |
| `standard.md` | 工作规范、验证、通过与阻塞条件、返工和人工介入 |
| `templates/` | 本阶段需要的文档产出模板，按实际需求创建 |
| `examples/` | 已验证的匿名示例与典型反例，按需创建 |

常规说明保持浅层目录。若模板或案例确需更深一层，在阶段入口说明其用途和检索方式；不预建更深层的空分类。

### 5.3 模板、规则与运行证据的边界

- 执行模板 `templates/pipeline/*.json` 仍是当前程序加载的事实源，阶段文档链接到它；移动它需要另外修改加载者及回归测试。
- 文档模板可按阶段归属；现有 `templates/requirements/` 服务于兼容工作台，不能直接视为默认 SRS 的模板。
- 跨阶段的安全、数据、测试等规范保留唯一正文，阶段文档说明适用部分和验证入口。
- V2.1 的结构化模板、规则库、Schema、验证器有各自版本和执行职责，不能一律作为普通 Markdown 模板搬进 `docs/`；具体部署位置仍按采用对照的待定项另行设计。
- 实际输入输出留在运行目录；阶段目录只定义契约、格式与示例。历史运行不能因新模板发布而被覆盖或重新解释。

## 6. 阶段契约应当回答什么

1. 开始条件与必要输入是什么，来源和版本如何确定？
2. 执行角色是谁，允许读写哪里，使用哪些工具？
3. 必须交付什么，哪些产物按条件适用，怎样说明不适用？
4. 程序验证、模型审查和人工决定各负责什么？
5. 哪些结果允许交接，哪些需要阻塞、返工或转人工？
6. 下游消费哪个版本，修订后哪些旧检查或确认需要作废？
7. 通过什么日志、检查结果、代码快照或其他证据追溯结论？

当前 `pipeline/build` 的主要契约如下，供后续提取，不作为 V2.1 的目标产物清单：

| 阶段 | 主要输入 | 主要输出或结果 |
| --- | --- | --- |
| S1 分析 | 原始需求；默认 SRS 路径由 handoff 生成基线 | `analysis.md` |
| S2 设计 | 需求、分析、项目快照、返修及人工意见 | `design.md`、`dev-plan.md`、`prototype.md` |
| S3 设计审查 | 同一基线下的需求、分析、设计、计划、原型 | `review.md` |
| S4 编码 | 设计包、代码目录、检查与审查反馈 | 代码变更、`exec-report.md` |
| S5 检查 | 代码与模板配置的检查命令 | `check.log`、检查结果 |
| S6 代码审查 | 需求、设计包、完整差异、检查结果 | `review.md` |
| S7 发布候选 | 前序通过的代码与版本配置 | 本地候选标签、`release.log` |
| S7U 使用验证 | 候选代码、人写的使用脚本 | `usage.log` |
| S8 验收 | 需求、设计、代码差异、检查与使用证据 | `acceptance.md` |
| S9 正式发布 | 验收结果、人工批准、版本配置 | 本地正式标签、变更记录、`release.log` |

此表仅列主要内容；完成标记、事件、尝试记录等以模板、代码和数据协议为准。默认 SRS 到 S2 的交接与原始需求从 S1 开始的路径须分别说明。当前 S7U 使用脚本带演示项目假设，不应视为所有目标项目的通用验收脚本。

## 7. 资料关联与按需加载

目录决定存放位置，索引记录用途与关联。一份正文可以供项目、阶段和负责人等多个视角引用。建议在已有文档头部或索引中按需记录：

| 信息 | 用途 |
| --- | --- |
| 类型、范围、维护角色 | 区分规范、模板、过程产物、正式交付和外部资料；明确谁维护 |
| 状态、权威来源、替代关系 | 区分提案、已接受、已实现、已验证及历史版本 |
| 项目与需求身份 | 任务资料遵守 D022；阶段通用模板不绑定虚构的需求号 |
| 输入版本、阶段与轮次、下游引用 | 交付能追溯到来源，审查能关联到对应内容 |
| 证据位置与最近核对日期 | 判断结论覆盖范围，避免把文件存在当作行为已验证 |

这些是文档组织要求的候选项，不新增统一 JSON 协议；现有文件能表达时沿用，缺口再单独设计。

每阶段入口的阅读清单分三组：必读（阶段规则、有效需求基线和必要上游交付）、按需（相关接口、源码、决策与证据）、不自动加载（其他项目、无关历史和私人凭证）。读取权限继续由执行边界控制，文档清单本身不提供隔离能力。

## 8. 后续整理步骤与验收

建议先在 S2/S3 验证组织方式，再推广到其他阶段；实施前形成文件迁移清单并确认范围。

| 步骤 | 交付与验证 |
| --- | --- |
| 1. 清点现有资料 | 每份文件记录职责、状态、权威来源、目标位置及代码路径依赖；独有信息全部有去向 |
| 2. 建立 S2/S3 入口 | 当前模板实现与 V2.1 目标分别可查；每条输入输出能定位到定义与证据 |
| 3. 迁移阶段说明与文档模板 | 先建入口再迁移；更新相对链接、索引和引用，检查无信息丢失及重复事实源 |
| 4. 整理当前状态与历史 | `next.md` 保留有效目标，历史目标通过决策或证据入口可追溯 |
| 5. 推广与按需改程序 | 其他阶段复用已验证格式；涉及执行模板路径、存储路径或协议时另做设计与回归 |

验收标准：

- 接手者只读总索引与某阶段入口，就能回答第 6 节的问题，知道哪些内容还未实现。
- 每份重要规范与正式产物有唯一权威正文，多入口仅引用；旧决策和唯一历史证据不丢失。
- 所有被迁移内容可通过迁移清单核对，当前本地链接有效，程序使用的路径无遗漏。
- 目标项目需求、AutoDev 阶段规范、运行证据和兼容会话的归属清楚，未因同名文件或需求号被合并。
- 纯文档整理验证内容与链接；若修改运行依赖，再按项目要求完成相关自动化测试和人工验收。

本轮目录落实结果见执行记录。V2.1 可执行资产已在 design-system/ 与 src/designsys/，本轮新增入口互相引用；正式交付包持久化、版本协议及执行模板接入仍是后续运行能力设计，本提案不代替其定案。
