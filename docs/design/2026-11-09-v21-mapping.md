### 2.1 融合方案（用户 2026-11-09 确认）

以 V2.1 为骨架，此前的东西能并入的并入，其余放到别处，不硬塞进复杂度判定：

| 来源 | 并入位置 | 做法 |
| --- | --- | --- |
| V2.1 功能特征 | 判定的输入 | 整套采用：UI、持久化、API、认证、敏感数据、文件、AI、异步任务、外部集成 |
| `has_ui` | 特征“UI” | 对应，去掉 |
| `changes_data_structure` | 特征“持久化” | 对应，去掉 |
| `changes_interface` | 特征“API” | 对应，去掉；V2.1 的 API 特指 HTTP API，其余对外接口归入“外部集成” |
| `touches_real_env` | **新增特征**，补进 V2.1 | V2.1 没有，部署类与设备类需要 |
| 硬件设备 | **新增特征**，补进 V2.1 | 同上 |
| `reusable_verified_asset` | **不进复杂度判定**，放到审查策略 | 它是 D019 的免审依据，与“设计做多深”是两件事 |
| 三档复杂度规则 | 作废，改为 D0–D3 判定规则 | 沿用“程序按特征算”的思路，输入换成特征加风险 |
| 需求类型 | 与项目类型并列 | 见第 5 节 |

融合后三件事分开计算，互不混用：

| 要回答的问题 | 由什么决定 | 谁算 |
| --- | --- | --- |
| 激活哪些产物与规则 | 功能特征（叠加，越多越多） | 规则引擎 |
| 设计做多深 | 设计等级 D0–D3 | 程序按特征与风险计算 |
| 审多重、可否免审 | D 档、风险与是否有可复用的已验证资产（D019） | 程序 |

### 2.2 此前设计的缺口，融合后补上

1. **安全**：此前完全没有。并入后由特征触发 SEC 系列规则（认证对应 SEC-002，敏感数据对应 SEC-004，文件上传对应 SEC-006，AI 对应 SEC-007），**D0 也不豁免**。
2. **D0–D3 的判定规则**：V2.1 只给了各档“适用情形”，没有公式，MVP 1 要求“定义特征识别与 D0 至 D3 分类”，即由我们自己写。初版规则见第 4.2 节。
3. **特征由谁取**：见第 4.1 节。

### 2.3 D0 的“一页极简文档”（用户确认）

V2.1 的 D0 不出技术设计文档，只出规则选择、跳过设计的理由与开发交接。用户此前要求简单应用的设计文档“只有形式”。融合办法：**D0 保留一页，由程序从 `plan.json` 按模板自动生成**，内容仅有特征清单、规则选择、跳过设计的理由、开发交接。这是对 V2.1 的一处偏离：V2.1 不要求这份文档，这里为了让后续开发、验收和人工查看有可引用的东西而保留。它不是 Agent 写的，不会引入新的自述内容。

## 4. 特征识别与设计等级

### 4.1 特征由谁取（V2.1 没有解决的问题）

V2.1 第 6.1 节：由模型识别项目类型、功能特征、复杂度与风险，输出 A01；规则引擎再据此算出必需产物与强制规则，**覆盖模型提出的可选清单**。所以“产物与规则由程序算”成立，“特征由程序取”不成立：特征仍来自模型，模型识别错了，后面全部跟着错。

这就是此前演示中 C10、C12 暴露的问题，V2.1 只是换了说法，没有消除它。采用的缓解办法：

1. 特征由模型识别，**记录识别依据**（引用需求中的哪句话），写进 `plan.json` 的 `classification_rationale`（V2.1 已有该字段）。
2. **关键特征由程序再做一次独立核对**：敏感数据、触碰真实环境、认证、跨租户、高影响操作这几项，程序从需求文本里用确定性规则（关键词与模式）再扫一遍。与模型结论**不一致时，取更严格的一边，并进入人工确认**。
3. 模型识别的特征与规则核对的结果都留痕，便于统计误判，并用于 V2.1 第 14 节的规则固化。

这只是降低风险，不是保证正确，文档里不把它写成“已解决”。

### 4.2 D0–D3 判定规则（初版，需用真实需求校准）

输入：功能特征集合、风险条件、需求是否明确。**取满足条件的最高一档**；程序计算，模型只给建议。

| 条件 | 下限 | 依据 |
| --- | --- | --- |
| 无任何功能特征，且需求明确、无关键技术风险 | D0 | V2.1 第 3.2 节 |
| 仅有持久化或 API 之一，单模块 | D1 | 小型服务、CLI、单模块 |
| 有 UI，或同时有持久化与 API，或多模块 | D2 | 常规 Web/移动、多模块 |
| 敏感数据、认证、跨租户访问、高影响操作 | D2 | V2.1 风险覆盖等级：即使 UI 简单也必须启用相关安全规则 |
| 触碰真实环境，或技术上有重大不确定性，或高风险业务 | D3 | V2.1 第 3.2 节 D3 |

注意：D0 只表示跳过独立设计，**不豁免工程规则**（V2.1 第 3.2 节）。上表的阈值是初版，不是定论。

## 5. 需求类型与 V2.1 项目类型：两个并列维度

V2.1 的“项目类型”是按产品形态分：脚本、CLI、后端服务、Web、移动端、AI 应用、复杂平台。AutoDev 需求阶段的类型是按工作性质分：`SOFTWARE`、`DEPLOYMENT`、`HARDWARE`、`HYBRID`。两者回答不同的问题，不替代：

| 维度 | 回答 | 来源 |
| --- | --- | --- |
| 需求类型 | 这是什么性质的工作 | 需求阶段已经产出，交接时已写入 S1 基线 |
| 项目类型 | 产品是什么形态 | V2.1 |
| 功能特征 | 要激活哪些专项设计 | V2.1 |
| 设计等级 D0–D3 | 设计做多深 | V2.1，由规则引擎计算 |

**V2.1 没有部署类和设备接入类的位置。**需求类型保留的做法是对 V2.1 做三处补充，不改它的结构：

1. 项目类型增加两类：`部署与脚本工程`、`设备接入工程`。
2. 功能特征增加：`触碰真实环境`、`硬件设备`。
3. 默认设计矩阵（V2.1 第 3.3 节）与工程规则库各增加对应行与基线，例如部署类的预检、幂等、回滚，设备类的断线重连与模拟器。具体条目在做规则库时逐条给出，不在本文预设。

`HYBRID` 取各部分的特征并集，项目模板按各部分叠加。

## 6. 人工确认的位置（用户确认的第 2 点）

V2.1 的退出条件里没有“人工定稿”，只在第 16.2 节写了无法程序判定的高风险问题要“保留明确的决策状态”，并在第 13.3、14.1 节提到“人工确认队列”。你的要求落在这个位置：

| 设计等级 | 是否需要人工确认 | 谁判断 |
| --- | --- | --- |
| D0、D1 | 一般不需要，`ready_for_coding` 由程序计算 | 程序 |
| D2 | 默认不需要；规则引擎或模型评审标出“无法程序判定的问题”时进入决策状态 | 程序先判，拿不准时由大模型判断 |
| D3（复杂、高风险） | 可能需要，由决策状态触发，不是每个 D3 都强制 | 同上 |

要点：

- “需要不需要人工确认”**不由生成设计的 Agent 自己宣布**。判断分两步：先由规则引擎按特征和风险规则算出必须确认的情形（例如触碰真实环境、敏感数据、跨租户访问、高影响操作，V2.1 第 3.2 节的风险覆盖等级）；规则没有覆盖到、拿不准的，再由独立的大模型评审给出“是否需要人工确认”的建议与理由。模型的结论是建议，记录在案，不能让设计作者自己跳过（沿用 D004、D019）。
- 之前定的“有界面时原型必须由人确认”**不再是硬规则**：按你这一点，改为只在复杂类、或评审认为需要时才请你确认原型。这与 D019 的原话“有用户界面且需要原型时人工确认”不矛盾，“需要”的判断就交给上面这套机制。
- 人工确认进入后，沿用现有机制（`gate: human`、`driver.reply`），不由飞书线程直接改状态。
- 模型判断的记录：模型、版本、输入、结论、理由，写进 `validation.json` 或 `plan.json` 的决策记录，便于事后核对误判（V2.1 第 16.1 节“有效检出率”同理）。

仍然待你确认的：D2 默认不需要确认，是否可以；“模型判断需要人工确认”的置信度阈值怎么定；模型判断与规则冲突时以谁为准（V2.1 第 15.2 节写的是确定性结果优先，建议沿用）。

## 7. V2.1 与已有决定的其他张力

1. **与 D019**：V2.1 的评审策略（第 6.3 节：低风险单次生成加程序校验，中风险必要时独立评审，高风险多候选）是 D019“分级审查”的具体化，二者一致，D019 的“不得把免审或降级伪称独立审核通过”仍然适用。
2. **与 D023**：V2.1 要求版本化的规则库、模板库、Schema、验证器，需要单独的目录与发布流程（第 17 节）。是否放在本仓库内、是否独立成模块，按设计稿 `docs/design/2026-11-08-stage-bots-design.md` 的“独立部署边界”处理：随项目部署，不依赖个人全局文件。
3. **与现有流水线模板**：现在的 `pipeline/design` 只产 `design.md`、`dev-plan.md`、`prototype.md`，没有 JSON 产物、没有程序验证、没有 D0–D3。落地是**重做设计阶段**，不是小改；旧模板保留给旧运行，新旧并存期间用新的流水线类型区分（沿用 `cockpit/kinds.py` 的登记方式）。
4. **与设计 Agent 的权限**：V2.1 要生成可运行原型和结构化文件，设计 Agent 需要受控的写权限。此前模板的“只读输入、只产出设计文档”约束要重新评估，不放宽到修改目标项目代码。
5. **规模**：V2.1 完整落地包括 Schema、规则库、验证器、模板库。它自己给了 MVP 1/2/3 的顺序，本项目按此推进，不一次做全。
