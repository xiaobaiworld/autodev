# 阶段机器人：需求讨论稿

日期：2026-11-08。状态：用户授权继续设计；目标来自 autosys 会话「探讨多机器人协作与交互展示升级」，下列实施边界与验收提议尚未确认。设计见 [设计草案](2026-11-08-stage-bots-design.md)，决策讨论见 [D020](../DECISIONS.md#d020-阶段机器人与人机协作工作区)。

## 用户已表达的目标

1. 在已有需求机器人基础上，增加开发、测试、优化阶段机器人。
2. 机器人能够与机器 Agent 协作、交接，流程可以持续推进。
3. 协作过程通过适当方式展示，用户能理解当前进展。
4. 人愿意参与时，可以进入每个阶段，直接与该阶段机器人一起完成任务。
5. 基于 AutoDev 继续设计，当前不实现代码。
6. 用户本轮补充：考虑原有设计、资产、分析和流程，已测试并使用的资产尽量不修改；只有与本次目标存在重大矛盾或冲突时，才明确讨论取舍。新增交互方式不能直接成为改造执行内核的理由。
7. 用户进一步明确：S2、S3 归为独立的设计工作区，输入承接上游需求分析文档；输出包含完整设计、定稿开发计划与原型（界面设计），为下游开发提供完整衔接。
8. 设计同时面向人使用的界面与系统开放性；开发计划须考虑 CLI、API 等入口的需要，具体采用哪些入口按项目需求确定。
9. 用户确认按“交互工作区／S1～S9 流水线／autoloop 调度底座”分层继续设计，保留现有执行规则与底座职责。
10. 用户提出后续可能增加项目负责人、安全负责人、文档负责人等角色；每位负责人由独立 Agent 承担，通过文档和产物完成职责。多个机器人主要用于方便人按职责进入交流；是否对应独立飞书 App 仍待定，独立 Agent 不代表常驻进程或独立模型供应商。
11. 用户进一步确认：选择独立 Agent 相当于默认带入其职责和目标，减少人每次说明讨论范围的负担；后续每个 Agent 可以拥有自己的独立上下文。具体上下文存储和恢复方案尚未确定。
12. 当前先完成设计机器人的工作契约，再逐步实现入口：明确输入、输出、原则和项目特有读取规则；通用设计常识简要引用；能用工具完成的步骤优先使用工具，沿用项目一贯做法。
13. 用户明确：飞书只是展现形式。设计机器人的业务能力与渠道无关，Web、飞书、未来微信应使用同一套设计过程与记录；具体微信平台和适配不在本轮选择。
14. 用户明确设计完成的条件式人工介入：交付包含用户界面且需要原型时，原型必须由人确认。无界面的程序、部署等任务不强制人工确认设计；适用的技术设计、其他既有人工关口和阻塞处理保留。审查强度按下条最新原则决定。
15. 最新审查原则（D019）：大部分任务优先独立模型审核，争取不同 Agent、不同模型及跨厂商；这些是优先级，不是所有任务的硬门槛。只有一个 Agent/模型也允许继续；简单、已有适用验证资产的需求可以复用免审。取代此前“至少双模型、跨厂商强制”的讨论，目的为平衡效率与精度。同模型复跑仍不能伪称双模型审核。

“阶段机器人”是否对应独立飞书 App、怎样展现、人工介入是否立即中断任务，用户尚未明确；不得把下面的建议写成已确认要求。

## 建议的首版范围

- 一个项目总览，需求、设计、开发、测试、优化五个可进入的工作区；设计工作区包含现有 S2/S3，底层沿用现有流水线与需求后端。
- 每个工作区展示输入、当前任务、产物、阻塞、待决问题及关键交接记录。
- 人可以查看、讨论、补充、提出修改或交回自动处理；优先映射已有人工关口。运行中暂停属于待论证扩展，不是当前已确认要求。
- 先跑通一份确认需求到开发、测试、人工验收的闭环；优化以有证据的提案进入已有需求流程。
- 独立机器人数量、群或私聊布局待定。先保持现有飞书入口可用，不启动新连接、不调整部署。
- 本期设计不扩大自动发布权限，不加入无止境优化、多项目并行调度或新的自治 Agent 框架。

## 建议验收场景（尚未执行）

| 编号 | 场景 | 可观察结果 |
| --- | --- | --- |
| B01 | 需求审核并人工确认后交设计 | 记录固定需求版本与哈希，沿现有 S1 分析、S2/S3 设计流程衔接；同一次交接只创建一个运行 |
| B02 | 测试发现缺陷 | 绑定代码快照、验收项与证据，程序按已有模板退回开发；修复后重新检查 |
| B03 | 人在任务运行中发修改意见 | 明确是否已生效及可用的介入节点，不声称当前 Agent 已看到；实时修改或暂停另行确认 |
| B04 | 人只提问或查看 | 可以交流，不自动批准、取消或修改任务 |
| B05 | 人修改需求 | 原确认版本与历史结果保留；新版本确认后才执行，旧版测试不能放行新版 |
| B06 | 旧卡片、重复消息、重启 | 旧版批准被拒绝，重复交接不重复执行；状态与交接从本地记录恢复 |
| B07 | 查看协作过程 | 总览与阶段工作区指向同一任务、版本与证据；区分正在做、已完成、失败和待确认 |
| B08 | 优化提出建议 | 写明触发证据、目标与停止条件，经人确认后成为新需求，不直接改模板或生产代码 |
| B09 | 未授权或串会话操作 | 无法读取或修改未绑定任务；不同用户、对话、阶段的上下文不混用 |
| B10 | 设计交付下游开发 | 设计包或适用复用引用完整，版本、接口及验收映射明确；按所选策略审核通过或记录有效降级/免审放行；已知阻塞或所需原型未确认时不交开发 |
| B11 | 项目需要多种入口 | 设计说明人用界面及所需 CLI/API 的能力、输入输出、错误与权限边界；开发者无需自行猜测入口行为 |
| B12 | 同一设计经不同入口操作 | 经授权绑定后读取同一任务、上下文与设计版本；设计和审查校验由后端执行，渠道不另设流程或私有正式版本 |
| B13 | 工具辅助设计 | 输入检查、版本与差异、交付文件和引用检查优先由工具完成；记录工具可验证范围，未执行或无法验证的项目不报通过 |
| B14 | 无界面任务完成设计 | 明确原型不适用，满足本任务检查与审查策略且无阻塞后，无须等待人工确认设计；既有授权和发布关口仍有效 |
| B15 | 单 Agent 或缺少第二模型 | 可切换模型则优先切换，同厂商可用；仅单模型也可按降级策略继续，记录实际检查与降级原因，不额外强制人工批准、不伪称双模型审核 |
| B16 | 简单任务复用免审 | 关联旧资产与适用验证证据，明确需求及约束匹配情况，免去额外模型审核并记录免审依据；不必重写整套旧设计或强行调用两个模型 |

## 设计定稿前的选择

1. 飞书呈现为一个机器人多个阶段入口，还是独立阶段机器人？逻辑工作区数量不直接决定 App 数量。
2. 设计包含 S2/S3；需要原型的界面交付已明确须人工确认，无界面设计不强制人工确认。原型保真度、展示与确认操作的具体形式待定。
3. 需求确认是否同时授权进入后续执行？建议先单独展示“启动设计”，避免把确认文档等同于花额度执行；设计完成与启动开发的授权保持区分。
4. 人工参与沿用已有介入节点是否足够？先设计每阶段的查看与讨论；若必须中途影响执行，再对照现有机制讨论冲突，不能默认新增暂停或取消能力。
5. 分级审查与简单复用的具体选择条件、有限降级尝试方式待细化；用户已确认允许同厂商、单模型和免审方向，无须再次请求原则授权。
