# 设计阶段：典型需求、判定标准、结果与模板

日期：2026-11-09。状态：**初版，供逐项查看**，规则条件与阈值尚未用真实需求校准。依据决策 D025 与 [设计出口与分级](2026-11-09-design-exit-and-grading.md)。

本文的第 3、4 节是由程序按当前 `config/design-rules.toml` **自动生成**的，不是手写；修改规则后重新生成，才能保证文档与规则一致。第 5 节是每个类型的模板原文。

## 1. 怎么查看这份文档

建议顺序：先看第 2 节的判定标准，再看第 3 节的典型需求和第 4 节的结果，对每一行问一句“这个结果合不合理”。不合理的，记下编号，改规则而不是改结果。第 6 节列出我自己觉得有疑问的地方。

## 2. 判定标准

### 2.1 五个事实（是/否，由程序取得，不由 Agent 自述）

| 事实代号 | 含义 |
| --- | --- |
| `reusable_verified_asset` | 有可复用的已验证资产 |
| `changes_interface` | 新增或改动对外接口 |
| `changes_data_structure` | 新增或改动数据结构 |
| `has_ui` | 有用户界面 |
| `touches_real_env` | 触碰真实环境或设备 |

### 2.2 复杂度怎么判

1. 命中任一项，判**复杂**：`touches_real_env`。
2. 同时满足，判**复杂**：`changes_interface`、`changes_data_structure`。
3. 否则，若 `reusable_verified_asset` 为真，**且** `changes_interface`、`changes_data_structure`、`has_ui`、`touches_real_env` 全为假，判**简单**。
4. 其余判**常规**。

### 2.3 三档的设计详略与审查深度

| 档位 | 设计文档 | 审查 |
| --- | --- | --- |
| 简单 | 简略：只保留形式，写变化点并引用被复用资产 | 按类型模板只核对必查项；有适用的已验证复用资产时可免去额外模型审核，改由程序检查文件、引用与版本 |
| 常规 | 完整 | 完整模板，优先独立审核（不同 Agent/模型，能跨厂商优先），不足时按 D019 降级 |
| 复杂 | 完整，并写明风险与回退 | 完整模板，优先独立审核；降级放行时定稿时须向用户显式披露 |

### 2.4 交付物与需要你确认的事项

- **每次都交付**：`design.md`、`dev-plan.md`、`prototype.md`（无界面时 `prototype.md` 写“不适用”及理由）。
- 当 `has_ui`（有用户界面）为是，另交付：`prototype/index.html`。
- 当 `changes_data_structure`（新增或改动数据结构）为是，另交付：`data-spec.md`。
- 当 `has_ui`（有用户界面）为是，需你确认：界面原型须用户打开确认。
- 当 `touches_real_env`（触碰真实环境或设备）为是，需你确认：会改动真实环境或设备的步骤须用户确认。

## 5. 模板

### 5.1 各类型的设计章节与审查必查项（来自配置）

**SOFTWARE**

- 设计需包含：架构与数据流、资产复用及证据、接口契约
- 审查必查项：
  - 需求原文逐条对应到设计、接口、数据与任务
  - 接口契约足以让开发按计划执行
  - 有界面时原型覆盖关键操作与状态，无界面时说明不适用
  - 原型与数据规范互相对得上（两者都存在时）
  - 资产复用有证据

**DEPLOYMENT**

- 设计需包含：部署拓扑与脚本清单、预检与幂等、回滚、对运行中服务的影响
- 审查必查项：
  - 预检、幂等、回滚是否齐全
  - 对运行中服务的影响是否评估
  - 脚本清单与拓扑是否一致
  - 会改真实环境的步骤是否标注需用户确认

**HARDWARE**

- 设计需包含：硬件抽象层与设备协议、断线与故障处理、软件模拟器方案
- 审查必查项：
  - 设备协议与硬件抽象层是否清楚
  - 断线与故障处理是否齐全
  - 没有真机时能否用模拟器验证
  - 涉及真机或接线的步骤是否标注需用户确认

**HYBRID**：需用 parts 指明组成部分；各部分的章节与必查项取并集，另加：

- 设计需包含：部分之间的接口
- 审查必查项：各组成部分之间的接口是否对齐

## 6. 我自己觉得有疑问的地方（请重点看）

1. **C05 纯后端新增接口加数据表，判成“复杂”。**依据是“同时新增接口和数据结构即复杂”。很多普通后端需求都会命中，可能偏严；若觉得过严，可改为“再加上触碰真实环境才算复杂”，或只对数据结构迁移判复杂。
2. **C10、C12 的输入有矛盾，不是规则的结论。**C12“硬件换同型号设备”和 C10“部署换一台机器”我把 `touches_real_env` 设成了“否”，所以被判成“简单”；但它们实际上都会碰真实设备或服务，按常理应当是“是”，结果就会变成“复杂”。这是我为了演示故意放的，用来说明一个问题：**事实由谁判断、怎么取，比阈值本身更关键**，而这一点目前还没有定。请不要把 C10、C12 的“简单”当成规则的合理输出。
3. **“有可复用的已验证资产”这个事实谁来确认？**它直接决定能不能判“简单”并少审，而 D019 要求不能让作者自己宣布。现在规则只写了“有证据”，没有定义证据的格式。
4. **审查必查项的数量**：`DEPLOYMENT`、`HARDWARE` 只有 4 条，比 `SOFTWARE` 少，只是我写得粗，不代表这两类要求更低。
5. **C07 软件改动要改运行中的服务，类型仍是 `SOFTWARE`**，所以审查模板里没有“回滚、对运行服务的影响”这些必查项；复杂度虽然判了“复杂”，模板却没变。这说明“类型”和“是否碰真实环境”是两件事，是否需要给这类需求追加部署类必查项，需要你定。
6. **`HYBRID` 的必查项是两个类型各自清单的直接并集**（C13 共 10 条，没有字面重复）。但“会改真实环境的步骤是否标注需用户确认”只来自部署类，软件类里没有对应项；并集后各部分的要求是否对等、是否需要为组合类型单独补必查项，需要你看过 4.1 的逐条清单后判断。
7. 复杂度条件**不覆盖** APP、安全等规范的触发（见设计说明第 8 节），目前这些规范只登记了位置，没有内容。
