# 工单模型：分类、拆解、确定化、成熟工具（2026-11-06）

状态：**提议，只记录用户的要求和待讨论的问题，没有实现，也没有验证。** 来源是用户 2026-11-06 的几段说明（第 6、7 节是后补的日志审计与审核想法）。定下来之后再写进 `AGENTS.md`、`docs/DECISIONS.md` 和 `docs/DATA_SPEC.md`。

## 1. 用户的要求（按原意整理）

1. 每一项工作、每一个步骤都有上下文和日志。每一步可以用大模型总结，并把步骤和类型规范化。能用程序确定化完成的，尽量用程序。
2. 收到工单或需求，先判断它是不是已知类型：
   - 已知：按原有流程执行。
   - 未知：看 Agent 能不能把它拆解成已知的任务；拆不了，就是一个新类型，要记录下来。
3. 已知任务最终都要尽可能落实为程序，因为程序带来确定性。Agent 的作用是把任务拆成可以串联的不同程序。
4. 用 Agent 串联程序时，每个程序要说清：输入输出放在哪里、怎么检测、可能出现什么异常。
5. 重要任务要重复运行 3 遍或 5 遍，比对结果是否一致。程序多跑几遍几乎没有消耗，用这种方式保证稳定性和合理性。
6. 同类事情做满 3 次，且都能用同一套工具和逻辑完成，就提炼成 skill（成熟工具）：
   - 提炼时写清：这是什么事、用什么工具、前三次的情况；
   - 必须经人工审核，之后才归档为成熟工具；
   - 第 4 次识别出同类，直接用。
7. 类型的粒度：不能太细（没有复用价值），也不能太粗（没有区分意义）。怎么选，要和用户一起讨论。

## 2. 一张工单需要回答的问题（用户要求先记下来）

- 它怎么运行：经过哪些步骤，每步谁做（程序还是哪个 Agent）。
- 结果是什么：产物是什么、放在哪里、怎么判断对不对。
- 结果能不能重复：同样的输入再跑一遍，结果是否一样；不一样的话差在哪里。
- 类似的问题有哪些：它属于哪一类，以前做过几次。

## 3. 提议的流程（我的整理，待确认）

```
工单进来
  → 分类：查类型库，是不是已知类型？
     ├ 已知，且有成熟工具 → 直接用工具（程序）→ 检查输出 → 完成
     ├ 已知，但还没有成熟工具 → 按原有流程，由 Agent 做；记录本次（第几次）
     └ 未知 → Agent 提出拆解方案（一份文件）
              ├ 能拆成已知类型 → 按各自的方式执行，串联
              └ 拆不了 → 登记为新类型，请用户确认
  → 每一步：写输入、跑、检查输出、记日志和类型
  → 重要工单：重复运行 3 到 5 遍，比对结果
  → 同类做满 3 次且逻辑相同 → 生成提炼提案 → 人工审核 → 归档为成熟工具
```

### 与 D004 的关系（需要确认）

D004 规定流转由确定性程序决定，不由 Agent 决定。这里 Agent 负责分类和拆解，看起来有冲突。我的提议是这样协调：**Agent 只提出一份拆解方案（文件），由程序按类型库校验后才执行**；方案里出现类型库没有的步骤、或工具的输入输出对不上，程序拒绝并转人工。这样流转仍由程序决定。这一条我没有和用户确认过。

### 串联程序时每个程序要登记的内容

| 项 | 说明 |
| --- | --- |
| 输入 | 放在哪里、格式、必填项 |
| 输出 | 放在哪里、格式、怎么检查 |
| 异常 | 可能的失败方式，以及失败后怎么办（重试、转人工、回退） |
| 确定性 | 同样输入是否同样输出；不是的话，哪些字段会变 |

## 5. 待讨论（没有答案，不要当成已定）

1. **类型粒度**：按什么划分？比如按“产物形态”（写文档、改代码、查信息）、按“用到的工具组合”，还是按“需求领域”。需要看几个真实工单再定，不宜先拍脑袋。
2. **“同一套逻辑”怎么判断**：三次都用同样的工具序列？输入输出结构相同？还是人来判断？自动判断容易误判，建议先由人确认。
3. **重复运行怎么比对**：程序的输出可以逐字比较；Agent 产出的文档不可能逐字相同，比对标准要另定（比如只比对结论字段、比对关键数据）。
4. **哪些算“重要任务”**：由谁标记，在工单里加字段，还是按类型定。
5. **成熟工具放哪里**：`tools/` 目录？和 `docs/TOOLS.md`（那是外部工具手册）怎么区分？
6. **第一步做什么**（已做一半，2026-11-06）：用户确认方向，`state.json` 加了 `kind` 字段，路径写法（大类/子类），现在只登记 `pipeline/design`；以后分子类只是多登记一行（`src/cockpit/kinds.py`）。“步骤类型”字段、事件里的类型还没做。原先的想法：用户的意思是先保证每一步都有规范的日志和类型，再在日志上调优。建议先给 `done.json` 和事件加一个“步骤类型”字段，并统一记录每步的输入输出路径。具体做不做、字段叫什么，等用户确认。

**待确认的做法（未实现）**：每步结束由程序写一份 `record.json`，内容是程序能确定的事实——输入文件、输出文件、中台运行号、日志路径（并把日志复制进需求目录，避免丢失）、起止与耗时、用量、实际模型、verdict；“为什么”由 `done.json` 新增一个 `summary` 字段承载，由 Agent 写一句话，程序检查非空。这样“事实”由程序记、“理由”由 Agent 写，二者分开。

## 7. 在记录之上的审核与抽象（用户 2026-11-06 提出，尚未定）

**第二步，审核记录找优化点**
- (a) 哪些由模型完成的任务可以变成确定的程序，看能拆出多少。
- (b) 模型选择与判断标准：能否换更合适的模型，或把判断标准写得更清楚，让模型更容易做对。
- 多次出现的类似任务，提取成公共库。

**第三步，跳出工具层**：是否需要更好的工具、更好的流程；尝试抽象出新东西。抽象出新工具、认为有提升后，把原任务用新方式再跑一遍，与旧结果比较。

**与第 3 节流程的关系**：这是第 3 节“重复运行比对”和“3 次提炼成熟工具”的上游——先有统一记录，才谈得上比对和提炼；“用新工具重跑旧任务再比较”需要旧任务的输入被完整保存（第 6 节的 `record.json` 恰好提供）。

**风险（我的判断，未验证）**：审核若全交给模型，会出现“模型审模型”的循环，建议审核产出只是提案，采纳与否由人定，和成熟工具的人工审核一致。
