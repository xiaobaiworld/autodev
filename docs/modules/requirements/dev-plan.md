## 1. 本次交付与边界

交付一个能独立调用的需求澄清后端及 CLI 客户端：外部想法进入后，人与模型多轮梳理，另一个可选模型审核；可修订的问题先在两模型之间处理，需人判断或自动往返超限时暂停；当前版本审核通过且人明确确认后，导出固定版本需求说明书。

用户补充的开发约束：后端可供 CLI、网页及整个上层项目复用。按用户最新要求，本期实现后端、CLI 和本机网页；采用标准库 HTTP 与原生页面，不引入 Web 框架、消息队列或通用插件体系（D017）。后端返回结构化结果，展示层只负责收集输入和显示结果，不拥有另一套状态机。

不生成开发计划或代码，不修改既有 S1～S9 行为，不修改 agent-autoloop 内核；不扩展工具调用、模型内部推理或服务端上下文审计。v0.9 是本模块当前开发需求版本，不是会话内需求文档版本，也不是 JSON schema_version。

## 2. 规则读取与现有能力核对

已读取入口层（AGENTS.md、全局 README/GLOBAL_DEV_WORKFLOW）、项目层（next.md、TOOLS.md、lessons.md、D008/D013/D014、模块文档）及与本计划有关的专项条款：AI_LLM_INTEGRATION_STANDARD、DATA_MODELING_AND_FLOW_STANDARD、ERROR_HANDLING_AND_LESSONS_STANDARD、SECURITY_CODING_STANDARD、TESTING_STANDARD、OBSERVABILITY_STANDARD。专项源位于全局规范的 iCloud 目录。

已补读 Python/FastAPI 全局规范；基于现有标准库工程及本机单用户工具采用标准库 HTTP 适配（D017），业务层仍独立。网页纳入浏览器交互和响应式检查，远程部署与多用户规范暂不适用。原始交互按用户明确限定保存输入和模型回复，运行事件仅保存必要状态、计时及引用，不因通用可观测性要求重新扩展底层审计。

核对当前代码后的复用范围：

| 现有位置 | 本模块如何使用 | 必须避开的耦合 |
| --- | --- | --- |

## 3. 后端与入口的边界

```text
CLI 客户端       后续网页客户端       后续上层项目
     |                |                    |
     +----------------+--------------------+
                      |
            需求澄清后端 Python API
      create / submit / advance / status
         check / confirm / export / reopen
                      |
      +---------------+----------------+
      |               |                |
   文档与校验      会话与审核循环     模型调用适配
      |               |                |
   JSON -> MD     版本/原文/确认     既有 AutoLoop
```

- 后端不依赖 argparse、print/input、sys.exit、终端会话、HTTP request 或当前工作目录；数据根目录、调用器、时钟显式传入。
- status/check 返回可序列化的数据和稳定错误类型，包含当前阶段、问题、缺项、文档版本/哈希、审核状态与调用耗时；CLI 自行转换为文字和退出码。
- 文件存储是后端内部实现，CLI 和网页均不得直接改 session.json、审核或确认文件。
- advance 可耗时，status 可独立读取已提交状态；写操作在锁内检查 busy/版本，模型调用前落盘 working/reviewing 及调用标识。本机网页由后台线程调用同一 advance，本版不实现独立后台队列。
- 用户确认只能经应用接口执行。模型没有替人确认的接口，也不能把自然语言“同意”解释成人工确认。

拟新增的最小布局如下，文件可在实现中按实际复杂度合并：

```text
src/requirements/
  __init__.py       应用 API 导出
  document.py       文档/审核协议校验、哈希、Markdown
  session.py        存储、会话状态、版本、审核循环、确认
  agent.py          AutoLoop 适配及需求模块规则合并
  __main__.py       CLI 参数、展示、退出码
templates/requirements/
  checklist.json   通用清单
  clarify.md       带版本的梳理/修订提示词
  review.md        带版本的审核提示词
tests/
  test_requirements_document.py
  test_requirements_session.py
  test_requirements_review.py
  test_requirements_cli.py
  test_requirements_agent.py
  fixtures/requirements/    匿名固定案例及预期结果
```

不另建仓库或复制工具链；运行数据仍在被忽略的 workspace/requirements/。除非实证需要，本版不新增依赖；输出按固定 JSON 契约做字段、类型、枚举和引用校验，不开发通用协议框架。

## 4. 分步实施

严格按 M1 → M2 → M3 → M4 → M5 → M6 推进；前一步达标后再进入下一步。

### M1：文档、审核与本地校验协议

目标：不调用模型，也能判断草稿缺什么、能否送审核、能否交人确认。

- 先写匿名 fixtures 和 document 单元测试，明确需求 JSON、审核 JSON、清单、稳定问题 ID、来源引用及整包哈希。梳理者回应逐项关联 finding ID；审核记录关联所审版本/哈希，不把正文修改权限交给审核者。
- 实现 document.py、通用清单及 JSON 确定性生成 Markdown。check 区分结构齐全与审核通过后可确认；空标题、占位内容、未处理必需项、非法不适用、阻碍问题不能完成。
- 验证建议与已接受需求分开；非阻碍待定项允许明确保留。审核 PASS 仍带阻碍问题、引用缺失或所审哈希不符时拒收。
- 验收：R03～R05、R15 的纯校验部分通过；正文或清单任一变化使整包哈希变化；同一 JSON 多次生成 Markdown/哈希一致。
- 交付：document.py、清单、fixtures、测试及 protocol.md 的字段定稿。此时不接中台，不声称会话功能已完成。

### M2：会话、版本、原文与计时

目标：用可注入的假调用器完成多轮需求交流，保持历史与重启恢复正确。

- 先测 create/submit/status/check/confirm/export/reopen 的持久化；审核通过记录在本步用受控 fixture 注入，下一步接真实审核循环。明确首次 ready、重复消息幂等、不同内容同 ID 冲突、busy 拒绝、完成后只读。
- 实现 session.py 及 API 导出；保存 sources/messages、每次调用 input.json/raw-output.txt/call.json、不可覆盖的版本、审核引用、人工确认和必要事件。先保存输出及版本，再提交关联状态，定义事件已提交而状态未写的恢复方式。
- 注入 wall_clock/monotonic，成功、失败、超时和显式重试分别计时；模型返回成功但 JSON 无效时保留原文、记录协议错误。中断耗时未知，不用重启时间伪造结束。
- 先用故障注入覆盖写原始回复失败、写版本后崩溃、事件尾行中断、会话状态落盘中断与同一结果重复采纳。恢复时核对稳定 call/attempt ID；无法判断是否已派发时等人，不自动重复花额度。
- 验收：R01/R02、R06～R11；用户等待期间 show/check/confirm 不新增调用，不增加已结束调用的耗时。旧版本和旧确认在 reopen 后仍可导出，未确认新版本不得导出为基线。
- 交付：可直接由 Python 调用的后端基本流程与恢复测试，模块无需 CLI 即可使用。

### M3：可选模型与双模型审核修订

目标：完整实现 v0.8 的“先两模型交流，必要时人参与，最终人确认”。

- 先写假双模型状态序列：一次通过；REWORK→回应修订→复核通过；NEEDS_HUMAN；持续 REWORK 到上限；复核时文件变化；模型建议被误放正文；两模型一致但人未确认。
- 在现有配置格式内增加 requirements_analyst、requirements_reviewer 与 requirements_review_rounds；解析和 D008 校验独立于旧流水线角色。具体模型与上限不硬编码到业务逻辑；缺配置、非法正整数、厂商未知或相同应在调用前报错。测试显式注入上限，例如 2，不作为产品默认值。
- 创建会话时保存所选角色的 CLI、厂商、完整模型 ID、有效 effort 和上限快照；每次调用记录角色、类型、提示词版本和关联快照。不能把请求模型配置写成已验证的实际响应模型。
- 实现有界审核修订：结构不齐全等人；结构齐全送另一模型审核；可修复问题交梳理者逐项回应，再重新检查和复核；业务选择、缺外部事实或上限触发时等人。程序决定转移，模型只返回产物。
- 一个审核轮计一次审核者的逻辑复核调用；失败重试不冒充新审核轮，但须显式 retry，且不能绕过上限。达到上限后本次自动循环停止；人提交新决定后开始新的有界处理，累计历史保留。
- confirm 在锁内重新校验当前整包哈希及审核通过记录；修改后旧审核失效。用户不能只靠旧版 PASS 完成新版，也不能由模型直接完成。
- 验收：R12～R16 及 R06～R09 回归；每条审核意见、回应、修订、复核和待人决定事项都能找到原文与对应版本。
- 交付：审核闭环、版本化提示词、配置和假模型测试。此步仍无真实模型费用。

### M4：CLI、网页与公共 API 验证

目标：人在终端能够使用完整后端，且以后换网页不需搬移业务规则。

- 先通过 Python API 跑完整匿名案例，再为 create/reply/step/show/confirm/export/retry/reopen 写 CLI 测试。show 必须显示审核状态、待人问题、版本和计时，错误有明确退出码。
- __main__.py 仅负责参数和展示，调用公开 API。使用假适配器测试，避免子进程默认连真实模型。对同一输入比较 API 与 CLI 的最终需求、审核/确认关系及固定版本导出，忽略生成时间和随机 ID。
- 测试后端导入和调用不会读取 stdin、打印交互提示或退出进程；从另一个工作目录调用仍有效。并发 step/reply/confirm 明确冲突，不覆盖有效结果。
- 验收：R01～R16 的假模型端到端可演示；命令行退出和重开后状态完整，无后台自动花额度。
- 同步实现 web.py 的本机 HTTP 路由、固定白名单静态文件和原生页面：会话列表、新建/选模型、交流、需求预览、审核、逐次耗时、显式确认、导出、重试和 reopen。长调用后台执行，页面轮询。路由不复制业务逻辑。
- 先写 HTTP 测试覆盖 Host/Origin/CSRF、请求大小、非法路径、旧版本确认与 CLI/网页续接；最后在浏览器操作新建→补充→审核→确认→导出，检查窄屏和纯文本渲染。
- 交付：CLI、本机网页、API 契约、使用说明及 R17～R19 证据。

### M5：AutoLoop 适配与隔离验证

目标：接入既有执行能力，同时证明没有误改旧流水线规则或越过人工确认边界。

- 先用假 Hub/事实流测需求事件 ID、调用/尝试关联、状态重放、输出校验、取消和显式重试；然后用隔离 AutoLoop home、临时端口与假 Agent 联机，不操作用户原有中台和 Herdr 空间。
- 在 agent.py 独立合并 requirements.clarify/revise/review 规则，复用 Hub 和 RunTracker；只更新本模块拥有的命名空间，不覆盖既有 stage.* 规则及同名 Agent 配置。新规则重复安装幂等；失败有备份和恢复证据。
- 调用器只读取受控输入，结果回到受控输出目录；后端校验后才写需求版本、审核和确认。实测所用 CLI 的权限隔离，不能把提示词“不要改确认文件”当成权限保证；若现有方式无法限制访问，先解决隔离，再进入真实试用。
- 验证模型不能写确认文件或会话状态，外部文本不能改权限/配置/规则；路径穿越、越界符号链接、恶意 ID、凭证进入错误信息均须拦截。所有攻击验证只对临时目录里的测试文件进行。
- 上下文保留原文，不静默摘要或截断；调用前按已核对的目标配置检查容量，超过限制明确报错。具体模型能力和权限在本步核对，不从历史型号名推断。
- 原始输入输出与状态保存在 workspace；共享中台自己的底层日志是既有能力，本模块不解析、复制或宣传为“完整模型上下文”。费用/token 若已有可靠来源可展示，不为本版新增底层采集。
- 验收：隔离中台的审核返工、人介入、失败/超时/重启均可恢复；规则前后差异只涉及本模块；既有假 Agent pipeline/build 及全量单元测试通过。
- 交付：生产适配器、隔离联机脚本（默认假 Agent）、权限证据和兼容性结果。运行真实 Agent 必须显式选择，绝不作为默认测试路径。

### M6：真实双模型人工试用与阶段交付

目标：验证可用性，而不只是假模型协议正确。

- 先说明两角色配置、上限及真实调用会花额度；按项目规则验证完整模型 ID 和实际可验证信息，无法证明的项明确标注。具体默认模型、上限数值和权限在首次试用前落实，不要求现在补充业务需求。
- 用匿名“网站需求”案例完成：初始想法→问题回答→需求草稿→独立审核→实际发生的修订/人工决定→当前版本审核通过→人确认→固定版本导出。真实模型未发生的分支只引用假模型证据，不写成实测通过。
- 人工检查问题是否重复、建议是否冒充原需求、审核是否有用、何时打扰人、CLI 是否清楚；核对每次原始回复、角色、模型配置、时段和耗时，以及不包含用户等待时间。
- 试用报告给出需求版本、模型配置、轮次、问题、证据路径和已知限制；不能凭单次试用宣称质量稳定，网页交付须有真实浏览器交互证据。
- 验收：R01～R16 有验证对应；全量回归通过；用户可读已确认需求且下游可按固定版本读取，不接受变动的“最新版”指针代替基线；CLI 与网页交替使用同一会话。
