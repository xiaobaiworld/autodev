# 需求澄清模块：需求与验收

版本：v0.9。状态：2026-11-07 用户补充网页交付后的需求基线，尚未实现或验证。来源：用户与 Agent 的本次讨论，包括最后补充的模型选择与交叉审核。固定副本见 [v0.9 基线](baselines/v0.9.md)。接口细节见 design.md，不把设计提议写成已确认需求；原 v0.8 副本保留；本次把网页交互纳入当前交付，后续范围变更另建版本。

## 1. 已确认的目标

原始需求来自外部的人、业务问题或资料；大模型辅助梳理、扩展和补充，不能把自己的建议自动当成用户要求。

通过人与 Agent 多轮交流，逐步明确项目目标、使用者、业务场景、功能、特别约束等，最终形成采用标准结构、比较完整的需求说明书。需求以后可以补充，不要求一开始穷尽所有细节。

本模块是上层项目推进的第一个模块，逻辑上相对独立；输出与后续开发总计划、开发阶段及任务制定密切相关。现有任务执行器保留，后续按具体任务选择标准执行。

## 2. 工作方式

- 人提供背景、回答问题和决定取舍；Agent 参考经验清单，理解已有回答、追问缺口、提出建议、整理文档。
- 经验清单可来自通用开发经验、同类项目经验和事后复盘，明确哪些方面应询问或确认。
- 已回答的问题不重复询问；不适用项明确说明；需要时允许提出清单以外的问题。
- 程序承担保存、状态流转、清单与产物检查。内容推理主要由 Agent 完成。
- 需求梳理者与审核者的模型可分别选择，至少增加另一个模型作最终审核；沿用项目 D008，作者与审核者采用不同厂商的模型，不能只更换 CLI 名称。
- 审核发现问题时，先由两个模型交换意见、修订并复核；信息不足、涉及业务取舍、分歧无法解决或达到交互上限时，再请人参与。模型不能替人决定业务方向或自行增加未确认的需求。
- 必需章节、内容、清单项、当前版本的独立审核以及人的当前版本确认均满足后，程序结束本阶段，不再为“是否完成”额外调用模型。

## 3. 输入与输出

输入：原始需求文本、用户主动提供的资料、适用的经验清单、后续交流。

输出：需求说明书、模型审核结论与意见处理结果、确认记录、未阻碍下一步的待定项，以及可追溯的原始输入、交流、版本和每次调用计时。后续计划模块消费已确认的具体版本，不能只读取会变化的“最新版”。

第一版标准章节：项目背景与目标、使用者与业务场景、功能与业务规则、本期范围与不做事项、约束与特别要求、验收标准、待定问题。章节的具体字段及经验问题是设计提议，不代表已制定出成熟的网站需求标准。

## 4. 完成条件

程序只根据预先约定的规则判定：必需章节有有效内容、必需清单项已处理、不存在阻碍规划的待定问题、另一模型已审核通过当前版本、人确认的也是该版本。仅出现标题、关键词、两个模型口头一致或 Agent 自报完成均不够。审核后正文或清单发生变化，旧审核与旧人工确认不能用于新版本。

程序能够确认结构和状态，不能证明业务需求真实、完整或正确；语义判断通过交流和人的确认完成。

## 5. 第一版边界

包括：创建会话、加载经验清单、提交用户消息、选择梳理与审核模型、按轮调用 Agent、双模型审核修订、必要时邀请人参与、检查并展示缺项、保存需求版本、人工确认、完成后导出、重启续接、命令行与本机网页两种入口。

不包括：生成开发计划、项目调度、编码、发布、自动从历史项目提炼经验、远程访问、超过梳理者与审核者两角色的多 Agent 评审体系。第一版经验清单由人维护，复盘后再更新。此前排除双模型审核的范围约定由本次确认取代。

## 6. 验收场景

| 编号 | 场景 | 预期可观察事实 |
| --- | --- | --- |
| R01 | 只有“做一个网站” | 保存原始输入；Agent 产出澄清问题和草稿，不自动确认、不中途开始编码 |
| R02 | 用户连续补充 | 交流按序保存，新草稿有版本；已明确事项可沿用，不要求机械重问所有问题 |
| R03 | Agent 提议一个新功能 | 可看到建议来源及未确认状态；未采纳不能冒充用户要求 |
| R04 | 只有空标题或占位文字 | 本地检查列出具体缺项，不能完成 |
| R05 | 清单有不适用项 | 必须说明原因并供人确认，不因模型随意跳过而通过 |
| R06 | 结构齐全且独立审核通过，但用户尚未确认 | 等待人，不反复调用模型 |
| R07 | 当前版本独立审核通过，用户确认且本地检查通过 | 落盘完成事件与基线；检查不再调用模型 |
| R08 | 确认后文档发生变化 | 原确认不能用于新版本；原基线仍可查 |
| R09 | 重复提交、进程重启或异常输出 | 不丢已确认版本；不重复采纳同一轮结果；错误可定位并可继续 |
| R10 | 下游读取结果 | 获取固定版本需求正文、关联项目与确认依据；下游无权替人确认 |
| R11 | 逐次调用计时 | 成功、失败、重试分别计时；等待用户不计入；中断时无法恢复的耗时标为未知 |
| R12 | 选择梳理与审核模型 | 两个角色配置可选且可追溯；拒绝不满足 D008 的配置 |
| R13 | 最终审核发现可修订问题 | 审核意见先交梳理模型回应与修订，再由审核模型复核；保留双方原始回复与结论 |
| R14 | 无法解决的分歧、业务取舍或交互超限 | 停止自动交流，展示分歧、依据和待人决定事项；人回答后继续修订和复核 |
| R15 | 审核通过后当前版本发生变化 | 新版本须重新审核及人工确认，不能沿用旧版通过结论 |
| R16 | 两模型已形成结论但人尚未确认 | 展示当前需求、审核结论及保留问题，仍不自动完成 |

## 7. 原始交互记录（用户明确范围，2026-11-07）

保留外部输入和大模型输出即可，供后续分析和改进：外部输入包括初始需求、用户提供的资料、每轮回答与修改意见；大模型输出保留梳理、审核、回应与复核每次原始回复。按会话、轮次与角色对应保存，不用总结替代原文。模型之间传递的审核意见与修订稿属于后续调用的输入，按同一规则保存。

不继续向下记录工具调用、内部执行过程、模型内部推理或服务端上下文，也不为本模块另建复杂审计系统。需求版本和人工确认仍按完成条件保存。

原始交流保存在本机 `workspace/requirements/`，该目录已加入 gitignore；不自动上传或提交。经验分析与自动优化不纳入第一版。

每次模型调用由程序记录开始时间、结束时间和耗时，失败或超时也留记录。等待用户回答不计入调用耗时。此耗时是程序观察到的调用时长，可能包含中台排队、网络和工具侧等待，不等于模型纯推理时长。

R11 的计时验证：注入可控时钟，验证每次成功、失败和显式重试各有对应时间记录；用户长时间未回答不会增加已结束轮次的调用耗时；重启无法恢复准确耗时时明确标记未知，不伪造数值。

## 8. 当前未定

通用和网站清单具体条目、两个角色的默认模型及权限、首轮每次提问数量、审核修订轮次上限的具体数值，均未确定或验证，作为实施配置项处理，不影响本版的范围确认。实现先用假 Agent 验证协议；真实调用复用项目既有 Agent 配置能力，模型使用完整 ID。双模型审核已纳入本版本，不再列为排除项。

## 9. 本期网页与后端复用（v0.9 补充）

用户明确最终目标是在命令行和网页中均能进行需求迭代、审核、人工确认与完成导出，本期应实际交付两种入口。二者复用独立后端与同一份会话数据，可交替续接；网页不是静态展示或只读原型。网页只监听本机，远程访问和多用户权限系统不在本版。

| 编号 | 场景 | 预期可观察事实 |
| --- | --- | --- |
| R17 | 网页新建、回答、审核、确认与导出 | 在浏览器内完成全流程，耗时调用期间可查看状态，错误可恢复 |
| R18 | CLI 与网页交替操作 | 读取同一会话、版本与审核结果，业务校验一致，不重复调用或确认旧版 |
| R19 | 网页安全与展示 | 本机监听、拒绝跨站修改和非法路径，外部文本按纯文本展示，模型无权伪造人工确认 |
