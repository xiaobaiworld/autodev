# 需求澄清模块：设计与实现计划

状态：2026-11-07 方案草案，未实现。需求真源为 requirements.md。以下接口、目录和字段为实现提议，评审后再写代码。

## 1. 边界与复用依据

现有 `Controller`、`driver.run` 和 `driver.reply` 用于任务流水线，`start_run` 从 S1 开始，`write_input` 解析分析、设计、检查等固定输入名称；CLI 持有 workspace 单实例锁，并安装中台派活规则。不能仅新增一个 kind 就声称已支持长期人机需求交流。

本模块采用独立的小状态循环，不修改现有 S1～S9 行为，也不修改 agent-autoloop 内核。复用 `cockpit.store.atomic_write`、锁、Agent 配置读取及中台能力；`Run` 的事件结构包含 stage/round 等流水线字段，需求会话不为复用它伪造开发阶段。`driver.record.parse_log` 可用于解析已取得的日志；其余派活、记录函数依赖现有 state 格式，接入时核对后使用，不把需求会话强塞进去。

先提供 Python API 和本机 CLI，不建 HTTP 服务。未来项目管理层直接调用同一 API。

## 2. 状态与循环

```text
创建会话 → ready
ready → working → 本地校验
                    ├─ 需要用户回答／确认 → waiting-human
                    ├─ 结构或协议错误 → error（保留上次有效版本）
                    └─ 有效草稿 → waiting-human
waiting-human + 新回答／修改意见 → ready
waiting-human + 确认当前版本 → 本地检查 → completed 或返回具体缺项
error + 显式重试 → ready
```

`ready` 表示有一条新用户输入待处理；每条输入最多触发一轮 Agent 调用，不因文档缺项自动循环消耗模型。合法草稿即使缺内容也应展示问题并等人；结构无效才进入 error。轮次及调用超时有上限，超限转给人处理，具体值复用配置或实现时明确设置。

程序从不解析自然语言“可以了”来自动批准。人使用明确的确认操作，指定版本；若用户只想继续讨论，照常提交消息。

完成后的会话只读。补充需求时显式 reopen，创建后续修订，保留原基线；重新确认前不覆盖下游已引用的版本。

## 3. 文件与数据协议

建议目录：`workspace/requirements/<session_id>/`（保持在现有被忽略的 workspace 内）。

| 文件 | 职责 |
| --- | --- |
| `session.json` | 会话 ID、project_id、状态、当前版本、待处理消息、调用编号、确认及错误引用 |
| `sources/` | 用户提交的文本或显式导入资料，保留来源；不自动扫描用户目录或联网 |
| `checklist.json` | 创建时使用的经验清单快照与版本，运行中不随全局模板静默变化 |
| `messages/0001.json` | 按序保存用户与 Agent 交流、来源、时间、待确认问题；不改写历史 |
| `rounds/0001/` | 本轮 input、Agent 原始输出、错误、归一记录；含模型配置、可获得的模型证据和用量 |
| `versions/0001/requirements.json` | 结构化需求正文、清单状态、来源和待定项；不可覆盖 |
| `versions/0001/requirements.md` | 从同版本 JSON 确定性生成的可读需求说明书 |
| `versions/0001/check.json` | 本地检查结果和具体缺项 |
| `confirmations/0001.json` | 用户显式确认的版本与内容哈希、时间；不由 Agent 写入 |
| `events.jsonl` | 顺序事件及状态快照，用于审计和恢复 |

结构化正文是该版本的真源，Markdown 是派生阅读产物，禁止两份分别编辑。Agent 返回草稿与问题，程序校验后保存版本和生成 Markdown；用户修改通过新的消息或受控导入产生新版本。

正文按固定章节键存储，每节文本不能为空；核心功能与验收项用带稳定 ID 的列表。清单项含 `id`、`status`（open/answered/not-applicable）、回答或原因、来源消息/资料引用；建议需注明 proposed 或 accepted。阻碍规划的 open 项必须解决，非阻碍项可保留但需由人随整版确认。Agent 的引用只说明声称依据，程序检查引用存在，内容吻合由人检查。

需求中的外部文字只作为数据，不得修改模型权限、状态、清单完成规则或确认记录。路径由程序生成，外部 session_id、版本号和产物路径必须校验，不能越界读写。

## 4. 清单与完成校验

模板建议位于 `templates/requirements/`，第一版通用与网站两份清单；网站是在通用条目上追加，先不开发复杂的继承系统。每项规定 ID、问题说明、是否必需以及允许不适用的条件；具体条目与真实需求案例一起打磨。

`check(session)` 为纯本地函数，返回 `ready_to_confirm`、`missing[]`、版本及内容哈希。它检查章节和列表的有效内容、已知占位内容、必需清单项、引用有效性、建议状态及阻碍项。不能承诺识别所有敷衍文本，检查通过仅说明可以交人确认。

`confirm(session, version, hash)` 在持有会话锁时重读版本、重新检查并记录用户操作；仅当前版本且哈希一致才能完成。生成一份确认覆盖的整包哈希（正文及清单处理状态），避免只改清单却沿用旧确认。Agent 没有调用 confirm 或写确认文件的权限。

人工确认是独立动作，因此没有已确认记录时返回 waiting-human；不为判定完成再调用模型。

## 5. 拟定调用接口

| Python 操作 | 行为 |
| --- | --- |
| `create(project_id, initial_text, checklist)` | 校验输入、落盘来源与清单快照，返回 session_id |
| `submit(session_id, text, message_id)` | 保存消息，重复 message_id 返回原结果；忙碌时明确报冲突，第一版不加消息队列 |
| `advance(session_id)` | 推进一轮，调用已配置的 Agent 或等待当前结果；不隐式确认 |
| `status(session_id)` | 返回状态、当前问题、检查缺项、当前版本和错误 |
| `confirm(session_id, version, hash)` | 本地检查与人工确认，通过后完成 |
| `export(session_id, version)` | 返回该已确认版本正文、文档、确认引用，供计划模块消费 |
| `reopen(session_id)` | 显式开启修订，不撤销或覆盖旧基线 |

CLI 只是同一接口的薄入口。第一版人在终端阅读问题和文档、提交回答，不开发聊天网页。

## 6. 日志、恢复与权限

每轮记输入、用户消息引用、清单和文档版本、模型配置、实际可取得的模型证据、工具/命令日志、输出、用量、错误；区分配置模型和实际模型，不把启动参数当服务端模型证明。Agent 的需求建议不是程序确认事实。

单会话单写者；共享中台配置的变更还须遵守现有 workspace 锁。启动时记录 attempt 和派活关联 ID，超时/崩溃后先核对已有运行，不直接重派；无法判断则 error 并提示人工处理。持久事件先落盘、快照后更新，恢复时验证序号；版本及确认文件不可覆盖。假 Agent 测试明确覆盖在两次写入之间退出的恢复。

实现前核对中台的事件去重与实际调用接口：现有模型日志可能分散在中台，必须复制归档。记录失败不能宣布完整完成，应显示可恢复错误。默认无网络、无代码执行、无仓库修改；真实 Agent 是否能强制满足读写范围需集成验证，提示词限制不能冒充权限隔离。

### 6.1 原始交互与后续分析分层

用户明确要求把交互过程作为原始审计日志。原始记录只追加，修正通过新记录关联旧记录；需求版本是整理产物，分析报告是派生产物，三者不得互相覆盖。

- 每条消息保存原文、角色、稳定消息 ID、时间、会话和轮次、回复关联；区分用户原话、Agent 建议、程序校验反馈与人工确认。
- 每轮保存实际交付 Agent 的输入和上下文快照（包括清单、需求草稿及显式提供资料的版本），不能只存会变化的文件路径。外部文件引用保留导入内容及哈希，不自行扩大资料读取范围。
- 保存可取得的原始 Agent 输出/事件流、工具调用及返回、失败、重试和模型用量证据。未取得或被 CLI 截断的字段明确注明，不声称保存了模型不可见的内部推理，也不声称完整记录了服务端隐藏上下文。
- 用户可见消息与原始 Agent 输出分别留存；如果界面只展示节选，记录它对应哪份原始输出。人工确认关联实际展示的文档版本及哈希。
- 用会话 ID、轮次/attempt ID、消息 ID、文档版本和事件序号串联输入、过程、产物和决定，便于回答“哪次交流形成了哪个需求”。追加日志及哈希用于追溯和发现意外修改，第一版不宣称具备防篡改审计保证。
- 原始资料位于 workspace 内并验证 git 忽略规则；凭证不应进入输入，意外暴露时需支持安全处置，不能因追加规则拒绝移除敏感数据。后续分析默认本地，若需调用外部模型分析原始业务资料，另行确认数据范围和授权。

补充验收：假 Agent 多轮交流包含用户纠正、工具输出、一次失败重试及最终确认；重启后可按关联 ID 查回各条原文，历史版本不变。检查派生需求/分析未覆盖原始消息、输入快照不随源文件变动、资料不会被 git 跟踪。经验分析与清单自动优化不纳入第一版。

## 7. 测试与分步落地

先定义可验证事实和测试，再实现；全程不启动收费 Agent，除非进入明确说明的真实试用步骤。

| 步骤 | 范围与验收 | 验证及收口 |
| --- | --- | --- |
| M1 本地协议 | 清单、需求 JSON、Markdown 生成、完成校验；空章节、占位、open 必需项、未采纳建议不能直接完成 | 先写匿名 fixtures 与单元测试；文档同步后小提交并 push |
| M2 会话循环 | create/submit/status/confirm/export/reopen；版本绑定、幂等、不可覆盖历史 | 假 Agent 测试 R01～R10；并发冲突、重启和落盘中断；小提交并 push |
| M3 Agent 与 CLI | 接现有中台和配置，归档每轮日志；进程失败/超时可定位；等待用户时无后台重复调用 | 假 Agent 端到端，再跑全量 unittest；文档同步、小提交并 push |
| M4 人工试用 | 用“网站需求”走完多轮澄清并读出固定版本需求说明书；检查真实权限和日志 | 使用真实 Agent 前说明额度，记录用户观察及证据；阶段结束按项目流程创建 PR、文档审计、等待合并确认 |

测试命令：`PYTHONPATH=src python3 -m unittest discover -s tests`。新模块测试放现有 tests，避免仅因逻辑独立复制一套仓库工具链。

每一步先更新 next.md 的范围和验证方式，完成后三问回顾、同步相关文档、更新 changelog 再提交。设计阶段只审阅文档与链接，不声称功能已通过测试。

## 8. 与后续模块的契约

输出稳定的 `project_id + session_id + version + hash + 文档引用 + 确认引用`。计划模块据此制定计划；发现需求缺口时返回澄清问题，不能自行改变已确认需求。开发阶段和任务可以引用同一基线，之后修订的影响分析留给项目推进层，本模块只保留版本关系。

待用户评审：第一版终端交互是否合适、需求说明书章节和清单条目、是否采用结构化正文派生 Markdown。这些选择尚未当作既定实现。
