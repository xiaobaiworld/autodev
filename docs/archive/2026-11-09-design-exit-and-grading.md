# 设计阶段的出口、复杂度分级与按类型的完成条件

日期：2026-11-09。状态：用户已确认方向，实施未开始；对应决策 D025。本文只定规则与产物，不表示模板或代码已按此实现。依据：D004、D019、D020、D022、D023，设计稿 `2026-11-08-stage-bots-design.md` 第 8 节。

## 1. 要解决的问题

现有 S2/S3 只有一条通用路径：产出 `design.md`、`dev-plan.md`、`prototype.md`，审查通过就结束，且设计审查不分轻重。这有四处不够：

1. 设计的完成条件不分类型，原型只是文字说明，没有数据规范。
2. 简单需求和纯后端项目也走同样重的设计与审查。
3. S3 通过后流水线直接结束，没有“定稿”这一步，也没有启动开发的授权。
4. 设计稿说“设计阶段不自动启动开发”，但模板里 S3 通过即进入后续，二者矛盾。

## 2. 两个维度

**类型**沿用需求阶段的 `req_type`：`SOFTWARE`、`DEPLOYMENT`、`HARDWARE`、`HYBRID`。它按需求取，不按项目取；同一项目的不同需求可以是不同类型。交接时已经把它写进了 S1 基线，不新增字段。

**复杂度**分 `简单`、`常规`、`复杂` 三档，决定设计做多少、审查做多重。

## 3. 复杂度怎么判

由程序按可追溯的条件判定，Agent 只能给建议，作者不能自己宣布“简单”来绕过审查（D004、D019）。条件如下，每条是“是/否”：

| 条件 | 含义 |
| --- | --- |
| 有可复用的已验证资产 | 能指向既有设计或实现，并附测试或使用证据 |
| 新增或改动对外接口 | 调用方、被调用方、输入输出有变化 |
| 新增或改动数据结构 | 实体、字段、关系、存放位置有变化 |
| 有用户界面 | 有人直接操作的页面或交互 |
| 触碰真实环境或设备 | 会改动运行中的服务、系统配置或硬件 |

初版规则：

- **简单**：有可复用的已验证资产，且后四项全部为否。
- **复杂**：触碰真实环境或设备，或同时满足“新增接口”与“新增数据结构”。
- **常规**：其余情况。

这些条件和阈值写进配置文件由程序读取，具体取值是初版，先按它跑，用误判记录调整，不引入评分系统。

## 4. 复杂度决定的设计与审查

| 复杂度 | 设计 | 审查 | 记录 |
| --- | --- | --- | --- |
| 简单 | 设计文档只保留形式，写得非常简略：变化点加对被复用资产的引用，不重复写已有内容 | 仍按该类型的审查模板审，但只核对模板里的必查项；有适用的已验证复用资产时可免去额外模型审核，改由程序检查文件、引用与版本 | 复用对象、证据、适用范围、免审原因；不得标成“审核通过” |
| 常规 | 完整设计包 | 优先独立审核（不同 Agent/模型，能跨厂商优先），不足时按 D019 降级 | 作者、审核者、实际模型、结论或降级原因 |
| 复杂 | 完整设计包，并写明风险与回退 | 同常规，且降级放行时必须在定稿时向你显式披露 | 同上，并列出未覆盖的检查 |

已发现的实质阻塞不因审查资源不足而消失。

## 4.1 审查模板：按类型选，按复杂度定深度

审查有两个独立的选择，不要混在一起：

- **用哪套模板，由类型决定。**每个类型有自己的审查模板，写明该类型设计必须核对的内容。
- **审多深、由谁审，由复杂度决定**（第 4 节）。简单需求仍用该类型的模板，只核对其中的必查项。

| 类型 | 审查模板的必查项（初版） |
| --- | --- |
| `SOFTWARE` | 需求原文逐条对应到设计、接口、数据与任务；接口契约足够开发执行；有界面时原型覆盖关键操作与状态；原型与数据规范互相对得上 |
| `DEPLOYMENT` | 预检、幂等、回滚是否齐全；对运行中服务的影响是否评估；脚本清单与拓扑是否一致；是否有会改真实环境而未标注需确认的步骤 |
| `HARDWARE` | 设备协议与硬件抽象层是否清楚；断线与故障处理；没有真机时能否用模拟器验证；涉及真机或接线的步骤是否标注需确认 |
| `HYBRID` | 各组成部分按各自模板审，另加部分之间的接口是否对齐 |

做法：

- 现有 S3 只有一段通用的任务说明。改为“通用部分 + 按类型的审查模板”，模板放在配置里，S3 的任务说明按需求类型拼出来，不为每个类型复制一份模板文件。
- `SOFTWARE` 模板就是现有 S3 的要点，所以对 `SOFTWARE` 的行为不变，旧测试保留。
- 新增一个类型的模板是加一段配置，不改流转代码。
- 模板只定义“核对什么”，结论仍是同一套（通过、返修、阻塞，以及 D019 的免审与降级放行），不另立结论。

## 5. 设计的出口：四个状态

| 状态 | 含义 | 谁推动 |
| --- | --- | --- |
| 设计中 | S2 产出、S3 审查，可返修，受轮次上限约束 | 程序 |
| 待定稿 | 审查通过，或按 D019 免审/降级放行，设计包齐全 | 程序到此停住 |
| 已定稿 | 你确认了这一版设计包；需要原型的，原型也已确认 | 你 |
| 已移交开发 | 你单独授权后才启动 S4 | 你 |

要点：

- **出口是“已定稿”，不是“审查通过”。**审查通过只让它进入“待定稿”。
- **定稿与启动开发是两步。**与设计稿“不因查看结果或结束讨论自动启动 S4”一致，也保留一次反悔机会。
- **定稿绑定版本。**设计包的任何改动都使旧的审查、旧的原型确认和旧的定稿作废，必须重新走。
- 返修超过轮次上限、业务歧义、重大冲突时，按既有规则请你处理，不被“简单”绕过。

## 5.1 过程产物与最终交付物

从需求文档到设计定稿，中间会产生很多东西，**但最终交付的是通过审查（或按 D019 免审/降级放行）的那一整套设计包**。两类要分开：

| | 内容 | 去向 |
| --- | --- | --- |
| 过程产物 | 需求分析（`analysis.md`）、复杂度判定记录、每一轮的设计草稿、审查意见与回应（`review.md`、`response.md`）、事件日志 | 留作审计和追溯，不作为交付物，不要求人去读 |
| **最终交付物** | **设计文档（含接口契约）**、开发计划、**界面原型**（有界面时）、**数据规范**（有数据结构时）、按类型要求的其他规范（第 6、8 节）、审查或免审记录 | 审查结束、你定稿时整套冻结为一个版本，交给开发和验收引用 |

要点：

- **设计文档任何情况下都要交付**；简单需求只是写得短（只写变化部分），不是不写。
- **所有交付物都由设计 Agent 按需求和上述步骤生成**，包括原型页面和数据规范，不由人手写。人只在定稿时确认、在需要时提意见返修。
- 定稿时程序把这一套交付物冻结成带版本号的交付包，并生成清单：文件列表、各文件的指纹、对应的需求版本、审查或免审记录、你的确认记录。开发阶段只读这个冻结版本，不读过程草稿。
- 交付物之间必须自洽：原型里的数据能在数据规范里找到，设计文档里的接口与数据规范一致；这由 S3 审查核对，程序另做引用和版本的结构检查（只能证明文件齐全，不能证明含义正确）。

## 6. 按类型的完成条件（最终交付物必须齐全的内容）

“有界面”“有数据结构”以及是否追加 APP、安全等规范，都由第 3 节的条件和第 8 节的清单判定，不由 Agent 自述；前端展示与后端数据是两份主规范，其余按条件追加。**没有界面的项目（含纯后端服务）不做原型、也不要求你确认原型；非常简单、没有新数据结构的需求不做独立数据规范。**

| 类型 | 必须齐全 |
| --- | --- |
| `SOFTWARE`，有界面 | 设计稿（含接口契约）、开发计划、**可打开的界面原型**、**数据规范与数据结构定义**、审查或免审记录；原型须你确认 |
| `SOFTWARE`，无界面 | 设计稿（含接口契约）、开发计划、审查或免审记录；有新数据结构时另有数据规范；原型文件写“不适用”及理由，不要求你确认 |
| `DEPLOYMENT` | 部署拓扑与脚本清单、预检/幂等/回滚设计、对运行中服务的影响评估、审查或免审记录；会改动真实环境的步骤须你确认 |
| `HARDWARE` | 硬件抽象层与设备协议、断线与故障处理、软件模拟器方案、审查或免审记录；涉及真机或接线的步骤须你确认 |
| `HYBRID` | 取各部分要求的并集 |

## 7. 界面原型的要求

- 形式：**一个能直接打开的页面**，用示例数据演示主要页面和数据交互。
- 重点：把**数据之间的业务联系**用视觉呈现出来，例如实体如何关联、操作如何影响哪些数据。
- 可以没有：动效、真实后端连接。
- 必须明示：页面里哪些是模拟行为、哪些数据是示例。
- 仅凭截图只能证明外观，不能证明交互通过；确认以你实际打开操作为准。
- 手机上查看的方式待定，本机地址不能直接给手机用，不因此开放公网服务。

## 8. 规范集合：两份主规范，其余按条件追加

设计要交付的规范不是一份，而是一组，按项目与需求取用。**最主要的两份是前端展示和后端数据**，其他规范只在条件命中时追加，不默认全做。

| 规范 | 产物 | 地位 | 何时要求 |
| --- | --- | --- | --- |
| 前端展示规范 | 界面原型页面（见第 7 节） | **主规范** | 有用户界面 |
| 后端数据规范 | `data-spec.md`：数据实体、字段与类型、约束、实体间关系、存放位置、版本与迁移 | **主规范** | 新增或改动数据结构 |
| APP 规范 | 待定义 | 追加 | 有移动端 APP |
| 安全规范 | 待定义：认证、权限、敏感数据、对外暴露面 | 追加 | 涉及认证、权限、敏感数据或对外暴露 |
| 其他（如接口、部署、硬件） | 按类型在第 6 节列出 | 追加 | 按类型或条件 |

要点：

- 规范集合做成**可登记的清单**：每种规范有名称、产物文件名、触发条件、审查要点。新增一种规范是加一行配置，不改流程代码，与 `config/bots.toml` 同一思路。
- 两份主规范的关系是前端展示呈现“数据之间的业务联系”，后端数据规范把这些联系落成结构；S3 审查时要核对二者一致：原型里出现的数据必须能在数据规范里找到，反之亦然。
- 触发条件复用第 3 节的“是/否”判定，由程序判断，不由 Agent 自述。
- APP、安全等追加规范的**具体内容和触发条件目前没有定义**，初版只登记名称和位置，不预设内容；用到时再按真实项目补，不提前写成空模板。
- 同一份 `data-spec.md` 作为后续开发和验收的共同引用。

## 10. 机器人在设计这一段做什么

- 只读：`/list`、`/status`、`/design`（视图模块已实现，尚未接入）。
- 会改变状态的：`/revise <意见>` 提意见让设计返修、`/approve` 定稿、`/start-dev` 启动开发。这三个不由飞书线程直接改状态，要走现有的人工关口与 `driver.reply`（设计稿第 6 节要求）。
- 机器人入口不放判断逻辑：复杂度、版本、完成条件、状态推进都在后端，Web 与飞书只负责身份、绑定和呈现。

## 11. 实施顺序

1. 本文与 D025 经你过目。
2. 复杂度规则与按类型的“完成条件”做成配置，加纯函数判定，先写测试。
3. S3 结论扩展与“待定稿”关口，改模板与转移，保留旧测试。
4. S2 的原型页面与 `data-spec.md` 产物及其审查要点。
5. 机器人接入只读指令，再接 `/revise`、`/approve`、`/start-dev`。

每一步通过测试、文档同步后再提交。
