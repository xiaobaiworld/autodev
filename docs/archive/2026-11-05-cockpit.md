# 驾驶舱：Herdr 四窗格加终端状态界面（2026-11-05）

状态：提议，用户已确认方向（窗格 4 块、Agent 每次调用重启进程、先做终端文字界面、布局由用户手动分一次）。与 `2026-11-02-autodev-design.md` 第 3、5、9 节配套，冲突时以本文所述范围为准并回写那几节。

## 1. 需求

### 1.1 目标

在 Herdr 的一个工作区里搭出 AutoDev 的运行界面：一个窗格跑主控程序并持续显示各 Agent 状态，另外几个窗格分别跑具体 Agent，用户能直接看到它们在干什么。

### 1.2 必须做到

| 编号 | 要求 |
| --- | --- |
| R1 | 工作区固定 4 块窗格：主控（含状态区）、claude-opus、codex、agy。各 Agent 窗格与 `config.yaml` 的 `agents` 一一对应 |
| R2 | 主控窗格持续自动刷新，每个 Agent 显示：窗格地址、当前角色与阶段、状态（运行中、等待、已结束、丢失）、本次已用时间 |
| R3 | 主控程序就是设计文档第 5 节的流程控制程序：按 `state.json` 推进九阶段，通过 `hc` 调度 Agent。界面只是它的一个视图，关掉界面不影响流程 |
| R4 | 每次调用 Agent 前在对应窗格重启 Agent 进程，不复用对话；Agent 之间只通过文件传递信息（设计 3.3 节） |
| R5 | 状态区下方显示当前需求、阶段、轮次，以及待用户决定的事项数量 |
| R6 | 主控重启后能从文件恢复，并重新认领 4 个窗格，不依赖界面内存 |

### 1.3 不做

- 程序自动分屏。布局由用户手动划分一次（`hc` 没有分屏方法，旧 `herdr pane split` 连不上桌面应用，见 `docs/lessons.md` L001）。
- Web 界面（D010 保留，后做）。
- 多目标项目、跨机器 `--on`。第一阶段只用本机。

### 1.4 验收

在 4 块窗格里跑一个玩具需求的 S1 到 S3，状态区能看到 Agent 在运行中、等待、已结束之间变化；强杀主控再启动后，流程从上一步继续，窗格被重新认领；每次调用的对话互不相连。

## 2. 设计

### 2.1 布局

```
┌──────────────────────┬──────────────┐
│ P0 主控 + 状态区       │ P1 claude    │
│                      ├──────────────┤
│                      │ P2 codex     │
│                      ├──────────────┤
│                      │ P3 agy       │
└──────────────────────┴──────────────┘
```

用户在 Herdr 里右键手动分成这 4 块。主控启动时在 P0 里运行，其余三块先是普通 shell。

### 2.2 窗格认领

`hc ls` 返回终端地址、`where`（空间与标签页）、当前前台进程。主控启动时：

1. 读 `hc ls`，筛出与自己同一 `where` 的终端。
2. 绑定方式分主次，不是二选一（P0 已验证标签可用，`hc ls` 不带标签，要逐个 `hc get` 读，见 L004）：
   - 主方式：在每个窗格里用 `hc label <t> role=claude-opus` 打标签，主控按标签认领。
   - 备用方式：标签缺失或读取失败时，改用 `workspace/cockpit.json` 里手填的地址（不进 git）。
   - 两种方式认领出的结果不一致时，拒绝启动并打印差异，不自行取舍。
   - `config.yaml` 的 `cockpit.panes` 只记角色列表和一个 `claim` 字段（`label` 或 `address`）指定主方式。
3. 4 块没凑齐就拒绝启动并打印缺哪块，不自动创建。

### 2.3 一次 Agent 调用

沿用设计 3.3 节，只把"新开终端"换成"复用窗格、重启进程"：

1. 写 `input.md`。
2. `hc send <窗格> "<启动命令>"`，命令由 `config.yaml` 的 adapter 生成，如 `codex --yolo` 之外按角色权限取只读等参数（审查角色只读，见设计 3.1 节约束，不照搬当前的 `--yolo`）。
3. `hc send <窗格> "读取 input.md，把产物写到 …，完成后写 done.json"`。
4. `hc wait <窗格>`，再检查 `done.json`。完成判断以 `done.json` 为准，`hc wait` 只用来知道"可以去检查了"（L003）。
5. 向窗格发退出命令，等前台进程回到 shell，才算本次调用结束。退不出就 `hc kill` 并在原地重开 shell，记 `failed` 并按重试规则处理。

调用之间窗格里保留上一次的屏幕内容，方便用户回看；下一次调用前清屏即可。

### 2.4 状态区

主控每 2 秒（`config.yaml` 可调）做一次：

1. `hc ls` 取 4 个窗格的 `status.state`（working、done、idle）与前台进程名。
2. 读各需求的 `state.json`，拿当前阶段、轮次、步骤状态、开始时间。
3. 把两者合并成下表，用终端文字重绘：

```
AutoDev  R20261105-001  S3 设计审查  第 1/3 轮
──────────────────────────────────────────────
 窗格  Agent        角色              状态      用时
 t8    claude-opus  designer          等待      -
 t9    codex        design_reviewer   运行中    01:12
 t12   agy          -                 空闲      -
待你决定：0     最近事件：S2 完成 09:41
```

窗格状态映射：`hc` 报 working 且主控记录该步骤为 running，显示"运行中"；`hc` 报 done 或 idle 且步骤为 pending，显示"等待"；步骤 finished 且窗格回到 shell，显示"已结束"；`hc ls` 里窗格消失，显示"丢失"并触发设计 5.4 节的恢复流程。

后续可改用 `events.subscribe` 订阅代替轮询，第一版不做（YAGNI）。

### 2.5 实现语言

提议 Python 3 标准库（`subprocess` 调 `hc`，`curses` 或纯 ANSI 重绘），不引入依赖。理由：本机已有，能直接解析 `hc` 的 JSON 输出，第一版界面很小。待用户确认；这同时回答 `next.md` 里"流程程序语言"一项。若选 Node，则结构不变。

### 2.6 巡检与卡住处理（待实现，来自 L008）

主控每隔 `watch_seconds`（建议 30 秒）巡检各窗格，不依赖界面是否打开：

1. 读 `hc get` 的 `status.state`、步骤 `started_at`、`events.jsonl` 最后进展时间。
2. 判为卡住：状态为 `blocked`，或 running 超过阈值且窗格无新输出，或窗格已不在 `hc ls`。
3. 卡住事项交给专门的处理者（watchdog），不阻塞主流程里其他需求或窗格。
4. 处理原则：不影响整体运行时直接处理并继续（例如放行只写本步骤目录的确认）；会影响其他部分，或涉及删除数据、凭证、权限、对外发送、花钱，则转 needs-human 并通知，不自动放行。
5. 每次处理写一条事件（如 `watchdog.unblocked`、`watchdog.escalated`），便于追溯。

放行哪类确认、阈值取多少，实现前先在测试里列表格定下来。
