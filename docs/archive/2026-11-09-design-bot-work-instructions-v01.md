## 8. 设计机器人工作说明 v0.1

状态：S2/S3 的输入清单、项目上下文快照、设计/计划/原型产物契约已实现；渠道交互、D019 放行策略和条件式人工确认尚未实现。适用于接入的目标项目；设计 AutoDev 自身时目标项目才是 AutoDev，不能把平台仓库的全部规则与资料混入其他项目。

### 8.1 独立业务能力与渠道边界

设计负责人是逻辑角色，负责与人讨论、组织 S2 产出和解释审查策略及结果。正常 S3 审核优先独立模型；降级、自检或免审依 D019 如实区分，不把作者自检伪称独立审核。角色上下文按目标项目与设计任务隔离，不以飞书聊天窗口作为唯一归属。

用户最新明确：独立模型审核是大多数任务的优先路径，跨厂商是增加视角独立性的方法，不是审核本身，也不是所有任务的强制条件。具体分级按 8.6 执行；只有一个 Agent/模型也允许继续，简单复用可免去额外模型审核。复制会话或重复运行同一模型仍不算双模型。这是设计审查策略，不等同于产品代码已执行自动测试。

记录各次实际可核实的模型标识、角色、产物版本和检查/审查结果；请求模型名与独立验证的实际模型须区分。不把缺少第二模型造成的降级放行写成独立审核通过。备用模型配置、策略选择与结果协议在实施前验证；现有 check_vendors 的强制校验仍未修改。

Web、飞书与未来微信只负责认证后的身份接入、任务绑定、操作转译和结果呈现。后端统一提供开始设计、查看状态与产物、提交意见、推进设计/审查、修订及导出等业务操作；操作名不是已实现 API。接口返回结构化结果和产物引用，具体展示文本、卡片或文件由渠道适配。设计判断、版本、完成条件和状态推进不得放在平台回调中。

不同渠道之间须经授权关联到同一设计任务，不能因为名称相同就自动合并身份或开放访问。沿用现有消息网关及配对模式评估接入；未来微信需根据实际平台落实身份与传输，不宣称替换入口即可直接上线。

### 8.2 输入清单

| 输入 | 内容与用途 | 缺失时的处理 |
| --- | --- | --- |
| 项目与任务标识 | 确定目标项目、读写范围和本次设计对象 | 不明确则先澄清，不写入猜测的项目 |
| 上游需求包 | 需求分析、可追溯的原文/确认版本、验收标准及约束 | 可讨论草案；缺少交付所需基线或有阻塞歧义时不能定稿 |
| 项目规则与决策 | 适用的项目规则、相关历史决定、禁止改动与批准边界 | 查指定入口；冲突列出出处交人取舍，不静默选边 |
| 已有资产 | 相关架构、模块与接口、可复用 UI、测试及使用证据 | 按范围查找，区分已验证与未验证；全新项目可明确无既有资产 |
| 设计历史 | 当前草稿、人工已确认意见、上一轮 S3 问题与修订回应 | 首轮可为空；后续轮必须关联本任务有效记录 |
| 可用工具与权限 | 已验证工具、适用范围、允许读取/输出目录、是否可联网 | 缺失能力要明示；不为完成任务自行安装、扩大权限或修改服务 |

输入清单由程序通过现有 input.md 和运行内项目资料快照记录来源、快照及用途；设计者与审核者读取同一上下文基线，审核另加本轮完整交付包。当前已快照 README 与项目配置列出的 context 文件；其他资料仍需受控加入清单，不能只凭角色记忆补造事实。长期对话如何裁剪与恢复另待设计，不靠常驻进程保上下文。

### 8.3 应读什么：入口固定，内容按任务选取

设计机器人自己的工作约定保持简短：职责、输入输出、工具优先、证据边界、审核与人工取舍方式。通用软件设计原则引用适用的既有规范，不在角色提示词复制整套教程。

项目资料按三类组织：

- 必需：本次需求分析与基线、适用项目规则、与任务直接相关的既有决定、当前人工意见。
- 按需：从文档索引定位的架构、数据与接口文档、相应源码和测试、已有界面与使用证据。读取源码用于核对资产与接口，设计阶段不修改产品代码。
- 不自动读取：其他项目、其他角色的全部聊天、无关运行历史、凭证与私人配置；不扫描整个用户目录。

以 AutoDev 自身为目标时，由受信的输入准备步骤先从 docs/INDEX.md、docs/TOOLS.md、docs/lessons.md、docs/DECISIONS.md 定位相关内容，并引用当前需求和设计；涉及底座时加入 D004/D014、地基方案和锁定版本协议，涉及模型时加入 docs/MODELS.md，涉及手机入口时加入 requirements/channels.md。next.md 用于识别当前目标，不把其中全部历史待办当成这次需求。已有原型只作为明确标注的参考，不当成已实现界面。

当前 pipeline/design 的 scope 限定只读输入清单，禁止运行时自行读取平台 next/lessons/全局规则，并限制无网络环境。这与受控资料包可以共存：项目 README/context 已由程序明确列入，AutoDev 平台规则按任务是否列入项目 context 决定是否提供。若后续扩充输入范围，须按需加入清单并验证；提示词约定不等于操作系统级权限隔离。

### 8.4 工作步骤与工具分工

| 步骤 | 工具优先承担 | Agent 或人承担 |
| --- | --- | --- |
| 接收与检查输入 | 校验项目、文件存在、绑定关系、版本和路径范围 | 判断关键业务信息是否齐备，向人澄清 |
| 核对资产与约束 | 文件检索、接口定位、已有证据与差异查询 | 判断能否复用、指出真正冲突及取舍 |
| 编写方案与计划 | 文件读写、现有模板与清单 | 架构、交互与接口设计，任务拆分和解释 |
| 制作原型 | 复用已有组件和设计资产；本地预览、截图与关键操作检查 | 设计使用流程，结合人工反馈修订 |
| 交付包预检 | 文件/引用检查、版本对应、需求与任务标识对应、缺项列表 | 判断覆盖是否充分，不能把结构检查当语义正确 |
| S3 独立审查 | 复用派活、结果校验与轮次控制 | 审查需求、设计、计划、原型及契约是否一致 |
| 修订与交付 | 保存新版本、差异与审查关联，生成交付清单 | 逐项回应，需业务决定或超限时请人处理 |

能由规则表达的动作不再交模型反复推断。工具选择先查现有工具手册和项目能力；工具缺失时说明缺口并讨论最小补齐，不把“工具优先”变成为每个动作新建一个工具。工具执行失败与检查不通过要区分；未运行的检查明确标注未验证。

已有可复用：input.md/模板、文件读写、S2/S3 派活与返修、done.json 校验与运行记录；SRS validator、handoff 交接器、项目上下文探测、统一 Web 与渠道无关 presentation/飞书入口。兼容消息网关与版本化工作台另行保留。第一步复用项目 `README.md` 和 `config.yaml` 中该项目明确列出的 `context` 文件，在每个 S2 轮次建立运行内只读快照并供 S3 共用；同轮重试保持快照不变，不自动扩展到其他资料。独立 `prototype.md` 已进入交付清单并传给 S4/S6/S8。交互式原型预览、交叉检查及设计包版本管理尚未成为完整工具链，需逐项验证。

### 8.5 交付包与完成条件

沿用 design.md、dev-plan.md、review.md 以及返修时 response.md 的现有职责。接口契约作为 design.md 的明确章节；独立 prototype.md 关联页面、需求、接口和开发任务；无 GUI 的项目在该文件说明不适用，同时设计其实际使用入口。

原型建议优先复用目标项目的界面资产；无既有载体时可讨论本地可预览 HTML，用示例数据展示主要交互，并明确模拟行为。原型的视觉精度待确定；静态截图只能证明外观，不能证明交互通过。飞书/微信查看原型的方式也待设计：本机 URL 不能直接作为手机可访问链接，不因此自动开放公网服务。

每版交付包关联项目、需求基线、设计版本、文件清单与审查结果。修订保留旧版，改变设计/计划/原型/契约后旧审查不能自动覆盖新内容。文件齐全与引用有效由工具检查，实际含义是否满足需求由 S3 与人判断。

完成门槛：输入基线明确；交付内容或适用复用引用齐备且版本一致；关键需求能对应到方案、接口/页面、开发任务和验收；没有阻塞性未决问题；按 8.6 的选定策略完成审核或有效降级/免审放行。条件式人工介入规则由用户明确如下：

| 本次交付范围 | 设计完成额外条件 |
| --- | --- |
| 包含需要原型的用户界面 | 人确认本次交付的原型与对应交互；模型审核不能代替人的使用体验确认 |
| 无用户界面，如纯后台、部署、程序间调用 | 明确原型不适用，满足其余条件即完成，不增设通用人工设计确认 |

是否需要原型应由需求与本次交付范围确定并记录，不能由 Agent 为了绕过确认临时声称“无前端”。无界面不等于无需技术设计；仍交付适用的方案、接口、计划与审查。业务歧义、重大冲突、审核超限以及既有发布/高影响操作关口仍按原规则处理，不被“无界面免确认”覆盖。

原型确认绑定展示版本；人工要求改变原型后，旧确认不能放行新版；若改动影响设计包，应重新判断本轮适用的审查策略，并记录对应新版的审核或放行依据，不能挪用旧审核。最终交付须有适用审查/放行记录及原型确认。仅查看不算确认，各渠道采用相同后端校验。具体版本与确认数据协议待实施设计。

现有 S3 PASS→S4 没有上述条件式原型门槛。未来应在 AutoDev 交付/流转层以最小改动落实：需要原型而未确认时不得交给开发；无界面沿用既有通过路径。不更改 autoloop 内核，也不为所有项目增加一道人为审批。界面相关未验证项与非阻塞遗留问题须明示。

首个设计机器人阶段先在此完成设计包和导出，不因用户查看结果或结束讨论自动启动 S4。衔接完整 build 流水线的启动授权、人工定稿方式及版本消费协议在后续实施计划中明确。

### 8.6 分级审查与可用能力降级（D019）

目的为平衡效率与最终精度。先判断能否简单复用，再为其余任务优先安排独立审核；不为凑模型数量重复工作，也不因只有一个 Agent 停住所有任务。

| 情况或能力 | 建议处理 | 如实记录 |
| --- | --- | --- |
| 简单任务且已有适用的已验证资产 | 引用原设计/工具/产物和必要差异说明，免去额外模型审核 | 复用对象、证据、适用范围、免审原因 |
| 正常任务，有不同 Agent 和跨厂商模型 | 优先独立审核 | 作者/审核者、模型、版本、结论 |
| 无上述组合，但有不同模型 | 同 Agent 切换模型或同厂商不同模型审核 | 实际模型与审核结果，注明独立性条件 |
| 只有一个 Agent/模型或备用模型不可用 | 用现有模型及适用工具完成检查后降级放行，不额外强制人工批准 | 单模型检查与工具结果、降级原因、未覆盖检查 |

简单复用的选择规则尚待定稿，建议至少核对当前需求和旧资产的输入输出、接口、约束/运行环境是否匹配，引用已有测试或使用证据；有实质变化时默认回正常设计路径，不以“做过类似的”为充分证明。工具检查可验证文件、版本和已知契约；业务等价不能只由文件哈希证明。规则允许 Agent 提建议，但最终分级和流转由程序按明确条件处理（D004）。

工具检查与语义审查按任务适用，简单复用不要求再生成一整套同义文档或额外自检调用。模型可用性优先复用已知配置和运行结果，不每次穷举所有平台；尝试次数/超时预算待定，不能无限重试以满足优选组合。

执行结果须区分独立审核通过、单模型降级放行和复用免审；免审/降级不冒充 PASS 的审核证据。现有 S3 只有 PASS/REWORK/BLOCK，未来需在 AutoDev 的策略、结果记录与转移层作最小兼容设计，保留既有严格路径测试，不改 autoloop 内核。已发现的实质阻塞不因审查者不可用而自动消失；既有授权及适用的人工原型确认继续有效。

> 2026-11-09 补充：设计的出口、按类型与复杂度的分级以及定稿与启动开发的分步，见已归档的 [设计出口与分级](../archive/2026-11-09-design-exit-and-grading.md)（D025，已被 D026 取代，当前依据见 [采用对照](../design/2026-11-09-v21-mapping.md)）；本节的分级审查表是 D019 的依据，仍然有效。

### 8.7 新旧规则冲突检查（2026-11-08）

用户明确冲突时以 D019 新原则为准，适用于项目审查规则；设计机器人先落地不代表其他文档中的旧硬门槛仍优先。检查涵盖项目入口、活动设计/模块文档、相关模板、代码与测试，并核对全局工作流。仅调整文档优先级，未修改代码、配置、旧数据、固定基线或外部底座。

| 原规则/位置 | 冲突或关系 | 本轮处理与剩余工作 |
| --- | --- | --- |
| AGENTS、README、D008、主线/旧设计、模型手册、重跑指南 | 强制作者/审核者跨厂商 | 改为 D019 优先；操作指南注明旧程序仍拒绝同厂商 |
| D020 前期讨论与本设计稿早期约定 | 所有任务至少两个模型、S3 必经独立审核 | 旧决定保留演进说明，当前规则为优先审核、可降级/免审 |
| D016、需求模块的活动文档及协议 | 强制双模型/跨厂商，完成与导出要求独立 PASS | 文档注明新规则优先、旧行为待迁移；固定 v0.8/v0.9 和证据不改写 |
| cockpit.pipeline.check_vendors、requirements.versioned_session.SessionStore.create、Web 角色配置 | 同厂商直接拒绝 | 属于实现差距；代码尚未改，后续按策略调整并覆盖测试 |
| pipeline/design 与 build 模板、Controller、需求完成/确认/导出检查 | 没有有效降级与免审的数据和转移路径 | 新原则不依赖伪造 PASS；后续需协议、路由和下游消费一起适配 |
| tests/test_controller.py、现有需求与流水线测试 | 固化旧拒绝与严格审核路径 | 本轮未改测试；实施时保留严格路径并补降级/免审测试，不能只删断言 |
| 全局 GLOBAL_DEV_WORKFLOW 的复杂任务对抗审查 | 要求反向检查，但允许当前 Agent 按清单复核，不要求两个模型 | 与单模型降级、简单任务复用免审兼容，不需修改全局规范 |
| D004、D014、原型人工确认、既有授权关口 | 程序控制、底座分工、明确的人工决定 | 无冲突，保留；不因免模型审核一并取消 |

这项变更与“尽量不动已验证资产”也兼容：只在旧硬校验与新目标明确冲突之处安排后续最小修改；已测过的派活、检查工具、事实日志和恢复能力继续复用。当前文档统一不等于现有程序已经支持单模型放行。
