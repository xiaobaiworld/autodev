## D004 流程由确定性程序驱动，状态全部落盘

- 日期：2026-11-02 ｜ 状态：已接受（用户决定方向，细节为提议中）
- 问题：流程需要在重启和崩溃后保持一致。
- 考虑过的方案：
  - A. 由一个 LLM 会话担任主 Agent 做流转（初稿方案）。缺点：状态依赖会话记忆，崩溃后难以恢复，弱模型指挥强模型。
  - B. 确定性程序做流转，只在需要语义判断的阶段调用 Agent（采用）。
- 选择 B 的理由：流转本身无需语义判断；状态以文件为准，任意时刻崩溃最多重做一步。
- 提议中的细节：`state.json` 为权威状态，`events.jsonl` 只追加；原子写；单实例锁；每步可重入；launchd 守护。
- 重开条件：出现程序无法表达、必须靠语义判断的流转规则。

## D005 九阶段流水线与角色分工

- 日期：2026-11-02 ｜ 状态：已接受（用户决定）

- 重开条件：某阶段长期是空转或瓶颈。

## D006 设计与开发计划采用「一写一审、多轮往返」

- 日期：2026-11-02 ｜ 状态：已接受（用户同意）
- 问题：架构设计和开发计划影响最大，用户希望两个模型共同完成。
- 考虑过的方案：
  - A. 两个模型同时编辑同一份文档。放弃：违反单写者原则，容易互相迁就、结论趋同，出错时无法归因。
  - B. Opus 写、Codex 审，多轮往返直到 PASS 或超限（采用）。
  - C. 两个模型各自独立出一版设计，Opus 对照合并，Codex 审合并稿。暂缓：能看到不同思路，但设计阶段用量约翻倍，并多一个合并步骤。
- 选择 B 的理由：保留了不同厂商模型的交叉检查，同时文件写者唯一、责任清楚，成本可控。
- 重开条件：真实需求运行后，设计缺陷频繁在 S6 或 S8 才被发现，或 S3 往返经常超限。届时评估方案 C。

## D007 编码模型按「够用、性价比」选择

## D009 人工参与通过「决策请求 / 回复」文件对完成

- 日期：2026-11-02 ｜ 状态：提议中（用户提出需求，结构由 Claude 提议）
- 问题：如何把需要用户判断的事推送出去，以及用户的决定如何回到流水线。
- 选择：程序写 `decision-K.md`（附推荐做法），herdr 通知只做指针；用户写 `reply-K.md`，程序校验后按 action 决定去向。用户指示作为高优先级上下文传给后续 Agent；长期有效的决定在发布时写入目标项目 `docs/DECISIONS.md`。
- 理由：通知可能失败，文件不会丢；回复有固定结构才能被程序可靠解析；写入目标项目决策记录可避免同一问题被反复问。
- 放弃的做法：在需求文件末尾追加意见（初稿）。放弃原因：需求文件同时有用户和程序两个写者，违反单写者原则，且难以对应到具体哪一次决策。
- 重开条件：需要从手机或 IM 回复，届时增加渠道，但仍落到同一 `reply-K.md`。

## D010 增加本地 Web 管理界面，作为文件的另一个客户端

- 日期：2026-11-02 ｜ 状态：已接受（用户提出），实现细节为提议中
- 需求（用户原话要点）：Web 界面显示重要文档和信息；重点看需求变更和最终结果，不看代码；可调换各阶段的 Agent 和模型；可直接进行人工参与。
- 选择：界面只读文件，只写新需求、回复、配置三类用户本就有权写的文件，与命令行走同一套校验；只监听 127.0.0.1，第一阶段不做登录。
- 理由：保持文件是唯一事实源，界面故障不影响流水线；不新增第二套状态。
- 风险：无认证依赖只监听本机；如果改成局域网访问，必须先加认证。
- 重开条件：需要多设备或多人访问。

## D011 经验总结围绕三个杠杆，改动须审查和用户批准

- 日期：2026-11-02 ｜ 状态：已接受（用户提出三个杠杆），机制为提议中
- 需求（用户原话要点）：能提升的是带给 Agent 的动作、如何拆分动作、如何带给 Agent 更多信息。
- 选择：三个杠杆分别落到角色模板、`pipeline.yaml`、上下文清单，均带版本号并记录在每次调用的 `input.md` 中。复盘由 retrospector 基于落盘指标、审查意见和用户回复提出带证据的补丁，经不同厂商 Agent 审查、用户批准后生效，下一批需求验证效果。
- 放弃的做法：让 Agent 自动修改自己的模板（原 README 的 evolver）。放弃原因：错误改动会扩散到之后所有需求且难以察觉；没有版本记录就无法判断改动是否有效。
- 重开条件：复盘建议的批准率长期很高且效果稳定，可考虑对低风险类别（如上下文清单增删文件）放宽为自动生效。

## D013 需求分析与需求分解都需要审核和往返修订

- 日期：2026-11-04 ｜ 状态：已接受（用户确认方向），运行机制为提议中
- 问题：需求理解和任务拆分会影响后续设计、编码和验收；若只在需求分析阶段产出一次，错误可能一路传递到后续阶段。
- 选择：需求分析与需求分解都纳入明确的审核和修订闭环。审核不通过时回到对应产出阶段修改，再次送审；允许多轮往返，并受配置的轮次上限约束。存在关键歧义、范围冲突、高影响假设或需用户决定的事项时，通过现有决策请求/回复机制暂停并邀请用户参与。
- 边界：人工参与按问题触发，不要求用户逐轮批准常规分析和拆分。S2/S3 已覆盖设计与开发计划的一写一审；需求分析的审核角色、审核结论格式、轮次上限及与现有九阶段的映射仍待细化，不据此擅自增加正式阶段或 Agent 绑定。
- 依据：用户于 2026-11-04 提出，整个阶段的需求分析和需求分解都可能需要审核、多轮交互，特定情况下需要人工参与。
- 影响：更新流程设计，后续完善状态、产物、结论类型、轮次计数和人工介入触发条件；实现前需将上述待定项写入开发计划。
- 重开条件：首批真实需求显示分析审核造成重复空转、无法有效发现问题，或用户介入频率与预期不符。

## D019 设计审查分级：优先独立审核，允许降级与简单复用免审

- 日期：2026-11-08 ｜ 状态：原则与冲突优先级已接受（用户明确要求），选择规则和实施未定稿、未实现。
- supersedes：D008 的强制跨厂商约束、D020 讨论中“任何设计至少双模型”的硬门槛，以及其他项目规则中冲突的审查硬要求（含 D016 的强制模型组合）。用户明确要求检查冲突并以新规则为主。S2/S3 等职责仍保留，允许按明确策略减轻或免去相应模型审核调用；不修改 autoloop 内核。历史基线和旧实现保留不能解释为旧规则优先。
- 问题与依据：用户要求在效率和最终精度之间平衡；大部分任务需要审查，但简单、原来做过且可用旧资产代替的需求不必强制审查；缺少第二 Agent/模型时也允许继续，不能仅因资源不足停住。
- 已知事实：现有 check_vendors 强制跨厂商，S3 模板只接受 PASS/REWORK/BLOCK；新策略尚不受现有执行代码完整支持。已有机制的证据不能用来声称降级与免审已实现。
- 考虑的方案：所有任务强制跨厂商双模型（独立视角较多，但增加耗时与资源依赖）；全部免审（快，但失去用户仍希望保留的大多数审查）；按任务与可用能力分级（采用，兼顾效率与质量，但需透明记录并防止误选免审）。
- 选择：正常任务优先不同 Agent、不同模型，能跨厂商则优先；不足时同 Agent 切换不同模型，同厂商也可；只有一个模型也可通过单模型检查与适用工具检查继续。不因缺第二模型额外强制人工批准。简单且有适用的已验证资产时可免去额外模型审核，直接复用。
- 建议规则（尚未定稿）：简单复用需关联已有资产及验证证据，并说明当前需求、接口、约束是否相符；其余默认尝试独立审查，依据已知能力和有限尝试降级，不无限寻找模型。分级由可追溯规则决定，Agent 可提建议，不能让作者随口宣布“简单”来绕过规则（D004）。不先增加复杂评分系统。
- 记录与边界：明确记录任务选择、复用依据、实际模型/检查、审查结论或免审/降级原因；同模型检查不算双模型，未审查不标成审核通过。缺审核资源可以降级，已发现的实质阻塞不能当作“资源不足”自动消失。界面原型适用的人工确认和其他既有授权/发布关口不受本决策取消。
- 收益、成本与可逆性：减少简单任务和资源不足时的等待；代价是降级任务的审查独立性降低、免审依赖复用适用性判断。记录保留后可按需补审；若误放行、复用失配或单模型漏报增多，收紧对应类别规则，不需更换底座。
- 范围与后续：作为项目当前审查原则，先落实到设计机器人契约；其他角色和模块的冲突规则亦以此为准，但本轮不修改需求固定基线、S6/S8 等代码和测试，不伪造已适配状态。选择条件、执行结果协议与针对性测试进入后续实施计划，本轮仅文档。
- 冲突检查（本轮）：已核对项目入口、主线/旧设计、模型手册、重跑指南、需求模块活动文档、模板/源码/相关测试及全局工作流。冲突归为强制跨厂商、强制双模型、无降级/免审出口三类；活动文档同步优先级或明确标注旧实现范围，历史报告和固定版本不改写。全局复杂任务的反向检查允许同一 Agent 按清单执行，不要求跨厂商或双模型，与新策略兼容。细节见设计草案 8.7。

## D022 跨阶段统一携带明确的项目与需求双身份，交接前严格程序验真

- 日期：2026-11-08 ｜ 状态：已接受（用户提出并确定）
- 问题：系统支持多项目并存与并行交互时，若依赖聊天窗口、单个 `cwd` 目录名或默认硬编码（如 `"toy"`、`"autodev"`）推断目标项目与需求身份，极易导致会话上下文串扰、代码写入错误仓库、产物身份混乱和交接错位。
- 不变量（Architectural Invariant）：
  1. **全链路统一双身份**：每个需求会话（ReqSession）、定稿版本（`REQ-*.md`）、流水线运行（RunState）及阶段产物（S1~S9 产物 Frontmatter）都必须显式携带同一个明确的 `project`（项目标识）和 `req_id` / `id`（需求标识），两者不可分割。
  2. **严禁隐式推断**：禁止仅凭聊天窗口、工作目录名（`os.path.basename`）或默认 fallback 猜测项目与需求身份。
  3. **交互双端感知外显**：飞书界面与 Web 界面必须在状态栏、卡片和响应头中显式可见当前项目与当前需求；切换项目时强制隔离历史记忆。
  4. **交接时程序强核对与分级处置（拒绝交接 / 人工介入）**：从需求定稿移交（Handoff）到主流水线（S2）时，必须由确定性程序核验来源文档中的 `project` 和 `id` 与目标工程配置是否一致。若无法核实（未指明、格式不符、目标工程不存在或来源与目标冲突）：
     - **直接阻断（拒绝交接）**：即时打回飞书/Web 交互端，给出明确错误原因（如“定稿缺少 project 声明”或“目标工程未在 config.yaml 中登记”），要求用户补充或修改；
     - **支持转人工介入（`needs-human`）**：在接入主流水线侧，若出现争议（如外部指定了新项目、或未明确分配工作目录），挂起并生成决策请求（`decision.md`），通知用户介入拍板指定目标项目或确认驳回，杜绝程序擅自猜测。
- 影响：
  - 会话管理（`src/requirements/session.py`）：扩展显式 `project` 与当前活跃 `req_id` 状态。
  - 飞书守护（`src/requirements/feishu_daemon.py`）与 Web（`src/web/api.py`）：外显当前项目与需求身份，支持显式项目选定。
  - 规范与校验（`src/requirements/validator.py`）：将 `project` 纳入标准 SRS Frontmatter 强制必填契约校验。
  - 交接桥梁（`src/requirements/handoff.py`）：剔除默认 `"toy"` / `"autodev"` 硬编码，增加来源与目标一致性核验断言。
  - 流水线产物（`src/cockpit/pipeline.py`、`store.py`）：所有 stage 产物 frontmatter 必须包含 `project` 和 `id`。
- 重开条件：系统重构为不需要多项目并存的完全单体且无外部关联模式（几乎不可逆）。
