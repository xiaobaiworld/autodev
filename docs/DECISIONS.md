## D001 以需求驱动流水线取代 goal.md 自迭代循环

- 日期：2026-11-02 ｜ 状态：已接受（用户决定）
- 问题：原 README 是 planner、executor、evaluator、evolver 组成的单目标自迭代循环，与实际需要不符。
- 选择：用户逐条提交功能修改需求，走固定的多阶段流水线。用户原话：「Readme 的描述都是不对的，我们就是要修改，要取代它。」
- 影响：README、config.yaml 已重写，空的 `core/`、`plugins/` 已删除。
- 重开条件：需要从零生成新项目，而不是修改已有项目。

## D003 角色与 Agent 解耦，经 herdr 调度

- 日期：2026-11-02 ｜ 状态：已接受（用户决定）
- 问题：后续会接入更多 Agent，各自发挥长处，不能把某个 Agent 写死在流程里。
- 选择：流程只定义角色，角色到 Agent 和模型的绑定写在配置中，Agent 进程由 herdr 启动和管理。
- 约束：审查角色的 Agent 必须与所审产物的作者不同。
- 未知：herdr 命令只核对过帮助文本，未实际运行验证。
- 重开条件：herdr 无法稳定启动或检测某个 Agent。

## D004 流程由确定性程序驱动，状态全部落盘

- 日期：2026-11-02 ｜ 状态：已接受（用户决定方向，细节为提议中）
- 问题：流程需要在重启和崩溃后保持一致。
- 考虑过的方案：
  - A. 由一个 LLM 会话担任主 Agent 做流转（初稿方案）。缺点：状态依赖会话记忆，崩溃后难以恢复，弱模型指挥强模型。
  - B. 确定性程序做流转，只在需要语义判断的阶段调用 Agent（采用）。
- 选择 B 的理由：流转本身无需语义判断；状态以文件为准，任意时刻崩溃最多重做一步。
- 提议中的细节：`state.json` 为权威状态，`events.jsonl` 只追加；原子写；单实例锁；每步可重入；launchd 守护。
- 重开条件：出现程序无法表达、必须靠语义判断的流转规则。

## D005 九阶段流水线与角色分工

- 日期：2026-11-02 ｜ 状态：已接受（用户决定）
- 选择：需求分析（Opus）→ 设计（Opus）→ 设计审查（Codex，多轮往返）→ 编码（Codex，用户于 2026-11-02 选定；原话「Codex 的 Haiku」不成立，Haiku 是 Claude 模型）→ 确定性检查 → 代码审查（Opus）→ 发布候选 → 验收（Codex）→ 正式发布。
- 理由：用户的需求以功能修改为主，对系统理解深度要求高，因此分析与设计交给能力最强的模型；每一步产物都可审查，形成小版本记录。
- 超限规则：任一关口超过轮次上限即通知用户，由用户指挥 Agent 处理。
- 未知：coder 绑定的 Agent；S7 和 S8 的具体做法取决于 personagent 的运行形态。
- 重开条件：某阶段长期是空转或瓶颈。

## D006 设计与开发计划采用「一写一审、多轮往返」

- 日期：2026-11-02 ｜ 状态：已接受（用户同意）
- 问题：架构设计和开发计划影响最大，用户希望两个模型共同完成。
- 考虑过的方案：
  - A. 两个模型同时编辑同一份文档。放弃：违反单写者原则，容易互相迁就、结论趋同，出错时无法归因。
  - B. Opus 写、Codex 审，多轮往返直到 PASS 或超限（采用）。
  - C. 两个模型各自独立出一版设计，Opus 对照合并，Codex 审合并稿。暂缓：能看到不同思路，但设计阶段用量约翻倍，并多一个合并步骤。
- 选择 B 的理由：保留了不同厂商模型的交叉检查，同时文件写者唯一、责任清楚，成本可控。
- 重开条件：真实需求运行后，设计缺陷频繁在 S6 或 S8 才被发现，或 S3 往返经常超限。届时评估方案 C。

## D007 编码模型按「够用、性价比」选择

- 日期：2026-11-02 ｜ 状态：已接受（用户同意）
- 事实：开发计划越细，编码越接近照计划执行；但用户的需求以修改已有功能为主，编码 Agent 仍需理解现有代码、处理边界并补测试。
- 选择：编码不要求最强模型，以能力够用、性价比高为准；S5 确定性检查与 S6 Opus 代码审查兜底。当前绑定 Codex（见 D005）。
- 观察指标：S5、S6 的回修轮次和超限次数。
- 重开条件：编码阶段回修轮次持续偏高，或频繁超限交给用户。
