## 3. 核心背景与业务目标 (Why & What)
- **业务背景**：
  1. 我们在前面已经分析并设计了 AutoDev 整个系统的 Web 管理界面（见 `2026-11-02-autodev-design.md` 第 9 节与 `autodev-workflow-prototype.html`），用于查看 S1~S9 九个阶段的进展、阅读设计/审查产物并处理「待你决定」的人工关口；
  2. 同时，我们刚刚落地了飞书端「需求分析师」与 9 章节 SRS 标准规范。但飞书受限于手机/聊天单列窗口，每次只能看 250 字的短卡片，无法在大屏上同时纵览“9 大章节的实时拼图进度、校验规则红绿灯、需求关联拓扑图、每轮原始问答耗时”以及“定稿后一键切入 S2~S9 流水线看板”。
- **业务目标**：
  构建统一的 **AutoDev 本机网页客户端（Web Workbench）**，将「源头需求澄清」与「S1~S9 系统工作流网站」彻底连成一体：
  1. 既能在网页上像飞书一样用 `1`、`2` 极简点选澄清需求，又能展示**比飞书丰富得多的桌面级伴随信息**（9 章节实时生长预览、RULE-01~09 逐项校验状态、需求规模与网状关系可视化、版本演进与每轮调用耗时记录）；
  2. 定稿通过校验后，在网页上点击【🚀 移交 S2 架构设计】，无缝流转到前面分析的 **S1~S9 九阶段系统工作台**，实现从“一句话想法”到“S9 正式发布批准”的全生命周期单客户端闭环。

## 4. 业务用例与核心流程 (Scope)

### 4.1 核心用例 1：在网页端进行引导式需求澄清（与飞书同构但信息更丰富）
1. 用户在浏览器打开本机 Web 客户端（`http://127.0.0.1:<port>`），在顶部或侧边栏选择目标项目、切换底层大模型（显示来自 `config.yaml` 的完整模型 ID，如 `ai-code-with/claude-sonnet-5-5`、`gpt-6-sol`）及调用方式（`cli_session` / `cli_stateless`）；
2. 用户输入初始想法，或直接点开一个正在飞书上聊了一半的需求会话；
3. 中间对话区呈现引导式拼图问答（选项 `1`、`2` 变成可直接点击的交互按钮，附带具体业务场景举例）；
4. **【比飞书多出的内容 A：右侧 9 章节 SRS 实时预览与规则校验面板】**
   - 右侧分栏实时展示《软件需求规格说明书》9 大标准章节的填充进度；
   - 实时运行 `validator.py`（`RULE-01 ~ RULE-09`），对每一条规则亮起 `✅ 已满足` 或 `⏳ 待补充 / ⚠️ 违规提示` 徽标；
   - 支持在网页端直接折叠/展开第 6 节「外部界面原型线框图」，并支持人工在线微调 Markdown 草稿并保存新版本。
5. **【比飞书多出的内容 B：需求规模、网状关系图谱与原始交互审计】**
   - 直观渲染当前需求的规模标签（`Epic` / `Feature` / `Sub-feature` / `Enhancement`）、所属模块与 `Parent` / `Depends-on` / `Relates-to` 关联卡片，点击关联需求可直接跳转查看；
   - 提供「原始交流与耗时记录」抽屉：按轮次展示用户输入原文、大模型原始输出、实际使用的完整模型 ID 及每轮调用耗时（等待用户时间不计入）。

### 4.2 核心用例 2：一键直通 S2 并进入全系统九阶段流水线工作台（与前面的网站需求连起来）
1. 当需求草案通过 `RULE-01 ~ RULE-09` 全部校验亮绿灯后，用户点击页面右上角 **【🚀 定稿并移交 S2 架构设计】**；
2. 服务端调用 `handoff_srs_to_pipeline()`，生成正式运行号 `R{YYYYMMDD}-{NNN}`，写入 `workspace/requests/active/{rid}.md` 与 `S1` 基线，将状态直接置为 `S2 架构设计`；
3. 页面自动平滑切换（或跳转）至该需求的 **「S1~S9 需求处理流程」主工作台**（即承接 `autodev-workflow-prototype.html` 与设计文档第 9 节的系统客户端）：
   - **总览顶栏**：展示所有需求分组（置顶「待你决定」列表、运行中需求、已归档需求）；
   - **左侧九阶段时间线（S1 ~ S9）**：实时高亮当前阶段（`S1 已通过基线直通 -> S2 方案设计 -> S3 设计审查 -> S4 编码 -> S5 自动检查 -> S6 代码审查 -> S7 发布候选 -> S7U 使用验证 -> S8 验收 -> S9 正式发布`），显示每阶段的轮次、执行 Agent、完整模型 ID、结论与耗时；
   - **右侧阶段详情与产物阅读器**：点击任一阶段，直接在线阅读对应的 `analysis.md`、`design.md`、`dev-plan.md`、`review.md`（高亮“原文对照”小节）、`check.log`、`usage.log` 及需求变更对比；
   - **右侧「需要你参与（待你决定）」交互面板**：当流水线停在人工关口（如 S9 发布前确认或审查超限 `needs-human`）时，直接在网页卡片中选择 `批准继续 (continue)`、`退回重做 (rework + 选择阶段)` 或 `拒绝 (reject)` 并填写附言，底层调用与 `driver.reply` 相同的原子写逻辑落盘 `human/reply-K.md`。
4. **Agent 与角色配置页**：展示 `config.yaml` 中各阶段角色（analyst、designer、design_reviewer、coder、code_reviewer、acceptor）绑定的 Agent 与完整模型 ID，保存前自动执行 D008（作者与审查者厂商不同）与完整模型 ID 校验。

## 5. 明确非目标与边界 (Non-goals)
- ❌ **不做另一套独立状态存储（严守 D004 与设计 9.1）**：Web 客户端绝不在内存或独立数据库中维护第二套流水线状态，所有数据 100% 读写现有的本地文件事实源（`docs/requirements/`、`workspace/requests/`、`workspace/runs/<id>/state.json`、`events.jsonl`、`config.yaml`）与 autoloop 中台 `/v1/state`；网页关掉或重启不影响任何后台任务；
- ❌ **不在网页端做重型在线 IDE 或直接展示全量代码 Diff 主体**：遵循设计 9.2「看需求和结果，不把代码 diff 作为主体」，仅在详细文档区展示产物 Markdown、检查日志、使用记录与改动文件摘要；
- ❌ **本期不开放公网访问与复杂多租户权限系统**：遵循设计 9.4 与 D010，Web 服务仅监听本机 `127.0.0.1`，不向外部网络暴露，不展示或编辑 `.env` 与密钥文件。

## 7. 业务约束与前置依赖
- **单一事实源约束（Single Source of Truth）**：Web 服务端禁止在内存中缓存权威状态，每次请求或轮询直接读取 `docs/requirements/`、`workspace/requests/`、`workspace/runs/` 与 `config.yaml`；所有写操作必须复用 `cockpit.store.atomic_write`、`requirements.handoff.handoff_srs_to_pipeline` 与 `cockpit.controller.Controller.resume`；
- **本机安全边界与密钥脱敏**：仅绑定 `127.0.0.1`；读取并展示任何日志或产物前执行敏感信息脱敏扫描，严禁在网页端展示或修改 `config.req.toml` 中的飞书 `app_secret` 或环境变量密钥；
- **模型名与异构厂商铁律（D008 & `docs/MODELS.md`）**：网页端的模型选择器与 Agent 配置页只能读写 `config.yaml` 中的完整模型 ID，且修改角色绑定时必须通过 `check_vendors()` 异构厂商检查后方能落盘；
- **零外部重度前端构建依赖**：为符合项目轻量化与离线可运行原则，Web 服务端优先使用 Python 标准库（`http.server` / `ThreadingHTTPServer`）或项目已有轻量依赖，前端采用像 `autodev-workflow-prototype.html` 一样干净自包含的现代原生 HTML/CSS/JS 构建，无需依赖复杂的 Node.js/Webpack 打包链路即可直接启动。

## 8. 可量化验收标准清单 (Acceptance Criteria)
1. **场景 1（网页端需求澄清与飞书多端状态互通）**：
   - *Given* 用户在飞书或网页端开启了一个需求会话；
   - *When* 用户在网页端点击选项按钮 `1` / `2`、发送补充描述，或通过下拉框切换完整模型 ID（如切换至 `ai-code-with/claude-opus-5-5`）及调用模式（`cli_session` / `cli_stateless`）；
   - *Then* 网页端正常调用 `run_agent_turn` 返回结构化引导卡片，且会话状态、历史问答记录与飞书端读写同一个存储结构。
2. **场景 2（比飞书多出的实时 9 章节预览、RULE-01~09 校验灯与关系图谱）**：
   - *Given* 网页端存在一份正在编写或已定稿的需求文档；
   - *When* 页面加载或文档内容更新时；
   - *Then* 右侧面板实时解析并展示 9 大标准章节、需求规模标签（`Epic`/`Feature`/`Sub-feature`/`Enhancement`）、关联关系网（`Parent`/`Depends-on`/`Relates-to`），并实时显示 `validate_requirement_spec()` 对 `RULE-01 ~ RULE-09` 的逐条通过/未通过状态。
3. **场景 3（一键定稿并直通 S2 架构设计）**：
   - *Given* 当前需求文档在网页端校验状态为 `SPEC-VALIDATED: PASS`；
   - *When* 用户点击【🚀 定稿并直通 S2 架构设计】按钮；
   - *Then* 系统调用 `handoff_srs_to_pipeline` 生成 `R{YYYYMMDD}-{NNN}`，自动写入 `active/{rid}.md` 与 `S1` 基线产物，将 `state.json` 置为 `stage: "S2"`，且网页自动跳转至该需求的 S1~S9 流水线详情页。
4. **场景 4（S1~S9 九阶段流水线实时查看与产物阅读）**：
   - *Given* `workspace/runs/` 下存在运行中、等待人工或已完成的需求（如 `R20261106-010`）；
