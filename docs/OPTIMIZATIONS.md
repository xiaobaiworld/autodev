## O001：输入加“范围”说明

- **日期**：2026-11-06
- **改了什么**：`templates/pipeline/design.json` 新增顶层字段 `scope`；`write_input`（`src/cockpit/pipeline.py`）把它作为“范围”一节写进每步的 `input.md`。内容是：这是流水线中的一轮，只读“输入文件”里列出的文件和本步骤目录，不要按 `AGENTS.md` 去读 `next.md`、`lessons.md`、`TOOLS.md`、`INDEX.md` 和全局开发规范。
- **为什么**：读 R20261106-003 的 Codex 日志（中台运行 18-1）发现，审查每轮先把 `next.md`、`lessons.md`、`TOOLS.md`、`INDEX.md` 和 iCloud 里的全局规范都读一遍，原因是工作目录在本仓库里，`AGENTS.md` 的“开始任务前”被它照做了。当时的记录里，S3 两步合计输入 551,467 token，是 S2 两步（330,672）的 1.7 倍，而输出只有 2,401。判断：这些文件对审查设计没有用。这是判断，不是已证实的因果。
- **怎么回退**：删掉 `design.json` 的 `scope` 字段即可（`pipeline.py` 里 `SCOPE` 为空就不写这一节），不用改代码。
- **怎么量**：同一个需求（`requests/demo-todo-cli.md`）用同样的配置重跑，对比 S3 的输入 token、返工轮数、结论序列。基线是 R20261106-003。
- **实际结果**（2026-11-06，R20261106-003 对 R20261106-004，各一次）：
  - 总输入 1,022,832 → 550,339（-46%）。**这主要是返工轮数 2 → 1**（R003 的审查打回过一次，R004 一次通过），不能算成 O001 的效果。
  - 看单步更说明问题：S3 第 1 轮输入 279,156 → 266,359（-4.6%），执行命令数 12 → 9；S2 第 1 轮 143,585 → 143,413（基本不变）。
  - 判断：这次看不出“范围说明”显著降低审查的输入。每步 26 万多 token 里，大头可能是 Codex 每轮固有的上下文，这一点我没有拆开验证。命令数少了 3 条，但具体少读了哪些文件我没核对（当时核对命令因工具故障没执行）。
  - 返工轮数变化是单次样本，可能只是运气，不能归因于 O001。
  - 结论：效果不明显，待多跑几遍再定是保留还是回退。
- **已知的比较风险**：Agent 输出有波动（同一个需求之前跑出过 3 轮和 2 轮），轮数不同会直接改变总 token；比较时看 S3 单步的输入更可靠，但样本只有一两个。
- **变更历史**
  - 2026-11-06 应用。

## O009：S7U 使用验证，程序替验收者把东西真的用一遍

- **日期**：2026-11-07
- **改了什么**：`pipeline/build` 在 S7 和 S8 之间新增程序步骤 `S7U`（工具 `usage`，`src/cockpit/tools.py` 的 `run_usage`）。它按模板里**人写好**的使用脚本，在隔离环境里把做出来的东西真的运行一遍：每步一条命令（列表，不经过 shell）、期望的退出码、输出里必须有或不该有的字、应该生成的文件、临时去掉的环境变量。原始输出一字不改写进 `usage.log`，作为 S8 的输入（`usage_now`）。第一步不符合预期就停，不再往后跑。命令不存在或没有可执行位算“用不了”（FAIL），退回 S4，计数器 `usage_rounds`（`config.yaml`，上限 3）。S8 的任务说明改成：你不能运行命令，逐条对照原文时优先引用使用记录，使用脚本没覆盖到的才靠读代码，并要写明“只是读出来的”。
- **为什么**：这是上一个“待定”里的选项 A。R20261106-010 的 S8 报告自己承认没亲手用过（A2），所以 S8 和 S6 区别很小。放开验收者的 Bash 等于让它执行任意命令，比 S5 里做的隔离宽松得多，所以由程序替它用。
- **隔离**：和 `check` 一样：最小环境变量（不带用户的密钥）、`HOME` 和临时目录指向步骤目录下的草稿目录、数据文件环境变量也指到草稿目录、不经过 shell、超时杀整个进程组。**挡不住网络，也挡不住对其他绝对路径的写入。** 另外使用脚本由人写在模板里，Agent 改不了，这是它比放开 Bash 安全的地方。
- **使用脚本跟项目绑定**：现在模板里那份是演示项目 `todo` 的（add、done、list、list --all、编号不存在、默认路径）。换项目要换一份；`build.json` 里它现在写死在 S7U 里，接 personagent 时要拆成项目配置。这一点没做。
- **怎么回退**：S7 的 `on.PASS` 改回 `{"goto": "S8"}`，删掉 S7U，S8 的 `inputs` 去掉 `usage_now`。
- **怎么量**：假 Agent 联机（`python3 tests/f2_pipeline.py --build`）：第 3 轮的 `bin/todo` 故意没有可执行位，测试（S5）和代码审查（S6）都放行了，S7 还打了 `v0.1.0-rc.1`，**只有 S7U 抓到了**（`Permission denied`），退回 S4 第 4 轮补上，之后 7 步全过，打 `v0.1.0-rc.2`，最后 `v0.1.0`。
- **实际结果**：212 个单元测试通过（`run_usage` 11 个：通过、命令不存在、没有可执行位、错误的退出码/缺字/多字/缺文件、nonzero、第一步失败就停、HOME 与数据文件隔离、unset、挂起被杀、坏脚本被拒、坏模板被拒）；假 Agent 联机跑完整 S1 到 S9 通过，回归 `--fake-rework`、`crash`、`hub-kill` 通过。**真实 Agent 跑 S7U 还没做。**
- **代价（要知道）**：每次候选标签都会先打再验，使用验证失败时留下了一个没用的 `rc.1` 标签（上面联机里就是这样）。标签只在本地，不影响，但会让候选编号跳号。
- **变更历史**
  - 2026-11-07 应用。

## 待定（已选 A，见 O009）：S8 验收者没法亲手运行代码

- **日期**：2026-11-07
- **发现**：R20261106-010 的 S8 验收报告自己写了（A2）：“本轮运行环境不允许执行 shell 命令，验收人没有亲手跑命令”。核对 `agent-a1.log`：验收者的 Claude 4 次调用 Bash，其中 `permission_denials` 里有 2 次被拒（内容是在临时 HOME 下对 `bin/todo` 跑 add、list、done，正是想做的验收）。原因是 `src/driver/setup.py` 给所有 Agent 的 `access` 都是 `edit`，只能读写文件，不能执行任意命令。
- **后果**：S8 现在是“读完代码和检查日志之后的判断”，不是“拿到手用过之后的判断”，和 S6 的区别变小了。
- **这个限制是有意义的**：放开 Bash 就等于验收者能执行任意命令，比 S5 里花力气做的隔离（最小环境变量、`HOME` 指向草稿目录、杀进程组）宽松得多。所以不想直接放开。
- **选项**：
  - A（我倾向）：由程序替验收者“用一遍”。新增一个程序步骤（放在 S7 和 S8 之间），在隔离环境里执行模板里写明的“使用脚本”（演示项目里就是临时 HOME 下 add、list、done），把输出写进 `usage.log`，作为 S8 的输入。命令由人写进模板，Agent 不能改。缺点：每种项目要写一份使用脚本。
  - B：只给验收者开 Bash，并加隔离（`sandbox-exec`、临时 HOME、无网络）。缺点：隔离要做对很难，我没验证过，做不好比不开更危险。
  - C：保持现状，接受 S8 是“读完判断”。缺点：S8 的价值有限。
- **没做的原因**：选项 A 需要为目标项目写使用脚本，我现在只有演示项目，写出来的脚本只能证明机制通，证明不了对真实项目好用。

## O006：Agent 进程崩溃时不再等中台的退避，立刻交给步骤重试

- **日期**：2026-11-06
- **改了什么**：`src/driver/runner.py` 的 `make_invoke` 参数从 `step_retries` 改成 `hub_retries`，默认 0：中台这一轮第一次失败（Agent 进程崩溃或非零退出），我们就取消它并报 `command_failed`，由 Controller 自己的步骤重试（`step_retries`，每次是新事件）接手。`driver.run` 和联机脚本不再给它传 `step_retries`。
- **为什么**：S5 联机验证那次，假 Agent 因我的测试缺陷每次崩溃，流水线用了 **2710 秒（45 分钟）** 才转人工：3 次尝试各等 15 分钟超时。原因是中台把崩溃的一轮放回排队、自己退避重试（第 1 次 5 分钟，翻倍），而我们要等中台的重试次数超过 `step_retries` 才放弃，两层重试叠加。确定性的崩溃（同一个 bug 每次必现）不该这样等。
- **怎么回退**：`make_invoke(hub, hub_retries=2)` 就恢复成原来的“允许中台自己重试 2 次”。
- **怎么量**：新增联机场景 `python3 tests/f5_crash.py crash`（假 Agent 每次崩溃）：3 次尝试、4 秒转人工；每次尝试的事件 id 各不相同（`-a1`、`-a2`、`-a3`），没有残留进程。
- **实际结果**：175 个单元测试通过；联机六项（`crash`、`hang`、`ctrl-kill`、`hub-kill`、`--build`、`--fake-rework`）通过。**45 分钟 → 4 秒。**
- **代价（要知道）**：偶发的、重试一次就好的崩溃（比如网络抖动），以前中台会在 5 分钟后自己再试，现在改成我们立刻重发一个新事件，效果类似但多占一次 `step_retries` 的额度。真实 Agent 上的网络类故障没测过。
- **变更历史**
  - 2026-11-06 应用。

## O005：S6 代码审查，厂商不同，审查者只读且被程序盯着

- **日期**：2026-11-06
- **改了什么**：`pipeline/build` 新增 S6（角色 `code_reviewer`，现绑 Claude，与编码者 Codex 厂商不同，D008 的检查扩到每一对作者与审查者）。S5 通过才进 S6；S6 `REWORK` 退回 S4（计数器 `code_review_rounds`，上限 3，超限转人工）。审查者的输入有：需求、分析、设计、计划、**从最初起点到现在的完整改动 `full.patch`**（不是只看本轮增量）、本轮检查结果。任务说明明确写了“测试通过只说明代码通过了自己的测试，不说明测试覆盖了需求”。
- **为什么**：R20261106-007 里 S5 判 PASS，但测试是 Codex 自己写的，S5 证明不了测试覆盖了需求（那次设计走的是 `python3 src/todo.py`，需求要求的是 `todo` 命令）。这一层要由另一个厂商的模型来看。
- **审查者有写权限，所以程序盯着它：** 审查前先把代码提交成检查点并记下内容指纹，审查后再取一次，不一样就判无效、把代码恢复到审查前、按步骤失败重试。这样审查者不能“改了代码再放行”。
- **怎么回退**：`build.json` 里 S5 的 `on.PASS` 改回 `"done"`，删掉 S6。
- **实际结果**：174 个单元测试通过，其中包括“审查者越权改代码被抓住、代码恢复”“S6 退回 S4 时不把通过的检查结果当成失败塞给编码者”“第 2 次审查看到的是完整改动”。假 Agent 联机跑通全回路（S5 失败一次、S6 打回一次）。**真实 Agent 跑 S6 还没做。**
