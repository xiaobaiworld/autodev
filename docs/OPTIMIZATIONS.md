## O001：输入加“范围”说明

- **日期**：2026-11-06
- **改了什么**：`templates/pipeline/design.json` 新增顶层字段 `scope`；`write_input`（`src/cockpit/pipeline.py`）把它作为“范围”一节写进每步的 `input.md`。内容是：这是流水线中的一轮，只读“输入文件”里列出的文件和本步骤目录，不要按 `AGENTS.md` 去读 `next.md`、`lessons.md`、`TOOLS.md`、`INDEX.md` 和全局开发规范。
- **为什么**：读 R20261106-003 的 Codex 日志（中台运行 18-1）发现，审查每轮先把 `next.md`、`lessons.md`、`TOOLS.md`、`INDEX.md` 和 iCloud 里的全局规范都读一遍，原因是工作目录在本仓库里，`AGENTS.md` 的“开始任务前”被它照做了。当时的记录里，S3 两步合计输入 551,467 token，是 S2 两步（330,672）的 1.7 倍，而输出只有 2,401。判断：这些文件对审查设计没有用。这是判断，不是已证实的因果。
- **怎么回退**：删掉 `design.json` 的 `scope` 字段即可（`pipeline.py` 里 `SCOPE` 为空就不写这一节），不用改代码。
- **怎么量**：同一个需求（`requests/demo-todo-cli.md`）用同样的配置重跑，对比 S3 的输入 token、返工轮数、结论序列。基线是 R20261106-003。
- **实际结果**（2026-11-06，R20261106-003 对 R20261106-004，各一次）：
  - 总输入 1,022,832 → 550,339（-46%）。**这主要是返工轮数 2 → 1**（R003 的审查打回过一次，R004 一次通过），不能算成 O001 的效果。
  - 看单步更说明问题：S3 第 1 轮输入 279,156 → 266,359（-4.6%），执行命令数 12 → 9；S2 第 1 轮 143,585 → 143,413（基本不变）。
  - 判断：这次看不出“范围说明”显著降低审查的输入。每步 26 万多 token 里，大头可能是 Codex 每轮固有的上下文，这一点我没有拆开验证。命令数少了 3 条，但具体少读了哪些文件我没核对（当时核对命令因工具故障没执行）。
  - 返工轮数变化是单次样本，可能只是运气，不能归因于 O001。
  - 结论：效果不明显，待多跑几遍再定是保留还是回退。
- **已知的比较风险**：Agent 输出有波动（同一个需求之前跑出过 3 轮和 2 轮），轮数不同会直接改变总 token；比较时看 S3 单步的输入更可靠，但样本只有一两个。
- **变更历史**
  - 2026-11-06 应用。
  - 2026-11-06 第一次对比（R003 对 R004）：单步输入 -4.6%，总量下降来自返工轮数不同。保留，未回退。

## O007：两个审查阶段必须对照需求原文，并单列“原文对照”小节

- **日期**：2026-11-06
- **改了什么**：`templates/pipeline/design.json` 的 S3、`build.json` 的 S6 任务说明加了：分析是对需求的转述，转述可能悄悄改了需求，先逐句读需求原文；`review.md` 里必须有一个标题为“原文对照”的小节，逐条列出原文的每个要求并注明它在设计/代码里对应哪里，原文有而分析/设计/代码里没有或被改写的单独标出并定级。模板新增 `required_sections` 字段，`validate_done` 检查产物里有没有这个标题（`src/cockpit/pipeline.py`），没有就判无效输出、重试。
- **为什么**：R20261106-008 一次通过到 S6，但需求原文是“做一个本地命令行待办工具 `todo`”，分析把它改写成“`todo add/list/done` 作为 argparse 子命令”，设计里只有 `python3 src/todo.py`，没有 `todo` 这个可执行入口。R20261106-002 的 S3 曾因此打回过。这次 S3 和 S6 都没指出。判断：审查者对照的是分析而不是原文，分析阶段的一处偏差会让后面所有审查一起放行。这是判断，不是证实的因果。
- **程序能保证的和不能保证的**：程序只检查标题在不在。审查者可以写一个空洞的“原文对照”糊弄过去，程序判断不了写得对不对，这一点要靠多跑几次、读审查内容才能发现。
- **怎么回退**：删掉两处 `required_sections` 和任务说明里新加的那几句。
- **怎么量**：同一个需求重跑，读 S3、S6 的“原文对照”小节：是否逐条列了原文要求、是否标出了 `todo` 命令入口这类偏差；对比 R008。
- **实际结果**：180 个单元测试通过（含小节检查的 5 个）；假 Agent 联机三项通过。真实 Agent 的结果见下一条记录。
- **变更历史**
  - 2026-11-06 应用。

## O006：Agent 进程崩溃时不再等中台的退避，立刻交给步骤重试

- **日期**：2026-11-06
- **改了什么**：`src/driver/runner.py` 的 `make_invoke` 参数从 `step_retries` 改成 `hub_retries`，默认 0：中台这一轮第一次失败（Agent 进程崩溃或非零退出），我们就取消它并报 `command_failed`，由 Controller 自己的步骤重试（`step_retries`，每次是新事件）接手。`driver.run` 和联机脚本不再给它传 `step_retries`。
- **为什么**：S5 联机验证那次，假 Agent 因我的测试缺陷每次崩溃，流水线用了 **2710 秒（45 分钟）** 才转人工：3 次尝试各等 15 分钟超时。原因是中台把崩溃的一轮放回排队、自己退避重试（第 1 次 5 分钟，翻倍），而我们要等中台的重试次数超过 `step_retries` 才放弃，两层重试叠加。确定性的崩溃（同一个 bug 每次必现）不该这样等。
- **怎么回退**：`make_invoke(hub, hub_retries=2)` 就恢复成原来的“允许中台自己重试 2 次”。
- **怎么量**：新增联机场景 `python3 tests/f5_crash.py crash`（假 Agent 每次崩溃）：3 次尝试、4 秒转人工；每次尝试的事件 id 各不相同（`-a1`、`-a2`、`-a3`），没有残留进程。
- **实际结果**：175 个单元测试通过；联机六项（`crash`、`hang`、`ctrl-kill`、`hub-kill`、`--build`、`--fake-rework`）通过。**45 分钟 → 4 秒。**
- **代价（要知道）**：偶发的、重试一次就好的崩溃（比如网络抖动），以前中台会在 5 分钟后自己再试，现在改成我们立刻重发一个新事件，效果类似但多占一次 `step_retries` 的额度。真实 Agent 上的网络类故障没测过。
- **变更历史**
  - 2026-11-06 应用。

## O005：S6 代码审查，厂商不同，审查者只读且被程序盯着

- **日期**：2026-11-06
- **改了什么**：`pipeline/build` 新增 S6（角色 `code_reviewer`，现绑 Claude，与编码者 Codex 厂商不同，D008 的检查扩到每一对作者与审查者）。S5 通过才进 S6；S6 `REWORK` 退回 S4（计数器 `code_review_rounds`，上限 3，超限转人工）。审查者的输入有：需求、分析、设计、计划、**从最初起点到现在的完整改动 `full.patch`**（不是只看本轮增量）、本轮检查结果。任务说明明确写了“测试通过只说明代码通过了自己的测试，不说明测试覆盖了需求”。
- **为什么**：R20261106-007 里 S5 判 PASS，但测试是 Codex 自己写的，S5 证明不了测试覆盖了需求（那次设计走的是 `python3 src/todo.py`，需求要求的是 `todo` 命令）。这一层要由另一个厂商的模型来看。
- **审查者有写权限，所以程序盯着它：** 审查前先把代码提交成检查点并记下内容指纹，审查后再取一次，不一样就判无效、把代码恢复到审查前、按步骤失败重试。这样审查者不能“改了代码再放行”。
- **怎么回退**：`build.json` 里 S5 的 `on.PASS` 改回 `"done"`，删掉 S6。
- **实际结果**：174 个单元测试通过，其中包括“审查者越权改代码被抓住、代码恢复”“S6 退回 S4 时不把通过的检查结果当成失败塞给编码者”“第 2 次审查看到的是完整改动”。假 Agent 联机跑通全回路（S5 失败一次、S6 打回一次）。**真实 Agent 跑 S6 还没做。**
- **测试发现的一个真实缺陷**：最初恢复用的是 S4 开始时的检查点，那会把编码者刚写好的代码一起清掉。改成审查开始前再提交一个检查点。
- **没验证的**：Claude 在审查时是否真的会遵守“只读”（程序能发现它改了，但不能阻止它去改）；审查者能不能读到 `full.patch` 和代码目录（Claude 的 `--add-dir` 范围在真实运行里没试过）。
- **变更历史**
  - 2026-11-06 应用。

## O004：S5 检查由程序运行，不再信 Agent 自述

- **日期**：2026-11-06
- **改了什么**：`pipeline/build` 新增 S5，`runner` 为 `tool`，工具 `check`（`src/cockpit/tools.py`）：S4 完成后，程序在代码目录里运行模板里写的检查命令（现为 `python3 -m unittest discover -s tests`），退出码为 0 且确实跑了测试才算 PASS；失败退回 S4（计数器 `check_rounds`，上限取 `config.yaml` 的 `limits.check_rounds`=3，超限转人工）。每个编码轮开始前把上一轮代码提交成检查点，退回的 S4 在已有代码上修，输入里带上上一轮的 `check.log`。
- **为什么**：R20261106-006 的 S4 报 DONE，“测试通过”只是 Codex 的自述，我当时是手工跑了一遍才确认。这是你说的“每一步都是调用一个工具”，也是“完成以文件为准、不以 Agent 自述为准”原则在编码阶段的落实。
- **怎么回退**：把 `build.json` 里 S4 的 `on.DONE` 改回 `"done"`，删掉 S5 一节。
- **怎么量**：确定性程序，用单元测试和假 Agent 联机验证（`python3 tests/f2_pipeline.py --build`：第 1 轮测试故意失败，S5 判 FAIL、退回 S4 在已有代码上修好、S5 PASS）。真实 Agent 上还没有跑。
- **实际结果**：169 个单元测试通过；联机五项（`--build`、`--fake-rework`、`f5` 三项）通过。**真实 Agent 跑 S5 未做。**
- **没覆盖的安全问题**：S5 执行的是 Agent 刚写的代码，而且在 Agent 沙箱之外。做了的隔离：最小环境变量（不带密钥）、`HOME` 与临时目录指向步骤目录下的草稿目录、不经过 shell、超时杀整个进程组。**没挡住**：网络访问，以及对其他绝对路径的写入（比如被测代码写 `/tmp` 或用户目录下的绝对路径）。检查命令只跑演示项目的测试时可接受；接真实项目前要换成容器或 `sandbox-exec`。
- **变更历史**
  - 2026-11-06 应用。

## O003：代码目录起点自带 `.gitignore`

- **日期**：2026-11-06
- **改了什么**：`src/cockpit/workdir.py` 的 `prepare` 在建起点提交时放一个 `.gitignore`（`__pycache__/`、`*.pyc`）。
- **为什么**：R20261106-006 的 `diff.patch` 里混进了两个 `.pyc` 缓存文件，是 Codex 运行测试产生的。补丁和“改动文件列表”因此不准，而且只改了缓存也会被误判成“有改动”。
- **怎么回退**：删掉 `prepare` 里加 `.gitignore` 的那一行。
- **怎么量**：这是确定性的程序改动，用单元测试验证，不需要多次真实运行：缓存不进补丁（`test_python_cache_never_enters_the_patch`），只改缓存算没有改动（`test_a_cache_only_change_counts_as_no_change`）。
- **实际结果**：154 个单元测试通过。真实 Agent 上还没有重跑确认。
- **变更历史**
  - 2026-11-06 应用。

## O002：范围说明里写明“运行环境没有网络”

- **日期**：2026-11-06
- **改了什么**：`templates/pipeline/design.json` 的 `scope` 末尾加一句：运行环境没有网络，设计和实现只能用 Python 标准库和本机已有的东西，不要依赖需要联网下载安装的包或构建工具（如 pip 安装 setuptools）。`pipeline/build` 继承它，所以设计、审查、编码都会看到。
- **为什么**：R20261106-005 里 S2 设计选了 `pyproject.toml` 加 setuptools 打包，S3 审查放行，S4 Codex 写完代码后验收安装入口时下载 setuptools 失败，如实 BLOCK，流水线转人工。同一个需求在 R20261106-002 里，S3 第 2 轮审查指出过一模一样的问题，第 3 轮设计改成了单文件脚本。也就是说同一类环境问题，审查有时抓到、有时放行，不稳定。判断：把环境事实直接告诉设计者和审查者，比指望审查者每次自己发现更可靠。这是判断，不是已证实的因果。
- **依据的证据与没核实的**：“沙箱没有网络”来自 R005 的 S4 `exec-report.md` 里 Codex 的自述（“构建依赖 setuptools 无法下载（本轮网络不可用）”）。日志里的网络报错我这次没核到，所以这是 Codex 的说法，不是我独立验证的。Claude 的步骤是否也没有网络，没测。
- **怎么回退**：删掉 `scope` 末尾那一句。
- **怎么量**：同一个需求（`requests/demo-todo-cli.md`）、`--kind pipeline/build`、同样的 `--effort low` 重跑，看 S4 是否还 BLOCK、设计里是否还出现需要下载的依赖。基线是 R20261106-005。一次对一次有波动，要多跑几遍才能下结论。
- **实际结果**（2026-11-06，R20261106-005 对 R20261106-006，各一次）：
  - S4 从 BLOCK 变成 DONE。Codex 写的代码在代码目录里，我自己跑了它的测试，4 项通过；`bin/todo` 存在；`exec-report.md` 声明的 4 个文件和 `diff.patch` 对得上。
  - 设计文档：R005 的 S2 第 2 轮写了 `pyproject.toml` 加 setuptools 打包（design.md 里提到 4 次）；R006 的 S2 第 1、2 轮都明确写了“不做打包，不依赖 setuptools/pip”，方向与 O002 一致。
  - 总输入 1,624,763 → 1,424,345（-12%），但**不能归到 O002**：S1 +27%、S3 +32%（O002 不该影响它们），S4 -49% 主要因为 R005 的 S4 把时间花在了尝试安装上。两次的设计和审查轮数相同（都是 S3 第 1 轮 REWORK、第 2 轮 PASS）。
  - 判断：O002 很可能起了作用（设计避开了 setuptools），但这是一对样本，R006 的设计避开 setuptools 也可能只是这次碰巧。R002 的第 3 轮、R003、R004 也都没选 setuptools，说明不加 O002 时也经常避开，所以基线概率不是 100% 踩坑。
  - 结论：保留，需要至少再跑几遍统计 S4 BLOCK 的比例才能算有效。
- **变更历史**
  - 2026-11-06 应用。
  - 2026-11-06 第一次对比（R005 对 R006）：S4 BLOCK → DONE，方向一致，样本不足。保留。
