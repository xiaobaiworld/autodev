# S2 设计：输入输出与交接契约

日期：2026-11-09。状态：对当前实现的核对说明；V2.1 目标单列，未接入的能力不视为已实现。返回 [S2 入口](README.md)。

## 1. 身份与开始条件

本阶段属于某个目标项目的一次运行，不属于某个聊天窗口。项目、运行号、阶段、轮次与尝试的格式见 [DATA_SPEC](../../DATA_SPEC.md)，跨阶段双身份原则见 [D022](../../DECISIONS.md)。

两条上游路径：

| 路径 | 输入来源 | S2 开始点 |
| --- | --- | --- |
| 原始需求走流水线 | 原文与 S1 的 `analysis.md` | S1 ACCEPT 后进入 S2 |
| 需求澄清定稿 | 目标项目 SRS 经 [handoff](../../../src/requirements/handoff.py) 校验并生成 S1 基线 | 新运行从 S2 pending 开始；创建交接记录本身不证明设计 Agent 已执行 |

缺少关键业务信息、输入冲突或无法确认目标项目时，设计者应给出 BLOCK 和证据。现有快照程序会记录缺失资料，不代表它会自动阻断所有缺项。

## 2. 输入与读取范围

实际装配以 [design.json](../../../templates/pipeline/design.json) 的 S2.inputs 和 [write_input](../../../src/cockpit/pipeline.py) 为准：

| 输入 | 内容与用途 | 版本或缺失处理 |
| --- | --- | --- |
| `request` | 原始需求或定稿 SRS 的运行内副本 | 保留原文；不能用分析转述替代 |
| `analysis` | S1 结论、范围与验收清单 | 交接路径由程序生成基线 |
| `project_context` | 目标项目 README 与 `config.yaml` 中显式 context 文件 | 每个 S2 轮次生成快照与 manifest；同轮重试不刷新，S3 使用最新 S2 轮次的同一份快照 |
| `review_prev` | 上轮 S3 问题 | 首轮无；返修应逐项回应 |
| `human` | 本运行 `human/reply-*.md` | 程序列出已有回复；不能假设包含其他渠道的全部聊天历史 |

快照目录：`workspace/runs/<运行号>/context/project-context/round-N/`。快照器拒绝复制仓库外路径，并把缺失或无效路径写入 manifest；它不是对 Agent 进程的操作系统级隔离。

阅读清单分三组：

- 必读：本轮 `input.md`、有效需求与分析、快照清单及其中适用的项目规则、返修意见和人工决定。
- 按需：目标项目明确提供的架构、接口、数据、组件、测试与使用证据；需要补入的资料先通过受控清单提供，作者与审查者共享。
- 不自动加载：其他项目、其他角色全部聊天、无关历史、私人凭证，以及 AutoDev 自己的全部规则。设计 AutoDev 本身时，平台资料才属于目标项目资料。

## 3. 允许输出什么

当前模板只允许产出设计文档，不修改目标项目代码。产物与 `done.json` 写入本轮 `S2-design/round-N/`；模板范围约定不等于已具备细粒度文件沙箱。V2.1 原型代码和 JSON 的受控写范围仍待实施设计。

| 当前产物 | 内容责任 | 下游消费者 |
| --- | --- | --- |
| `design.md` | 架构与数据流、资产复用证据、完整接口契约、界面与交互 | S3、S4、S6、S8 |
| `dev-plan.md` | 可执行任务、依赖、输入输出、接口、测试/验收映射与完成条件 | S3、S4、S6、S8 |
| `prototype.md` | 有 GUI 时提供可评审说明；无 GUI 时说明不适用及实际使用入口 | S3、S4、S6、S8 |
| `response.md` | 返修时逐条回应上轮问题，模板任务要求，但不在固定 outputs 中 | 本轮审查的参考；尚无独立强校验 |
| `done.json` | 角色、运行号、阶段、轮次、结论、非空摘要和文件清单等 | Controller 的完成校验 |

`validate_done` 实际核对完成标记的身份字段、结论、摘要、清单与文件存在，以及模板要求的小节。它不完整验证 Markdown frontmatter、任务可执行性或业务语义；项目身份原则也不能等同于每个完成标记字段都已有强校验。

## 4. 结论与版本交接

DONE → S3 同轮；BLOCK → needs-human。S3 REWORK → 新一轮 S2，受 `design_review_rounds` 限制。实际转移见模板与 `next_move`，人工回复走既有 Controller/driver.reply，不从渠道回调直接改运行状态。

当前下游按运行内最新 S2 轮次读取设计文件；旧轮次保留。完整设计包哈希锁定、改稿使旧审核/原型确认自动失效、正式导出后的持久化与授权启动 S4 协议尚未实现。仅查看设计或结束讨论不构成新设计机器人启动开发的授权；现有 `pipeline/build` 的 S3 PASS 则确实会自动进入 S4，不能混为一条已改造的路径。

## 5. V2.1 目标与执行资产

目标产物、设计等级、规则与验证层级的唯一主规范是 [V2.1](../../Agent自动化设计阶段规范_V2.1.md)，项目取舍见 [采用对照](../../design/2026-11-09-v21-mapping.md)。本契约不另抄一份注册表。

- 静态阶段说明在本目录；可执行规则、Schema 在 [design-system](../../../design-system/README.md)，实现代码在 `src/designsys/`。
- V2.1 的 `design/` 是每次运行的设计包概念，不是本目录，也不是平台方案目录 `docs/design/`。当前旧流水线尚未确定新设计包的接入位置。
- MVP 1 独立模块已实现；当前三份 Markdown 的路径及语义不因本次文档整理改变。不能把模块的 `ready_for_coding` 当作已经接入 Controller 的放行条件。

## 6. 追溯与尚缺内容

本轮 `input.md`、设计文件、`done.json`、`record-aN.json`、`agent-aN.log`、上下文 manifest 与人工回复组成现有证据。实际模型身份能否从日志核实须另行区分，不以请求模型名代替。

待补的是运行能力：V2.1 模板与程序验证接入、关键特征独立核对、版本/导出协议、渠道无关的讨论修订服务与原型检查。工作步骤与完成标准见 [standard.md](standard.md)。
