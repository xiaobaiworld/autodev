# Agent 自动化设计阶段规范 V2.1

> 适用范围：自动化软件开发流水线的第二阶段「设计」。
> 上游：需求分析；下游：代码生成；后续：检查审核。
> 目标：依据已确认需求，自适应选择设计内容，生成可供代码 Agent 消费且可被程序检验的设计包。

## 1. 基本原则

1. **需求基线固定**：设计不得擅自修改已确认需求；缺失信息标记为 `open_questions` 或 `assumptions`。
2. **按需设计**：项目类型决定默认方向，功能特征触发专项产物，复杂度和风险决定设计深度。
3. **最小充分产出**：简单任务允许 D0 直接交接；复杂任务增加原型、数据、接口、架构等产物。
4. **基础工程约束贯穿全流程**：安全、数据、接口、异常等规则从版本化规范库选取，传递到代码生成及检查审核。
5. **机器可读优先**：结构化 JSON/YAML、OpenAPI、可运行原型为主要交付；Markdown用于解释关键设计决策。
6. **生成与验证分离**：Agent生成和语义评审，程序执行格式、引用、覆盖、构建及契约检查。
7. **模板参考与规则约束分离**：模板为Agent提供可复用的设计案例；强制规则由程序独立选择、执行和验证。
8. **规则逐步固化**：将反复发现的设计问题沉淀为有测试证据的确定性规则，保留版本和回滚能力。
9. **允许失败**：阻塞问题未解决时输出 `blocked`，不得为了完成流程强制标记通过。

## 2. 输入与边界

### 2.1 必需输入

- 需求基线：需求ID、描述、优先级、验收条件及来源。
- 项目背景：新建或存量、项目类型、技术栈、现有代码或组件约束。
- 工程规则库：带版本号的安全、数据、接口、异常、UI等规则。

缺少关键输入时记录缺口，必要时停止对应设计任务。设计阶段不重新进行需求分析，不负责完整业务代码实现，也不代替第四阶段的真实安全与功能测试。

### 2.2 固定输出协议

所有项目至少输出：`manifest.json`、`plan.json`、`artifacts/security.json`、`validation.json`、`handoff.json`。其中 `security.json` 可仅记录适用的基础规则及不适用理由；D0不要求额外技术设计文档。

## 3. 项目分类与设计深度

### 3.1 三个独立维度

| 维度 | 用途 | 示例 |
|---|---|---|
| 项目类型 | 决定默认设计方向 | 脚本、CLI、后端服务、Web、移动端、AI应用、复杂平台 |
| 功能特征 | 激活专项设计 | UI、持久化、API、认证、敏感数据、文件、AI、异步任务、外部集成 |
| 复杂度与风险 | 决定设计深度和验证投入 | 交互复杂性、跨模块依赖、安全影响、技术不确定性 |

### 3.2 设计等级

| 等级 | 适用情形 | 产出深度 |
|---|---|---|
| D0 | 简单脚本、局部修复、需求明确且无关键技术风险 | 规则选择、设计跳过理由、开发交接 |
| D1 | 小型服务、CLI、明确的单模块功能 | 简要技术设计和必要契约 |
| D2 | 常规 Web/移动应用、多模块系统 | 按需生成原型、交互、数据、接口、技术设计 |
| D3 | 复杂平台、高风险业务、重大技术不确定性 | D2基础上增加关键方案竞争、独立评审、技术验证 |

风险覆盖等级：涉及敏感数据、身份授权、跨租户访问或高影响操作时，即使UI简单，也必须启用相关安全规则与设计检查。D0只表示跳过独立设计，不表示豁免工程规则。

### 3.3 默认设计矩阵

| 项目类型 | UI原型 | 数据 | API | 安全 | 架构 |
|---|---|---|---|---|---|
| 简单脚本 | 无 | 按需 | 无 | 基础 | 通常无 |
| CLI工具 | 无 | 按需 | 按需 | 基础及特征触发 | 按需 |
| 后端服务 | 无 | 按需 | 有API时必须 | 按特征 | 按需 |
| Web/移动应用 | 有UI时必须 | 按需 | 按需 | 按特征 | 按需 |
| AI应用 | 有UI时必须 | 按需 | 按需 | AI专项 | 按需 |
| 复杂平台 | 有UI时必须 | 通常需要 | 通常需要 | 必须 | 必须 |

此表仅为默认值，最终由功能特征与风险规则覆盖。

## 4. 设计产物注册表

每项产物定义 `artifact_id`、`trigger`、`path`、`schema_version`、`required_fields`、`validators`、`consumers`。初始注册表：

| ID | 产物 | 文件/目录 | 触发条件 | 关键验证 |
|---|---|---|---|---|
| A01 | 设计计划 | `plan.json` | 所有项目 | 分类、规则、产物选择完整 |
| A02 | 可运行UI原型 | `artifacts/prototype/` | 需要UI且D2/D3 | 构建、路由、核心交互、截图 |
| A03 | UI规格 | `artifacts/ui.json` | A02启用 | 页面、状态、交互映射 |
| A04 | 技术设计 | `artifacts/technical.json` | D1及以上 | 模块、依赖、决策、风险 |
| A05 | 数据设计 | `artifacts/data.json` | 持久化或复杂数据流 | 实体、字段、关联、分类、生命周期 |
| A06 | 接口契约 | `artifacts/openapi.yaml` | 存在HTTP API | OpenAPI解析、路径及Schema引用 |
| A07 | 安全约束 | `artifacts/security.json` | 所有项目 | 适用规则及落实位置覆盖 |
| A08 | 开发交接 | `handoff.json` | 所有项目 | 任务、依赖、规则、验收完整 |

可扩展产物：`artifacts/workflows.json`、`artifacts/ai.json`、`artifacts/architecture-decisions.json`、`artifacts/performance.json`。不得仅为凑齐文件而生成空壳文档。

### 4.1 各产物最低内容

- **A01**：项目类型、功能特征、设计等级、判定依据、启用产物、适用规则ID、生成/评审策略、未决问题。
- **A02**：可启动的前端原型、Mock数据、核心页面与状态、必要截图；标识哪些代码可复用、哪些仅供演示。
- **A03**：页面ID、需求ID、路由、主要组件、交互ID、状态、异常/空数据/加载反馈、原型对应位置。
- **A04**：模块职责、输入输出、依赖、关键技术选型、约束、失败处理、需验证的风险；D1允许简写。
- **A05**：实体、字段类型、主键/唯一性、关联、枚举、时间与空值规则、敏感字段标记、必要的数据保留及迁移约束。
- **A06**：接口路径、方法、请求/响应Schema、错误状态、鉴权要求、版本或兼容性约束。
- **A07**：规则ID、适用依据、适用资源/模块、设计落实位置、开发任务绑定、审核验证方法；无用户身份的项目可记录认证规则不适用。
- **A08**：需求基线引用、设计包版本、任务ID、任务依赖、设计文件引用、强制规则ID、验收条件、未解决问题。

## 5. 工程规则库：最低基线

规则库独立于具体项目，统一字段：`id`、`version`、`severity`、`applies_when`、`requirement`、`verification`。设计 Agent 只能选择适用规则和补充项目级决策，不能随意删除强制规则。

### 5.1 安全基线

| ID | 触发条件 | 强制要求 | 后续检查 |
|---|---|---|---|
| SEC-001 | 全部项目 | 密钥和凭证不得硬编码或提交仓库 | 密钥扫描 |
| SEC-002 | 受保护资源 | 服务端执行身份及资源级授权检查 | 授权测试 |
| SEC-003 | 外部输入 | 输入类型、长度、格式校验；避免不安全拼接 | 边界测试、静态检查 |
| SEC-004 | 敏感数据 | 数据分类、最小暴露、日志脱敏、存储与传输保护 | 数据流与日志检查 |
| SEC-005 | 多项目/多租户 | 数据访问隔离，禁止跨边界读取 | 隔离测试 |
| SEC-006 | 文件上传 | 类型、大小、路径和存储访问控制 | 恶意/异常文件测试 |
| SEC-007 | AI/Agent | 不可信内容与指令隔离；工具调用遵守权限边界 | 注入及越权测试 |
| SEC-008 | 关键修改/审批 | 可追踪的操作记录和责任主体 | 审计测试 |

### 5.2 数据基线

| ID | 触发条件 | 强制要求 | 后续检查 |
|---|---|---|---|
| DATA-001 | 持久化实体 | 稳定标识、字段类型、必要唯一约束 | Schema/迁移检查 |
| DATA-002 | 时间数据 | 明确时间格式、时区及存储规则 | 类型与时区测试 |
| DATA-003 | 关联数据 | 明确实体关系、完整性与删除行为 | 关系及约束测试 |
| DATA-004 | 结构变更 | 迁移方案及兼容性要求 | 迁移测试 |
| DATA-005 | 敏感字段 | 字段分类与访问控制关联 | 分类覆盖检查 |
| DATA-006 | AI提取/证据型数据 | 记录来源、定位、版本与核查状态 | 溯源完整性测试 |

### 5.3 其他基线

- **API-001**：有API时明确请求、响应、错误与鉴权契约。
- **ERR-001**：关键失败路径有明确处理、提示及必要的恢复策略。
- **CODE-001**：优先遵循现有技术栈和模块边界，避免无依据引入新依赖。
- **UI-001**：核心操作有加载、成功、失败、空数据状态与可见反馈。

规则的 `applies_when` 必须由分类结果和需求特征驱动。安全规则覆盖率以**全部适用规则**为分母，不得由生成模型自行缩小分母。

## 6. Agent执行流程

### 6.1 规划

1. 读取需求基线、工程规范版本和现有项目约束。
2. 识别项目类型、功能特征、复杂度和风险，输出 A01。
3. 由规则引擎确定必需产物及强制规则，覆盖模型提出的可选清单。
4. 根据等级生成任务计划；D0直接进入交接生成。

### 6.2 设计生成

- UI系统：先生成页面/交互清单，再生成可运行原型；核心页面按需生成多个候选。
- 数据系统：生成最小必要数据模型，落实类型、关联、敏感字段和迁移要求。
- API系统：生成契约并引用一致的数据结构。
- 高风险系统：对关键技术选择生成备选方案并记录取舍。
- 所有系统：将适用工程规则落实到设计对象或开发任务。

### 6.3 候选生成与独立评审

| 风险 | 默认策略 |
|---|---|
| 低 | 单次生成，程序校验 |
| 中 | 单次生成，必要时独立模型评审 |
| 高 | 2至3个候选，程序过滤、独立评审、必要实验 |

评审必须基于同一需求和约束，先剔除违反硬约束的候选，再比较需求满足度、复杂度、维护成本与实现风险。模型评分仅作辅助证据，不可替代程序验证。

### 6.4 问题处理与修复

| 问题 | 处理策略 |
|---|---|
| 格式、字段缺失 | 定向重生成对应产物 |
| 引用、契约不一致 | 修复受影响文件并回归验证 |
| 需求遗漏 | 补充对应设计及追踪关系 |
| 模块设计冲突 | 局部重设计并检查依赖 |
| 重大架构风险 | 重新比较候选方案，必要时技术实验 |
| 无法确定的业务事实 | 记录阻塞问题，禁止模型编造结论 |

建议每类问题最多自动修复3轮；连续无改进或达到成本预算则停止并输出 `blocked`。

## 7. 可程序化验证与验收

### 7.1 四层验证

| 层次 | 内容 | 执行者 |
|---|---|---|
| V1 | 文件存在、语法合法 | 程序 |
| V2 | JSON Schema/OpenAPI结构合法 | 程序 |
| V3 | 需求覆盖、规则覆盖、引用、跨产物一致性 | 程序/规则引擎 |
| V4 | 方案合理性、UI可用性、技术可行性 | 独立模型及必要实验 |

### 7.2 核心量化指标

| 指标 | 定义 | 初始门槛 |
|---|---|---|
| 必需产物完整率 | 已生成且合法的必需产物 / 应生成产物 | 100% |
| 需求设计覆盖率 | 已关联有效设计或D0交接任务的需求 / 适用需求 | 100% |
| 强制规则落实率 | 已绑定设计对象或开发任务的适用强制规则 / 全部适用强制规则 | 100% |
| 结构与引用有效率 | 通过检查的结构及引用项 / 检查总项 | 100% |
| 核心交互验证率 | 通过验证的核心交互 / 应验证核心交互 | 100%，仅UI项目 |
| 阻塞问题数 | 未解决Critical/High问题 | 0 |

以上是初始门槛，项目可版本化调整，但不得降低适用强制安全规则的门禁。模型语义评审应输出问题、证据、置信度与建议，避免把主观分数当作确定性结果。

### 7.3 跨产物一致性示例

当项目涉及项目级数据隔离时，程序至少检查：

1. `security.json` 启用了 `SEC-005`。
2. `data.json` 中受隔离实体存在明确的项目归属或等效隔离机制。
3. `openapi.yaml` 中相关资源接口声明鉴权要求（如存在API）。
4. `handoff.json` 将隔离规则绑定到对应开发任务和审核用例。

### 7.4 原型专项验收

有UI时执行：构建成功、主要路由可访问、核心交互可操作、关键状态可呈现、截图无严重截断或溢出。原型允许使用Mock数据，但必须标识模拟边界。原型与正式技术栈一致时可标记可复用组件；代码生成阶段仍需完成真实业务接入。

### 7.5 退出条件

```text
Design Accepted =
  required_artifacts_valid
  AND mandatory_rules_mapped
  AND references_consistent
  AND required_prototype_checks_passed
  AND blocking_issues == 0
```

设计阶段通过仅表示具备代码生成条件；代码功能、性能和安全有效性由第四阶段检查审核验证。

## 9. 编排程序实现约束

1. **规则引擎确定必需项**：模型提供分类建议，程序根据特征和规则库计算最终产物及规则集合。
2. **统一Schema**：为 `manifest`、`plan`、`ui`、`technical`、`data`、`security`、`validation`、`handoff` 定义JSON Schema；OpenAPI使用标准验证器。
3. **引用可解析**：所有需求ID、规则ID、任务ID、产物路径和验收ID必须存在；不允许孤立引用。
4. **版本锁定**：设计包记录需求基线、规则版本、Schema版本；正式交接时可记录文件哈希。
5. **可重复验证**：验证器输出每项检查的ID、状态、证据路径、失败原因；不依赖自然语言结论。
6. **增量修复**：只重生成受影响产物，并对依赖它的产物执行回归检查。
7. **预算控制**：记录模型、调用次数、Token成本、耗时、修复轮次；高风险任务才启用多候选。
8. **失败可见**：存在未解决阻塞问题时 `ready_for_coding=false`，保留问题清单与已完成产物。

## 10. 设计阶段状态机

```text
received → classified → planned → generating → validating
                                             │
                               ┌─────────────┴─────────────┐
                               │                           │
                            passed                       failed
                               │                           │
                            accepted                  repairing
                                                           │
                                             validating ←───┘
                                                           │
                                                  超预算/无法解决
                                                           │
                                                         blocked
```

所有状态变化保存时间、输入版本、执行器、结果和问题ID。`accepted` 之后向代码生成阶段发送 `manifest.json` 与 `handoff.json`，由代码 Agent 按引用读取具体产物和规则。

## 11. 最小可行落地顺序

**MVP 1：规则与产物闭环**
- 定义项目特征识别与D0至D3分类。
- 建立A01、A04、A05、A07、A08的Schema及规则选择器。
- 实现产物完整性、引用和规则覆盖验证。

**MVP 2：UI原型闭环**
- 增加A02、A03。
- 支持原型构建、页面访问、核心交互检查及截图评审。

**MVP 3：高风险设计优化**
- 增加多候选、独立评审、技术实验、定向修复和成本指标。

## 12. Agent执行指令摘要

> 你负责自动化软件开发流水线的第二阶段设计。输入为已确认的需求基线、项目约束和版本化工程规则。先判断项目类型、功能特征及设计深度，再根据规则引擎确定必需产物。仅生成必要设计；存在UI时按需提供可运行原型；涉及持久化、API、身份、敏感数据、AI等功能时落实相应工程规范。所有产物遵循固定Schema，需求、规则、任务、测试之间必须可追踪。对关键设计问题可生成多个候选并独立评审；对程序校验失败项执行定向修复。最终输出标准设计包、验证报告和开发交接文件。不得虚构业务规则，不得忽略适用强制安全规则，阻塞问题未解决时不得宣称设计通过。


## 13. 模板驱动设计体系

### 13.1 目标与边界

模板用于减少Agent重复推理、统一常见设计结构并提供参考案例。**模板不是需求事实，也不能替代规则引擎**。Agent可以调整推荐结构；凡涉及强制规则的变更，必须经程序校验。模板库与规则库独立版本化。

模板采用可组合的三层结构：

| 模板层级 | 示例 | 提供内容 | 使用方式 |
|---|---|---|---|
| 项目模板 | `web-admin`、`mobile-app`、`api-service`、`cli-tool`、`ai-application` | 默认设计级别建议、常见产物组合、典型目录与交互模式 | 按项目类型选取一个主模板 |
| 功能模板 | `authentication`、`file-upload`、`async-task`、`multi-project-isolation`、`ai-extraction` | 功能流程、常见异常、数据与权限约束、验收案例 | 按已确认功能特征叠加 |
| 产物模板 | `ui-spec`、`data-model`、`security`、`api-contract`、`handoff` | 字段结构、参考示例、对应Schema与检查点 | 按产物注册表生成 |

模板选择应执行：`需求特征识别 → 候选模板匹配 → 冲突检查 → 规则合并 → 设计计划确定`。多模板冲突时，优先遵守需求基线、强制规则与明确技术约束；仍无法决策时生成 `open_questions`，不得任意覆盖。

### 13.2 模板注册格式

每个模板至少包含以下元数据，示例值仅供演示：

```yaml
template_id: web-admin
version: 1.0.0
category: project
applies_when:
  project_types: [web_application]
recommended_artifacts: [A02, A03, A04, A05, A07, A08]
feature_templates: [authentication, file-upload]
required_rule_ids: [SEC-001, DATA-001]
references:
  - examples/web-admin/
conflicts_with: []
```

**强制要求**：`template_id`和版本必须可解析；引用的规则ID、产物ID和功能模板必须存在；示例文件必须可定位。模板不得自行取消已由规则引擎激活的强制规则。

### 13.3 模板组合与覆盖优先级

1. 需求基线与用户明确约束。
2. 已发布的强制工程规则。
3. 项目技术栈及现有代码兼容性约束。
4. 功能模板的适用设计建议。
5. 项目模板和产物模板的推荐结构。
6. Agent自行提出的设计选择。

模板建议被覆盖时，记录 `override_reason`；强制规则冲突时输出 `blocked` 或进入人工确认队列。项目模板只给出默认产物，最终必需产物仍由设计义务矩阵确定。

### 13.4 模板选择产物

在 `plan.json` 中增加：

```json
{
  "template_selection": [
    {"id": "web-admin", "version": "1.0.0", "reason": "web_application"},
    {"id": "file-upload", "version": "1.0.0", "reason": "feature:file_upload"}
  ],
  "template_overrides": [],
  "required_artifacts": ["A01", "A02", "A03", "A04", "A05", "A07", "A08"]
}
```

该片段为新增字段示例，正式结构须与 `plan.schema.json` 合并。程序验证每个模板的适用条件、版本、引用与冲突状态。

## 14. 规则成熟度与确定性固化

### 14.1 规则生命周期

| 级别 | 含义 | 执行主体 | 能否阻断设计 |
|---|---|---|---|
| R0 经验 | 尚未结构化的设计经验 | Agent参考 | 否 |
| R1 结构化 | 有ID、适用条件、要求和检查建议 | Agent辅助评估 | 原则上否 |
| R2 程序验证 | 已实现验证器并具备测试样例 | 程序 | 可在试运行中告警；按发布策略配置 |
| R3 强制 | 验证器通过正反测试和误报评估，正式发布 | 程序 | 是 |

成熟度与严重级别是两个独立字段：`maturity=R3` 表示执行机制成熟；`severity=blocking` 表示违规时阻断。安全高风险要求即使暂处R1，也应由既有强制门禁或人工确认兜底，不能因验证器尚未实现而自动放行。

### 14.2 标准规则结构

```yaml
rule_id: DATA-001
version: 1.0.0
name: 持久化实体主键
category: data
maturity: R3
severity: blocking
applies_when:
  features: [database]
  artifact_types: [A05]
requirement: 每个持久化实体应声明可验证的主键或等效唯一标识。
validator:
  id: validate_entity_primary_key
  version: 1.0.0
  input: artifacts/data.json
  expected_result: pass
fixtures:
  positive: [tests/rules/DATA-001/valid.json]
  negative: [tests/rules/DATA-001/missing-key.json]
```

规则库发布前应检查ID唯一性、Schema合法性、适用条件、验证器存在性及测试样例。规则执行结果必须记录规则版本和验证器版本，便于复现。

### 14.3 从问题到强制规则的固化流程

```text
设计或代码审核发现问题
       ↓
归类并记录可复现案例
       ↓
识别是否具有普遍性
       ↓
创建规则候选（R0/R1）
       ↓
明确适用范围与误报边界
       ↓
实现确定性验证器（R2）
       ↓
正例、反例、边界例及回归测试
       ↓
试运行并统计误报、漏报
       ↓
审批发布（R3）
       ↓
纳入设计阶段与代码审核阶段
```

禁止由Agent根据单个失败案例直接发布R3规则。规则变更必须有变更记录、测试结果和回滚方案。对于无法确定性验证的语义问题，保留模型评审或人工复核，不伪装为程序能够保证的正确性。

## 15. 验证器接口与问题反馈协议

### 15.1 统一验证器契约

每个验证器应声明：`validator_id`、`version`、`supported_artifact_types`、`input_schema`、`rule_ids`、`timeout`、`output_schema`。同一输入、规则版本和执行环境应尽量产生可复现结果；涉及外部状态时记录环境指纹。

验证器统一返回：

```json
{
  "validator_id": "validate_entity_primary_key",
  "validator_version": "1.0.0",
  "rule_id": "DATA-001",
  "rule_version": "1.0.0",
  "artifact": "artifacts/data.json",
  "status": "failed",
  "severity": "blocking",
  "location": "entities.Document",
  "message": "Document实体未声明主键",
  "evidence": {"entity_id": "Document"},
  "repair_hint": "为实体声明主键并检查引用关系"
}
```

状态至少支持 `passed`、`failed`、`not_applicable`、`error`。`error` 表示验证器执行失败，**不得当作通过**；阻断级验证器执行失败时应阻止设计验收。`not_applicable` 必须附适用性判定依据。

### 15.2 分层检查与边界

| 层级 | 检查 | 优先执行者 |
|---|---|---|
| V1 | 文件存在、可解析、Schema合法 | 程序 |
| V2 | 引用、必填项、模板与规则适用性 | 程序 |
| V3 | 数据/API/权限/页面之间的一致性，原型构建与交互测试 | 程序及测试工具 |
| V4 | 方案合理性、交互质量、技术取舍 | 独立模型，必要时技术实验 |

V4的模型分数只能作为辅助信号。凡有确定性验证结果与模型结论冲突，以验证结果为准；发现验证器规则不合理时进入规则变更流程。

### 15.3 自动修复与回归

- 只向修复Agent提供失败规则、证据、相关产物及必要上下文。
- 修复后重新运行受影响验证器及其依赖项的回归检查。
- 对相同问题重复失败、质量下降或超预算的情况停止自动修复并标记 `blocked`。
- 所有修复记录变更前后产物哈希、问题ID、模型版本、验证结果。

## 16. 质量指标与反馈闭环

### 16.1 必备指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 必需产物完成率 | 通过验收的必需产物数 / 应生成的必需产物数 | 判断交付完整性 |
| 强制规则执行率 | 已执行的适用强制规则数 / 应执行的适用强制规则数 | 防止漏检 |
| 强制规则通过率 | 通过的适用强制规则数 / 已执行的适用强制规则数 | 判断是否满足门禁 |
| 确定性规则覆盖率 | 具备程序验证器的适用规则数 / 全部适用规则数 | 衡量规则固化进度 |
| 有效检出率 | 经确认真实的报告问题数 / 报告问题总数 | 监控误报 |
| 设计缺陷逃逸率 | 后续阶段发现的设计缺陷数 / 同一统计窗口确认的全部设计缺陷数 | 衡量前置检查效果 |
| 设计修复成本 | 每个通过设计包的平均模型调用成本与修复轮次 | 控制效率 |

分母为零时记录 `not_applicable`，不得直接填100%。误报率、漏报率需要抽样复核或带标注的测试集；无法确认时标记 `unknown`，不得臆造准确率。

### 16.2 设计阶段通过条件

```text
ready_for_coding =
  所有必需产物存在且Schema有效
  AND 所有适用的强制规则均已执行并通过
  AND 所有阻断级跨产物检查均已通过
  AND 关键原型构建/交互检查通过（适用时）
  AND blocking_issues = 0
  AND handoff.json 通过校验
```

无法程序判定的高风险设计问题必须保留明确的决策状态，按照已配置门禁决定是否阻断。设计验收不代表代码已经安全或业务逻辑已经正确，第四阶段仍须执行代码级验证。

### 16.3 第四阶段反馈到第二阶段

代码生成和检查审核阶段应记录 `origin_stage`、`rule_id`、`artifact_id`、`root_cause`、`fix`、`regression_test`。定期将高频缺陷转换为模板修订、规则候选或验证器回归样例，发布新版本后对历史设计包进行抽样回放，观察漏检和误报变化。

## 17. 目录与版本管理补充

```text
design-system/
├── templates/
│   ├── projects/          # Web后台、API、CLI、AI应用等
│   ├── features/          # 登录、文件上传、异步任务等
│   └── artifacts/         # UI、数据、安全、接口等产物模板
├── rules/
│   ├── security/
│   ├── data/
│   ├── api/
│   └── ui/
├── schemas/               # 模板、规则及设计产物Schema
├── validators/            # 确定性验证器
├── tests/
│   ├── rules/             # 正例、反例、边界样例
│   └── regression/        # 历史缺陷回归
└── feedback/
    ├── design-issues/
    └── rule-candidates/
```

每次设计运行必须锁定：需求基线版本、模板ID及版本、规则集版本、Schema版本、验证器版本、设计Agent模型版本。`manifest.json`记录这些信息以及产物哈希。**升级模板或规则不应静默修改已经验收的设计包**；如需升级，生成新设计版本并重新验证。

## 18. Agent执行指令补充

> 设计前先读取已确认需求与项目约束，依据项目类型、功能特征和风险选择模板，并由规则引擎确定必需产物及强制规则。模板仅供参考，允许在满足需求和强制规则的前提下调整。生成的产物必须遵守对应Schema，保留模板及规则版本。优先运行程序验证，再执行必要的模型评审；修复失败项后执行回归检查。遇到无法确认的业务事实、规则冲突或阻断级验证错误，明确输出 `blocked`。将设计和代码审核中反复出现的问题记录为规则候选，未经测试与发布不得自动升级为强制规则。
